## Project Overview

A standalone desktop markdown previewer built with Rust for **Windows only**. Features at a glance — see the dedicated sections below for details:

- Real-time GitHub-flavored markdown preview with **auto-reload on external file changes**
- **Fully offline capable** — all dependencies bundled locally (no CDN required at runtime)
- Mermaid diagrams, KaTeX math, syntax-highlighted code blocks with copy button, CSV/TSV codeblocks → tables, **copy-any-table-for-PowerPoint** (hover "Copy table" button → native PPT/Word/Excel table via rich-HTML clipboard), **Plotly charts from external CSV/TSV** (`plotly` codeblock with `file:` directive), **ABC music notation** (`abc` codeblock — sheet-music / staff rendering of [ABC notation](https://abcnotation.com/) via the bundled `abcjs`; render-only, no audio playback), **Markwhen timelines** (`markwhen` codeblock — horizontal cascading timeline drawn from [markwhen](https://markwhen.com/) text via the bundled [`@markwhen/parser`](https://www.npmjs.com/package/@markwhen/parser) + a custom SVG renderer), **tikz-cd commutative diagrams** (`tikzcd` codeblock — [tikz-cd](https://ctan.org/pkg/tikz-cd) rendered to inline SVG by a bundled WASM TeX engine [@rod2ik/tikzjax](https://www.npmjs.com/package/@rod2ik/tikzjax); a general `tikz` codeblock uses the same engine; **fully offline**, the project's only WebAssembly + copyleft dependency), Markdown footnotes — see *Preview Pipeline*
- Images served via the `/userfile/` protocol route (lazy, async — fast startup even for image-heavy docs; re-inlined as base64 only at HTML-export time), Obsidian-style `|WxH` sizing, relative-path resolution — see *Preview Pipeline*
- **Video & YouTube embedding** (image syntax `![](clip.mov)` / `![](youtube-url)`; local `.mov`/`.mp4`/`.m4v`/`.webm`/`.ogv`/`.ogg` + YouTube; works in plain docs and Marp) — see *Preview Pipeline*
- Drag & drop file/folder support, `.md` file association, cross-file `.md` link navigation with back/forward history — see *Preview Pipeline*
- **New file creation** (`Ctrl+N` — native Save dialog picks the location, a blank `.md` is created and opened via the normal `OpenFile` flow; an existing target is opened without truncating) — see *Preview Pipeline*
- **Open install directory** (`Ctrl+D` — reveals the folder holding the exe + `assets/` in Explorer via an `openinstalldir:` IPC → `explorer` spawn) — see *Preview Pipeline*
- **GitHub task lists** (`- [ ]` / `- [x]`) render as disabled checkboxes in **both** the normal pipeline and **Marp slides** (marp-core has no task-list plugin, so a DOM post-pass converts them) — see *Preview Pipeline*
- **Definition lists** (`用語` / `: 説明` → `<dl><dt><dd>`, Pandoc / PHP-Markdown-Extra syntax) in **both** the normal pipeline (a `defList` marked extension) and **Marp slides** (a `⦃DL⦄`/`⦃DT⦄`/`⦃DD⦄` sentinel pre/post-pass), themeable via `--md-dl-*` — see *Preview Pipeline*
- **Ruby / 振り仮名** (`｜猫《ねこ》` / `漢字《かんじ》` / `{吾輩|わがはい}`, でんでんマークダウン syntax, incl. **mono ruby** `{漢字|かん|じ}`) in **both** the normal pipeline (a `ruby` marked inline extension) and **Marp slides** (a line-aware pre-pass emitting raw `<ruby>`), themeable via `--md-ruby-*`; `bunko.css` cancels the annotation's line-box reservation so the 行取り grid survives — see *Preview Pipeline*
- **Companion editor window** (`E` key, CodeMirror 6 + Vim, live preview, autocomplete, **Jupyter 風セルモード** — `---`-delimited cells with Esc/Enter two-mode operation, **Office 表の貼り付け変換** — `Ctrl+V` turns a clipboard `<table>` / Excel TSV range into a GFM pipe table, the inverse of "Copy table", **文字サイズの拡縮** — `Ctrl` + `=`/`-`/`0` and `Ctrl`+ホイール scale the editing text only, plus a selectable font family, all gathered with every other preference into a single **`⚙ 設定` モーダル**) — see *Companion Editor Window*
- **Dark / Light toggle** (`M` key), **user-defined styles** picker (`S` key, table modal over `assets/*.css`, with a **⚙ per-style settings pane** driven by a `/* @user-vars */` declaration in the CSS itself — so each theme exposes its own set of adjustable CSS variables), a **`bunko.css` 文庫本レイアウト** (fixed 39字 line length + a 行取り-aligned 16行 page rule with a **ノンブル (page number) under each page**, on top of `tategaki.css`), **auto section numbering** (`N` key), **full-width layout toggle** (`W` key), **per-style HTML exporters** — see *Styles & Theming*
- **Marp presentation slides** (`marp: true` YAML front-matter, 3 view modes via `P` key) — see *Marp Mode*

## Platform Requirements

This application assumes a **Windows environment only**:
- Uses WebView2 (Windows-specific WebView runtime)
- Build target is Windows executable (.exe)
- Window subsystem disabled for Windows release builds (no console window)

## Preview Pipeline

Markdown is rendered server-side to HTML via Rust's `pulldown-cmark` for the initial load and re-rendered client-side via `marked` for live updates. Both pipelines feed into `#preview` in `assets/index.html`.

**Shared webview-side helpers (`assets/index.html`).** The two pipelines and the many Marp pre/post-passes used to hand-roll the same scaffolding repeatedly; these are the single sources of truth, and a new feature should reuse them rather than add a sixth copy:

- **`__makeMdLineScanner(lines)` / `__rewriteMdLines(md, visit)`** — front-matter- and fence-aware line walking, previously written out **five** times inside `renderMarp()`. The scanner is a stateful single-forward-pass classifier returning `'fm' | 'fm-close' | 'fence' | 'code' | 'body'`; lines you skip are never examined, which is what the definition-list pre-pass relies on. `__rewriteMdLines` layers rewriting on top: `visit` is called only for `'body'` lines and may return `undefined` (copy), a `string`, a `string[]`, or `{ out, skip }` to consume a multi-line run. The slide→source-line map uses the classifier directly (it scans a different string and emits nothing). Regexes: `MD_FENCE_RE`, `MD_FM_DELIM_RE`, `SLIDE_SEP_RE`, `COL_DIVIDER_RE`.
- **`__isSentinelP(node, text)` / `__unwrapSentinelRegions(root, opts)`** — the "find an opening sentinel `<p>`, replace it with a wrapper, walk `nextSibling` to the closing sentinel, bucket at separators" shape shared by the inline-columns, alignment and definition-list post-passes. `opts` = `{ open, close, marker, wrap, fill }`; buckets always start with one `{ marker: null, nodes: [] }`. The **split** post-pass deliberately does *not* use it (no opening sentinel, stricter single-text-child predicate, rebuilds the section wholesale, header-hoisting tail) — forcing it in would be a worse abstraction.
- **Fenced-div grammar** — `ALIGN_KW_SRC` and the `ALIGN_*` / `COLS_*` / `FENCED_DIV_CLOSE_RE` constants built from it, plus `normalizeAlignKeyword()` (`centre` → `center`) and `alignKeywordClass()`. Add a keyword **here only**. `ALIGN_SENTINEL_RE` is separate on purpose: it matches an already-normalized sentinel, so it correctly has no `centre` branch.
- **Keyboard shortcuts** — `__isTypingTarget()`, `onPlainKey()`, `onCtrlKey()` (Ctrl/Cmd + letter, Shift excluded), `onShortcutKey()` (prelude only, for multi-key handlers) and `bindBodyClassToggle()` (restore + toggle + persist + toast). The text-entry guard was previously retyped 12 times. The listeners stay separate — their `preventDefault` placement and control flow differ.
- **`__createContextMenu()`** — floating right-click menu (`.app-context-menu` / `.app-menu-item`), owning the viewport clamp and the outside-click / Esc / scroll dismissal. Callers keep their own `contextmenu` listener and target test, so a right-click elsewhere still falls through to WebView2's native menu.
- **Diagram memoization** — `__diagKey()` (theme salt), `__diagCacheSet()` (FIFO cap), `__diagSource(el, attr)` (percent-decoded `data-…-source` with a text fallback) and `__diagCacheHit(cache, key, el)`. There is deliberately **no** all-in-one render wrapper: markwhen cannot supply its cache key up front (the calendar key needs the parsed header's `country` and the month-count fallback), and mermaid caches the raw SVG string it was handed while abc must snapshot `el.innerHTML` after abcjs writes into the element.

**Diagram render memoization** — because `#preview` is rebuilt via `innerHTML` on every render (including every live-edit keystroke, ~150ms debounced), mermaid diagrams are memoized so an unchanged diagram re-attaches its prior output instead of re-running the (expensive) renderer. The shared module-level cache (`__mermaidCache` in `assets/index.html`) is keyed by `(dark/light theme salt + source string)` via `__diagKey()` — the renderer varies its output with `body.dark-mode`, so the theme salt is required for correct invalidation on the `M`-key toggle. The shared helper `renderMermaidCached` is wired into **both** `renderMarp()` and the normal `renderMarkdown()` async render phases. A FIFO cap (`__DIAGRAM_CACHE_MAX = 200`) bounds memory across long sessions; render errors are not cached. (Mermaid's optional `scale:` directive line is part of the cached source string, so changing the factor invalidates the entry — see *Mermaid*.) Plotly is excluded (live interactive widget). **ABC notation** (` ```abc `) is also memoized via `renderAbcCached` / `__abcCache` (wired into both pipelines), but with two differences from mermaid: (1) abcjs renders directly *into* the element (`ABCJS.renderAbc(el, src, …)` returns no HTML), so the helper snapshots `el.innerHTML` *after* rendering to populate the cache; (2) the key is the **raw source with no theme salt** — abcjs output is monochrome SVG recolored for dark mode purely via CSS, so the rendered bytes don't vary by theme and the cache stays valid across the `M`-key toggle. **Markwhen timelines** (` ```markwhen `) are memoized via `renderMarkwhenCached` / `__markwhenCache` (wired into both pipelines), keyed by `__diagKey(src)` **with the theme salt** like mermaid — the renderer bakes concrete light/dark colors into the SVG (the `::highlight`-style `var()` non-inheritance into generated SVG strings makes baked colors the simplest correct choice), so the salt invalidates the entry on the `M`-key toggle. The markwhen **calendar view** (`display: calendar`) uses a *separate* `__markwhenCalCache` whose key additionally carries the holiday country and online/offline state (`|cal|<country>|on|off`), so switching connectivity re-renders with/without holidays — see *Preview Pipeline → Markwhen timelines → Calendar view*. **tikz / tikz-cd** (` ```tikz ` / ` ```tikzcd `) are memoized via `renderTikzCached` / `__tikzCache`, keyed by `kind+source` with **no theme salt** (like abc — the SVG is `currentColor`, recolored for dark mode by CSS) — see *Preview Pipeline → tikz-cd commutative diagrams*.

**Marp instance reuse** — `renderMarp()` builds its `Marp` instance once via `getMarp()` (cached in `__marpInstance`) and registers theme CSS once, instead of `new Marp()` + re-`themeSet.add()` on every render; `marp.render` is effectively pure and `themeSet.add` is idempotent, and theme switching works by rewriting the front-matter `theme:` line against the already-registered theme set.

- **Continuous newline / soft-break join (改行連結)** — a single plain newline inside a paragraph is treated as a *continuation of the same sentence*, not a hard line break. `marked` is configured with **`breaks: false`**, so a plain `\n` renders as a soft break: Latin text joins with a single space (the browser collapses the literal `\n` to a space), while only an explicit hard break (`  \n` two trailing spaces, or a trailing `\`) becomes `<br>`. Between two CJK characters that collapsed space is unwanted, so a post-render DOM pass `applyCjkSoftBreakJoin()` in `assets/index.html` walks the `#preview` text nodes and drops the soft break (plus any spaces hugging it) **only when CJK sits on both sides** — matching GitHub's East-Asian line-break rule; mixed CJK↔Latin boundaries keep their space. The pass uses a `TreeWalker` that skips `pre / code / script / style / textarea / svg / .katex` (so code, math, and inline-SVG diagrams keep their literal newlines) and a lookahead-anchored regex (`CJK_SOFTBREAK_RE`) so consecutive `CJK\nCJK\nCJK` runs all collapse. Wired into **both** `renderMarkdown()` and `renderMarp()` alongside the other post-render passes (after `applyBlockquoteAttribution`). It mutates only inline text, so the block-level `data-line` attributes that drive editor↔preview sync are never disturbed (a source-text join would shift line numbers and was deliberately avoided). Because the switch to `breaks: false` means a no-blank-line `> quote` / `> -- Author` blockquote now carries a literal `\n` instead of a `<br>`, `applyBlockquoteAttribution()` was updated to split on `/<br\s*\/?>|\n/` (and rejoin the body with `\n`) so attribution detection still works. Carries into HTML export automatically (export serializes the post-pass `#preview` DOM). Sample: `samples/softbreak.md`. **Marp caveat** — this pass is effectively a **no-op inside Marp slides**: marp-core (verified against the bundled 4.3.0 by reading `marp.markdown.options.breaks`) runs its markdown-it with **`breaks: true`**, so a soft break there becomes a real `<br>` element rather than a literal `\n` in a text node, and `CJK_SOFTBREAK_RE` never sees it. Don't assume the two pipelines agree on this — it is the reason the definition-list Marp support below had to use a sentinel pre-pass instead of a DOM post-pass.
- **Mermaid** — ` ```mermaid ` fenced blocks are intercepted post-`marked.parse()` and substituted with rendered SVG. Mermaid accepts an optional leading `scale: <factor>` directive line (e.g. `scale: 1.5` enlarges to 150% — useful in Marp where mermaid's natural `max-width` makes diagrams feel small on a 1280px slide): `parseMermaidScale()` in `assets/index.html` strips the leading `scale:`/blank lines before `mermaid.render` (mermaid keys off the first line for the diagram type, so the directive must not reach it) and `applyMermaidScale()` post-multiplies the rendered SVG's `style="max-width:Npx"` (mermaid v10 `useMaxWidth:true` output; falls back to the `width`/`height` attributes otherwise). Works in both pipelines since both go through `renderMermaidCached`; the memoization cache key is the full source incl. the `scale:` line, so changing the factor re-renders (see *Diagram render memoization*). **Node-label clipping fix** — `mermaid.initialize` is fed a shared `mermaidBaseConfig()` (used by both `ensureMermaid()` and the `applyDarkMode()` M-key re-init) that sets `fontFamily` to the page's system-sans stack, so mermaid *measures* label text with the same font it *renders* with; without this the `<foreignObject>` HTML labels inherit Segoe UI (taller than mermaid's default measuring font) and the node box is sized too short, clipping the bottom of the glyphs. A CSS safety net (`.mermaid foreignObject { overflow: visible }` + `box-sizing: content-box` on the label `div`/`span`, undoing the global `* { box-sizing: border-box }`) guards against any residual overflow.
- **YAML front-matter is not rendered** — `marked` has no front-matter tokenizer, so a leading `---\n…\n---` block would otherwise show up as an `<hr>` + text (directives like `confidential:` / `title:` / `theme:` leaking into the preview). `stripFrontMatterKeepingLines()` in `assets/index.html` removes the block at the top of `renderMarkdown()`'s normal branch (after the Marp early-return — Marp docs keep their front-matter for marp-core), replacing it with the **same number of blank lines** rather than deleting it, so every following block keeps its original source line number and the `[data-line]` editor↔preview scroll sync stays accurate. Only a block at the very start of the document is stripped; a later `---` (thematic break) is untouched. Front-matter *values* are still read where needed via the ad-hoc key matchers (`isMarpDocument` / `watermarkSetting`) before the strip.
- **CSV / TSV codeblocks** — fenced ` ```csv ` / ` ```tsv ` render as HTML `<table>` (first row → `<thead>`). CSV parsing follows RFC 4180 (quoted fields may contain commas, newlines, and `""` for a literal quote); TSV splits each line on `\t` with no quoting. Fully-empty rows (blank lines anywhere in the source — leading, between header and body, or trailing) are dropped before the first row is assigned to `<thead>`, so authors can add visual whitespace inside the fence without producing a stray empty `<tr>`. Output wraps the table in `<div class="csv-table">` and inherits each theme's existing table styling. Carries through to HTML export since the live `<table>` DOM is serialized.
- **Plotly charts from external CSV/TSV** — fenced ` ```plotly ` blocks contain a YAML spec referencing an external `.csv` / `.tsv` file (path relative to the `.md`), plus chart-type and column directives. The CSV is fetched via the existing `app://localhost/userfile/...` route (the new `csv` / `tsv` MIME registrations in `get_mime_type` ensure `text/csv; charset=utf-8` / `text/tab-separated-values; charset=utf-8`), parsed with the same `parseCsv()` used by `csv` tables, then handed to `Plotly.newPlot`. Supported `type:` values: `line`, `scatter`, `bar`, `histogram`, `box`, `heatmap`, `surface` (the last two read the CSV as a matrix — row 0 → x labels, col 0 → y labels, remaining cells → z). `y:` may be a list for multiple series; full multi-trace control is also available via a `traces:` list whose `x:`/`y:`/`z:` strings are resolved as CSV column names. Optional `layout:` / `config:` blocks deep-merge into Plotly's layout/config. Plotly.js + js-yaml are lazy-loaded (`ensurePlotly()` / `ensureJsYaml()`) so docs without `plotly` blocks pay no startup cost. **Live reload on external CSV change**: each block posts a `csvwatch:<relpath>` IPC to the Rust host on render, which adds the resolved absolute path to a `watched_csvs: Arc<Mutex<HashSet<PathBuf>>>` and (in single-file mode) calls `watcher.watch()` on it; a `csvwatchreset:` IPC at the start of every render flushes the prior set so only files of the current document are tracked. The notify event handler re-renders the active `.md` when any tracked CSV is modified. Errors (missing `file:`, fetch failure, parse failure, invalid `type:`, missing column) render as a `.plotly-error` red-bordered block in place; other charts on the same page remain unaffected. Carries into Marp slides (separate branch in the Marp `code[class*="language-"]` substitution loop; the `.plotly-block` is a *figure* participant so it is horizontally centered like the other figures via the `.marp-fig` class — see *Marp Mode → Figure horizontal centering*). HTML export snapshots each block's `__plotlySpec` ({traces, layout, config}) onto a `data-plotly-spec` attribute, references Plotly.js via `cdn.jsdelivr.net` (`EXPORT_PLOTLY_JS_CDN`), and ships an inline `initPlotlyArtifact()` that re-runs `Plotly.newPlot` on each block once the deferred CDN script has loaded — so the artifact retains zoom / hover / pan interactivity when hosted on a static server.
- **ABC music notation** — fenced ` ```abc ` blocks contain [ABC notation](https://abcnotation.com/) (the plain-text music notation format) and are rendered as an inline staff SVG via the bundled [`abcjs`](https://github.com/paulrosen/abcjs) (`assets/libs/abcjs/abcjs-basic-min.js`, MIT, lazy-loaded by `ensureAbcjs()` the first time an `abc` block appears). **Render-only — no MIDI/audio playback.** Post-`marked.parse()` the block is replaced with `<div class="abc-notation" data-abc="1" data-abc-source="…">`; `renderAbcCached()` then calls `ABCJS.renderAbc(el, src, { staffwidth: 740, … })` into it. **abcjs emits the `<svg>` with fixed `width`/`height` attributes but no `viewBox`**, so `.abc-notation svg { max-width:100% }` shrinks the SVG *box* while its content stays drawn at absolute `0..width` coordinates — i.e. inside a narrow container (notably a Marp split column, ~245–535px wide) the staff is **clipped on both axes, not scaled**. To fix this `renderAbcCached()` post-processes the rendered SVG: it adds `viewBox="0 0 <w> <h>"` (from the intrinsic `width`/`height`), sets `preserveAspectRatio="xMidYMid meet"`, sets `width="100%"`, caps `style.max-width` at the intrinsic width (so it never upscales beyond native in a wide container), and drops the `height` attribute so the viewBox ratio drives `height:auto`. The result is a responsive SVG that scales-to-fit any container width purely via CSS — **no width measurement**, and correct even when rendered while the slide is `display:none` (e.g. a non-active deck slide), since the cached innerHTML already holds the responsive SVG. This manual viewBox is preferred over abcjs's `responsive:'resize'` (which leaks a window listener that is lost on cached-innerHTML re-insert). Output is pure inline SVG so HTML export carries through with no special snapshot handling. Dark mode recolors the monochrome SVG via CSS (`body.dark-mode .abc-notation svg path/text/rect/line { fill/stroke }`), so the rendered bytes are theme-independent (the memoization cache is therefore un-salted — keyed by the raw source; see *Diagram render memoization*). Errors render as an `.abc-error` red-bordered block in place; other blocks are unaffected. Carries into Marp slides via the same `code[class*="language-"]` substitution loop, and `.abc-notation` is included in the Marp `.marp-fig` figure detection (horizontal centering). Sample: `samples/abcjs.md`.
- **Markwhen timelines** — fenced ` ```markwhen ` blocks contain [markwhen](https://markwhen.com/) text (a markdown-like timeline DSL) and are rendered as a **horizontal cascading timeline** (custom inline-SVG renderer; no iframe / Vue view). The bundled [`@markwhen/parser`](https://www.npmjs.com/package/@markwhen/parser) (esbuild IIFE at `assets/libs/markwhen/markwhen.iife.js`, exposing `window.Markwhen`, lazy-loaded by `ensureMarkwhen()` the first time a `markwhen` block appears) does all the date work — `parse(src)` returns a single timeline whose `events` tree resolves every event's `dateRangeIso.fromDateTimeIso` / `.toDateTimeIso` to absolute ISO strings, so the renderer needs **no runtime date library** (`Date.parse` only). Post-`marked.parse()` the block is replaced with `<div class="markwhen-timeline" data-markwhen-source="…">`; `renderMarkwhenCached(el)` in `assets/index.html` then: walks the `events` tree (`Markwhen.isEvent()` distinguishes an `Event` from an `EventGroup`), flattening it into rows — each `EventGroup` with a non-empty `title` emits an indented section label and bumps the depth; each `Event` emits a row using `firstLine.restTrimmed` as its label; gets the overall span from `Markwhen.ranges(root, [])` (`{fromDateTime,toDateTime}`, falling back to scanning events); picks axis tick granularity (years > ~3y span, else months, else day-ish); and emits one responsive `<svg>` (`viewBox` + `width:100%`/`height:auto`) with gridlines + a time axis, one row per item, **range events as bars / single-date events as dots**, positioned by date. Tag color comes from the markwhen header (`#tag: color` lines — the parser escapes the leading `#` to `)`, so the lookup is `header[")"+tag]`, validated with `CSS.supports('color', …)`), else a stable hashed palette color; light/dark palettes are chosen at render time. Memoized via `__markwhenCache` keyed by `__diagKey(src)` (theme-salted, since concrete colors are baked into the SVG — see *Diagram render memoization*). Errors render as a `.markwhen-error` red-bordered block in place; other blocks are unaffected. Output is pure inline SVG so **HTML export carries through with no special snapshot handling**, and it works in **Marp** via the same `code[class*="language-"]` substitution loop (`.markwhen-timeline` is included in the `.marp-fig` figure detection so a timeline on a non-split slide is horizontally centered). Built by `tools/build-markwhen/` (see *Architecture → Tools*). Sample: `samples/markwhen.md`.
- **tikz-cd commutative diagrams (` ```tikzcd `) + general TikZ (` ```tikz `)** — fenced blocks are rendered to **inline SVG by a bundled WASM TeX engine**, [@rod2ik/tikzjax](https://www.npmjs.com/package/@rod2ik/tikzjax) (`assets/libs/tikzjax/dist/`, ~7.7MB: `tikzjax.js` orchestrator + `run-tex.js` engine + `tex.wasm.gz` + `core.dump.gz` + `fonts/*.woff2` + on-demand `tex_files/*.gz`). This is the project's **first WebAssembly** dependency and **first copyleft (GPL/LPPL)** dependency; it's **fully offline** and **lazy-loaded** by `ensureTikz()` only when a `tikz`/`tikzcd` block appears (docs without one pay nothing). `ensureTikz()` sets `window.TikzJaxOptions.assetBaseUrl` to an **absolute** URL (`new URL('libs/tikzjax/dist', document.baseURI)`) — the TeX engine runs in a blob **Web Worker** whose base URL is opaque, so a relative base can't resolve the on-demand `tex_files/*.gz` fetches (they'd 404 and break package loads like tikz-cd) — and injects a `<link>` to `fonts.css` (glyphs are PUA-mapped `<text>` in the Computer-Modern web fonts, not embedded paths). Post-`marked.parse()` each block becomes `<div class="tikzcd-diagram|tikz-diagram" data-tikz-kind="cd|raw" data-tikz-source="…">`; **`renderTikzCached(el)`** injects a `<script type="text/tikz">` (auto-wrapping a `tikzcd` body in `\begin{tikzcd}…\end{tikzcd}` with `data-tex-packages='{"tikz-cd":"","amssymb":""}"`; the body is **whitespace-trimmed** because a blank line inside a tikzcd matrix becomes a `\par` → the cryptic "Missing $ inserted") which tikzjax's `document.body` `MutationObserver` auto-compiles in the worker; `__tikzAwait(el)` resolves when the wrapper drops its `tikzjax-loading` class (success **or** a broken-image failure — no 30s wait) or on a 30s timeout, then the finished `el.innerHTML` is memoized. **Diagrams render small, so they're enlarged by default** — `__applyTikzScale()` multiplies the finished SVG's intrinsic `width`/`height` (its `viewBox` drives clean scaling; `max-width:100%` still caps an oversize result) by `__TIKZ_SCALE = 1.6`, overridable per block with a leading `scale: <n>` directive line (stripped before the TeX body, mirroring mermaid's `scale:`; the full source incl. that line keys the cache). **NOTE** some diagrams (curved/diagonal arrows) contain a dvisvgm-emitted *nested* `<svg>` inside the outer one — `__applyTikzScale` scales the **outer** wrapper svg only, so the whole figure scales together. Cache **`__tikzCache`** is un-salted (keyed by `kind+source`, like abc) because the SVG uses `stroke/fill=currentColor` → **dark mode is a CSS `color` change** (`body.dark-mode .tikzcd-diagram .tikzjax-wrapper { color:#d0d0d0 !important }` overrides tikzjax's inline black). A failed compile (tikzjax's `.tikzjax-broken-wrapper`/`.tikzjax-broken-image`) is replaced with a styled `.tikz-error` block. **Rendering is fire-and-forget (NOT awaited before `__emitRenderDone`)** — a TeX compile takes seconds and a bad diagram waits out the 30s timeout, so awaiting it would freeze the "読み込み中" splash (hidden only after `renderMarkdown` resolves); each block shows a "コンパイル中…" placeholder and fills in async. Wired into **both** pipelines (Marp uses the same `renderTikzCached`; `.tikzcd-diagram`/`.tikz-diagram` are in the `.marp-fig` figure-centering set). **HTML export**: the inline SVG carries through the cloned DOM, but glyphs need the CM fonts — so `buildExportArtifact()` collects the `font-family` values used across tikz SVGs and inlines just those `libs/tikzjax/dist/fonts/<name>.woff2` as base64 `@font-face` (else PUA glyphs render as blank tofu). **`--export-png` does NOT capture tikz** — the headless hidden window can't run the wasm Web Worker (documented limitation; awaiting would hang, which is another reason rendering is fire-and-forget). `src/main.rs` `get_mime_type` gained `Some("wasm") => "application/wasm"` (the `.gz` assets stay `application/octet-stream` and are decompressed in JS). Fetched (as an extracted npm tarball) by `tools/fetch-libs.ps1`. Sample: `samples/tikzcd.md` and the 可換図式 slide in `samples/marp.md`.

- **Edit table** — a hover **"Edit table"** button (next to "Copy table") turns a rendered GFM pipe table into an editable grid and writes the result back to the source `.md`. **No Rust change** — it reuses the generic `savefile:` IPC (`src/main.rs`), exactly as the Marp theme picker does.

Cells are `contenteditable="plaintext-only"` and shown monospaced.
  - **Row / column operations** come from a right-click menu on a cell, built with the shared `__createContextMenu()` (Insert row above / below, Delete row, Insert column left / right, Delete column, Align column left / center / right). The menu is scoped to `.table-editing` cells, which also resolves the collision with `setupMathContextMenu()` — an editing cell holds source text, so it can never contain a `.katex` for both menus to match. Deleting the last row or column is `disabled`; header cells disable the row items.
  - **Source location is refuse-first.** `data-line` gives the start line and the retained `__blockTokens` entry (from `computeBlockLineNumbers`, so no re-lex and no change to the fragile positional `stampLineNumbers()`) gives the span via `token.raw` with trailing newlines trimmed. Then the parsed source's shape must match the rendered table's `<th>` / `<tbody>` counts. Anything unproven is refused with a toast rather than spliced: a table nested in a blockquote / list / column (its `data-line` resolves to the ancestor, so the real span is unknown), a `csv`/`tsv` block (`renderDataTable()` drops blank rows, so the round trip is lossy), Marp, or a missing `currentFilePath`.
  - **The emitter preserves the source's own formatting** so committing never reformats lines the user did not touch — indent, optional outer pipes, `| a |` vs `|a|`, the original per-column dash run, and column padding in either of the two conventions found in the wild (`left` = pad right, what people type by hand; `align` = padding follows the alignment marker, what Prettier / VS Code emit, so a `--:` column pads on the LEFT). Padding of the content and of the delimiter row are detected **independently** — a source can pad one and not the other. Widths are measured in **display columns** (CJK = 2), since these documents are mostly Japanese. The property the tests assert is idempotency: `tblEmit(tblParse(lines)) === lines` byte for byte.
  - **Splicing is offset-based** (`tblReplaceLines`), so only the replaced span changes and the file's EOLs — CRLF or LF, and a missing trailing newline — are left alone. A line-split/join round trip would rewrite every EOL in the document.
  - **One write per commit.** Each `savefile:` costs a 1.5 s watcher-suppression entry plus a full re-render, so per-keystroke saving is not an option. Commit also re-checks that the span still matches what was read (optimistic concurrency) and refuses if it changed underneath.
  - **An inbound render abandons the session with a toast.** `#preview` is replaced wholesale by every render — the watcher, link navigation, `M`/`S`, `csvwatch:`, and above all the companion editor's live channel on each keystroke — and that content is authoritative, so the render is never skipped (a stale preview would be worse). Known limitation: `EditorRegistry::push_file_to_editor` clears the editor's dirty flag unconditionally, so a preview-side save while the paired editor has unsaved changes can overwrite them; in practice typing in the editor fires the abort above first.

- **Footnotes** — standard Markdown footnote syntax (`[^id]` references and `[^id]: body` definitions, including multi-paragraph indented bodies). - **`data-line` fidelity (a precondition for anything that splices source)** — `data-line` is meant to be a faithful 1-based line number into the LF-normalized source, and every preprocessing pass in `renderMarkdown()` must therefore preserve the line count. Two passes did not, and their errors compounded: `extractMathInto()` padded a masked fenced block with `'\n'.repeat(n)` *and* restored the fence verbatim at the end, so every code block inflated the count by (fence lines − 1); and `extractFootnoteDefinitions()` deleted definition lines outright. Together they made `data-line` wrong by tens of lines in ordinary documents — `samples/sample.md` (153 lines) stamped a heading as `data-line=176` — silently breaking editor↔preview scroll sync and the `jumpto:` reverse jump, and making any `data-line`-keyed source splice unsafe. Both are fixed (the fence placeholder needs **no** padding precisely because it is restored verbatim), and `data-line` now matches real source lines exactly. **If you add a preprocessing pass, it must be line-count preserving**; the regression net is `tools/preview-harness/domdump.py` (the digest records `data-line` per block, so any drift shows up as a diff).

- **Image serving via the `/userfile/` protocol (NOT base64)** — local images are served lazily through the `app://localhost/userfile/...` custom-protocol route (the same route videos use), **not** base64-inlined into the markdown. This was a deliberate performance change: inlining a large image set (e.g. an image-heavy Marp deck — ~40 MB of images) produced a ~53 MB data-URI string that had to be marshalled through `evaluate_script` as a JS source literal, parsed, and decoded synchronously on `innerHTML`, making startup very slow. Now the webview's `transformImagePath()` (in `assets/index.html`) rewrites every local image `src` (`img/foo.png` → `/userfile/img/foo.png` via `toUserfileUrl()`) so WebView2 fetches/decodes images in parallel off the UI thread with native caching; image `<img>`s also get `decoding="async"`. `transformImagePath()` skips external URLs / data URIs and **video** paths (those are left for `applyVideoEmbeds()`, which builds its own `/userfile/` URL — double-prefixing must be avoided). Relative paths resolve against the open file's directory via the route's `current_dir` (`Arc<Mutex<…>>`), identical to the video mechanism. **The Rust-side base64 embedding has been removed entirely** — `embed_images_as_base64` and its `IMG_RE` / `IMG_CACHE` statics are gone. They had become unreachable: the skip list (originally video-only) grew to cover every image extension, and every image MIME `get_mime_type` knows is in it, so the encode path could only ever fire for a non-renderable extension. **Raw vs. content channel** — `FileData` still carries both `content` and `raw`; they are now equal (both relative paths), but the distinction is kept so any host-bound save (the Marp theme picker's `savefile:` IPC) still serializes `currentMarkdownRaw`. **HTML export re-inlines images as base64** to stay self-contained: `buildExportArtifact()` in `assets/index.html` walks the cloned `<img>`s whose `src` is a `/userfile/` URL, `fetch()`es each unique one (the protocol route reads it off disk), converts the blob to a data URI via `FileReader`, and writes it back onto the clone (parallelized with `Promise.all`) — so single-file exports remain one self-contained `.html` exactly as before. Export is a one-shot user action, so the fetch latency is acceptable.
- **Image sizing** — Obsidian-style pipe syntax inside the alt text: `![alt|300](p)` (width px), `![alt|300x200](p)` (width × height), `![alt|x200](p)` (height-only), `![alt|@0.5](p)` (scale × intrinsic size). Implemented as a webview-side pass (`applyImageSizing()` in `assets/index.html`) that runs after both `marked.parse()` and `renderMarp()`. Pixel dimensions become `width`/`height` attributes; scale resolves to a concrete `width` once the image reports its `naturalWidth` (images now load asynchronously via the `/userfile/` route, so `applyImageSizing` reads `naturalWidth` on the `load` event when the image isn't yet `complete`). - **Relative image paths** are resolved against the directory of the open markdown file (current-directory tracked in `src/main.rs` via `Arc<Mutex<…>>`). **Parent-directory references (`../`, `../../`, …) that climb above the document directory are supported.** The Rust `/userfile/` resolver already handles `..` (`Component::ParentDir => resolved.pop()`, no boundary guard — escaping the doc dir is intentional). The catch is browser URL normalization: the page is served on the synthetic `https://app.localhost/` origin, so a relative `/userfile/../x` would be collapsed by the URL parser *past* the `/userfile/` prefix (→ `/x`, losing the route) before the request reaches Rust. So `toUserfileUrl()` in `assets/index.html` detects (via `relPathEscapesBase()`) when a relative path escapes the document directory and, when it does, resolves it to an **absolute** path (reusing `resolveRelativePath()` against `currentFilePath`'s dir, stripping the `file:///` prefix) — an absolute `/userfile/C:/…` path has no `..` to collapse and hits Rust's `file_path.is_absolute()` branch directly. Non-escaping paths (`img/foo.png`, `sub/../foo.png`) keep the original relative `/userfile/…` form. This covers images, `applyVideoEmbeds()` videos, and the `plotly` block's `file:` CSV (which now routes through `toUserfileUrl()` too) — all share the one helper. Sample: `samples/parent-paths/demo.md`.
  - **Non-ASCII (e.g. Japanese) paths** — `marked` percent-encodes non-ASCII characters in `<img>` / `<a>` URLs (`画像.png` → `%E7%94%BB%E5%83%8F.png`), while raw paths (file drops, `plotly` `file:`) arrive unencoded. `toUserfileUrl()` must not `encodeURI()` these — `encodeURI()` is **not idempotent** and re-encodes an existing `%E6` into `%25E6`, producing a double-encoded URL that Rust's single `urlencoding::decode()` can't recover (→ 404). Instead a shared **`encodePathForUserfile()`** helper in `assets/index.html` normalizes each `/`-split segment by decoding then re-encoding once (`encodeURIComponent(decodeURIComponent(seg))`), skipping empty / `.` / `..` / Windows drive-letter (`C:`) segments — idempotent for both raw and pre-encoded input. Used by all three `toUserfileUrl()` return paths and the workspace-export fetch. (Cross-file `.md` link nav via `openmd:` needs no such fix — the click handler's `decodeURIComponent` already normalizes `marked`'s encoding before the raw path reaches Rust.) Sample: `samples/japanese-path/文書.md`.
- **Video & YouTube embedding** — the image syntax `![alt](target)` is reused for video. `applyVideoEmbeds()` in `assets/index.html` runs a webview-side `<img>` scan (immediately *before* `applyImageSizing()`, in both the normal pipeline and `renderMarp()`) and converts: (a) a `src` whose extension is a video file (`.mov` / `.mp4` / `.m4v` / `.webm` / `.ogv` / `.ogg`) into `<video class="video-embed" controls preload="metadata">` with a `<source>` routed through the `/userfile/` protocol route; (b) a YouTube URL (`youtu.be/ID`, `youtube.com/watch?v=ID`, `…/embed/ID`, `…/shorts/ID`) into a responsive `<iframe class="video-embed youtube-embed">` (start offset parsed from `?t=` / `?start=`, accepting `90`, `1m30s`, or `90s`). The Obsidian `|W` / `|WxH` pixel sizing suffix (in the **alt text**, e.g. `![alt|480](clip.mp4)` — *not* inside the URL, where `marked`/marp-core percent-encode the `|` to `%7C` and it fails to match) is consumed here for videos (`@scale` is image-only). The alt is parsed by a shared **`parseVideoAlt(alt)`** helper (returns `{text, widthCss, heightCss, frameTime}`) that splits the alt on `|` and picks out, order-independently, a size token (`W` / `WxH` / `xH`) and a **PDF frame-time token `t=<time>`** (`parseTimeSpec()` accepts `3` / `2.5` / `90s` / `1m30s` / `0:03` / `1:02:03`); the frame time is stored on `video.dataset.pdfFrameTime` and used at PDF-export time to rasterize a still frame (see *Export → PDF export → video frames*), and the video is also seeked to it on `loadedmetadata` so the preview shows that frame. **Marp-native image sizing directives are honored for video/YouTube too**: marp-core translates `![w:400 h:225](…)` / `![width:400px](…)` into an inline `style="width:…;height:…"` on the `<img>`, and `applyVideoEmbeds()` carries that inline width/height (px **or** %) onto the generated `<video>` / `<iframe>` when no alt suffix is present — this is what fixes "Marp スライドで動画サイズ調整が効かない" (the swapped-in element previously discarded the `<img>`'s marp style). All sizes are applied via **inline `style` on the embed** (not `width`/`height` attributes), so they beat the `#preview video.video-embed { height:auto }` stylesheet rule and an explicitly-requested height actually takes effect; when only a width is given, height is left unset so `height:auto` (video) / `aspect-ratio:16/9` (the `iframe.youtube-embed:not([width])` rule) preserves the ratio. **Local videos are deliberately *not* base64-embedded** — `embed_images_as_base64` in `src/main.rs` skips video extensions (and now image extensions too — see *Image serving via the `/userfile/` protocol*) so the path passes through to JS and is served lazily via the `/userfile/` route, which now honors HTTP `Range` requests (`parse_byte_range` + a `206 Partial Content` branch) so seeking/scrubbing works. `.mov` plays only when its codec is Chromium-supported (H.264 ok; ProRes/HEVC not). YouTube `<iframe>`s survive HTML export unchanged; local videos are copied (see *Export*). The Marp figure-centering pass treats `<video>` / `iframe.video-embed` (and a paragraph whose sole child is one) as a figure.
- **Cross-file `.md` link navigation** — clicking a link to another `.md` / `.markdown` file re-opens it in the current viewer (WebView2 blocks `file://` navigation, so the click is routed back to the Rust host via `openmd:` IPC). **Relative links resolve against the document directory in the click handler** — Rust's `to_abs()` resolves a relative path against the *process CWD* (the wrong directory), so a bare `openmd:./foo.md` would fail. The normal pipeline sidesteps this by rewriting every `<a href>` to an absolute `file:///` path at render time (`resolveRelativePath()` in `renderMarkdown()`), but **the Marp pipeline leaves hrefs relative** (marp-core renders them as-is). So the delegated `#preview` click handler in `assets/index.html` resolves any still-relative `.md`/`.markdown` href against `currentFilePath`'s directory (via `resolveRelativePath()`) before posting `openmd:<abs>` — this is what makes **links inside Marp slides** work (they otherwise silently no-op'd because the relative path never resolved). Absolute (`C:\…`) and `file://` hrefs are passed through unchanged, so the normal pipeline is unaffected.
- **Back / Forward history** — each cross-file navigation pushes a `history.pushState` entry, so WebView2's native context-menu「戻る」/「進む」, `Alt+←` / `Alt+→`, and mouse side buttons traverse previously opened files. `popstate` routes the stored filepath back to Rust via the same `openmd:` IPC. **View position is preserved across Back/Forward** — the current view position is persisted per history entry as a source line in `history.state.line` and restored on return, so navigating back to a Marp deck lands on the **slide you were viewing** (not slide 1) and a plain doc restores its **scroll position**. The line is written by `__syncHistoryLine()` in `assets/index.html`, which reuses `currentPreviewLine()` (resolves the right line for deck active-slide / list / scroll / plain-doc modes) to `history.replaceState({...state, line})` the *current* entry — a continuous-sync design (updated whenever the view changes, not snapshotted on leave), since the History API can only edit the current entry, which keeps multi-hop Back/Forward correct. Two triggers feed it: **deck slide changes** via a call at the end of `__marpUpdateDeck()` (the single funnel for every deck move; deck navigation doesn't scroll the container), and **scrolling** via a debounced `previewContainer` `scroll` listener (plain docs + Marp scroll mode). A `__loadingFile` guard suppresses sync while a load is in flight (`history.state` is transient during render, so an unguarded sync would write the new doc's line onto the *outgoing* entry). On `popstate` the handler stashes `e.state.line` in `pendingHistLine`; after the file re-renders, `loadFileFromRust()` calls `applyEditorScroll(pendingHistLine)` (the same editor→preview bridge — deck branch advances the deck to the matching slide, scroll branch scrolls with the shared 25% top margin so the round-trip is stable) and re-stores the line on the (popstate-)replaced entry. No Rust change. `list` mode has no scroll target so restore is a no-op there. Sample: the リンク検証 slide in `samples/marp.md` (a cross-file link to click, then `Alt+←` back to confirm the slide is restored).
- **Drag & drop opening** — handled by a **wry file-drop handler** registered on the WebView via `WebViewBuilder::with_file_drop_handler` (`src/main.rs`). This is required because on Windows WebView2's own HTML5 drag-drop consumes file drops over the webview, so a JS `drop` event never carries a usable file path (`File.path` doesn't exist), and only folders — which HTML5 can't accept — used to bubble up to tao's `WindowEvent::DroppedFile`. wry's handler **revokes WebView2's drop target** (so the JS `handleDrop()` in `assets/index.html` no longer fires — it's now a no-op fallback) and hands the Rust host the dropped items' **real absolute paths**. On `FileDropEvent::Dropped`, paths are routed by preference **directory > markdown > image**: a folder dispatches `CustomEvent::OpenDirectory` (workspace mode); a `.md` / `.markdown` file dispatches `CustomEvent::OpenFile` — the *same* pipeline as double-click / CLI-arg / cross-file links — so the watcher, `current_dir` / `current_file` state, on-disk relative-image resolution (via `/userfile/`), and editor pairing are all set up identically (pressing `E` opens the companion editor); a single image dispatches `CustomEvent::OpenImage`, which points `current_dir` at the image's folder, clears `current_file`, and calls `window.loadImageFromRust(name)` to show it via the `/userfile/` route. The tao-level `WindowEvent::DroppedFile` arm is kept folder-only as a fallback for any drop that bypasses the webview handler. (Earlier, markdown drops were loaded entirely in JS via `FileReader`, which base64-inlined loose images dropped alongside the `.md` but couldn't learn the file's path — so `current_file` stayed unset and `E` failed with "no file is currently loaded".)
- **New file creation** (`Ctrl+N`) — a dedicated `Ctrl+N` keydown listener in `assets/index.html` (sibling to the `E`-key handler; `preventDefault()`s to suppress any WebView2 "new window" default) posts a payload-less `newfile:` IPC. The Rust handler (in the IPC chain next to `exporthtml:` in `src/main.rs`) runs an `rfd::FileDialog` Save dialog on a worker thread (same off-thread pattern as the export handlers), seeded with `untitled.md` and the current file's directory; on confirm it forces a `.md` extension if the chosen name lacks `md`/`markdown`, writes an **empty** file **only when the path doesn't already exist** (an existing target is opened *as-is* — never truncated, to avoid clobbering content via the dialog's overwrite prompt), then dispatches `CustomEvent::OpenFile(path)`. From there the standard `OpenFile` handler does everything else (watcher swap, `current_file`/`current_dir`, render, and — in workspace mode — the recursive watcher refreshes the tree + `__setActiveFile` highlight), so no new state model is introduced. The editor is *not* auto-spawned; press `E` to start writing.
- **Open install directory** (`Ctrl+D`) — a dedicated `Ctrl+D` keydown listener in `assets/index.html` (sibling to the `Ctrl+N` handler; requires ctrl/meta and not alt/shift, `preventDefault()`s to suppress the browser bookmark default) posts a payload-less `openinstalldir:` IPC. - **GitHub task lists** (`- [ ]` / `- [x]`) — rendered as **disabled checkboxes** in both pipelines by the shared `applyTaskLists(liNodes)` DOM post-pass in `assets/index.html` (wired into `renderMarkdown()` after `applyBlockquoteAttribution`, and into `renderMarp()` after the code-block substitution loop). Two cases are normalized to the canonical GFM DOM shape: (a) the **normal pipeline** — `marked` (`gfm:true`) already inserts a `<input type=checkbox disabled>` but this build tags neither the `<li>` nor the `<ul>`, so the pass just adds the `.task-list-item` / `.contains-task-list` classes; (b) **Marp** — marp-core's markdown-it ships no task-list plugin, so `- [ ]` survives as literal `[ ] …` text in a plain `<li>`, and the pass strips the leading `[ ]`/`[x]`/`[X]` (matched with `/^(\s*)\[([ xX])\]\s+/` on the `<li>`'s or its leading `<p>`'s first text node), prepends a disabled checkbox (checked for `x`/`X`), and adds the same classes. - **Definition lists** (`用語` / `: 説明` → `<dl><dt><dd>`) — Pandoc / PHP-Markdown-Extra syntax: a one-line term, then one or more `: ` lines (each becoming a `<dd>`). Consecutive term/definition groups merge into a **single `<dl>`**; a blank line between term and definition is Pandoc's **loose** form and only adds the `.dl-loose` class (identical DOM, wider spacing). Continuation lines must be indented **≥2 spaces or a tab** (2, not Pandoc's 4, to match the `: ` marker width) and there is **no lazy continuation**, so a following fence / heading / prose line cleanly ends the list; an indented `<dd>` body is block-parsed, so multiple paragraphs, lists, code fences and images all work inside a definition. A shared line-based scanner **`scanDefList(lines, start)`** in `assets/index.html` is the single source of truth for both pipelines (same design as `buildSpanStyle()` for the styled span), so they cannot drift.
  - **Normal pipeline** — the block-level `defList` marked extension (registered next to `alignDiv` / `columnsDiv`). Two subtleties drove its shape: (1) marked tries **custom block extensions before its own `fences`/`heading`/`hr`/`list`/`table` tokenizers**, so the term line is guarded by `DL_TERM_BAD_RE` (rejects anything that looks like another block construct — without it `# 見出し` + `: x` would become a `<dt>`); `DL_MARK_RE` requires `:` **plus a space/tab**, so `:::` fenced divs and a GFM `:---|---:` alignment row never match. (2) marked calls `startBlock(src.slice(1))` and clips a would-be paragraph to `src.substring(0, min + 1)` — that is the *only* mechanism stopping a preceding paragraph from swallowing the term, so `start()` returns the sliced index of a term line and **never 0** (0 would clip after the first character and split a word). Only **one term line per group** (Pandoc's rule, not PHP-Extra's multiple `<dt>`): allowing several made the tokenizer match at `^` for `Intro paragraph.\n用語\n: 説明`, emitting `<dt>Intro paragraph.</dt>` and robbing `start()` of its chance. `<dt>` is inline-parsed (a term is a phrase), `<dd>` is block-parsed with `lexer.state.top` forced true so a single-paragraph body still yields a `paragraph` token inside a list item; the renderer unwraps that lone `<p>` so a tight `<dd>` is bare inline HTML. It emits exactly **one** top-level element, which is what lets `stampLineNumbers()` (positional over `preview.children`) give the `<dl>` its `data-line` for editor↔preview sync with no extra code — don't add sibling wrappers.
  - **Marp** — a **sentinel pre-pass + DOM post-pass**, not a DOM-only pass: marp-core runs markdown-it with `breaks: true` (see *Continuous newline* above), so `用語`/`: 説明` collapses into one `<p>用語<br>: 説明</p>`. Emitting raw `<dl>`/`<dt>`/`<dd>` is also not viable even under `html: true` — those are CommonMark **HTML-block** tags, so markdown-it passes their content through verbatim and `**用語**` would show literal asterisks. So the pre-pass (the **last** one in `renderMarp()`, after the fenced-div pass, so every `:::` is already an `⦃ALIGN…⦄` / `⦃COLS…⦄` sentinel — and `⦃` is in `DL_TERM_BAD_RE`, so those can't be misread as terms) emits `⦃DL⦄` / `⦃DL:loose⦄` … `⦃DT⦄` … `⦃DD⦄` … `⦃/DL⦄` blank-line-padded sentinel paragraphs with the bodies left as ordinary Markdown. The post-pass runs **after** the footnote `<sup>` restore and the split / inline-columns / alignment passes (so a `<dl>` works inside `.split-col` / `.align-…` / `.md-vcenter`, since it operates on the open sentinel's actual `parentNode`) but **before** the code-block substitution, figure centering, and — critically — **before the `.marp-fit-body` wrapper**, which runs last and sweeps every body child (otherwise the raw sentinel `<p>`s get wrapped and the `<dl>` lands outside the autofit region). A scan can't cross a slide break because `---` / `***` / `___` fail the term guard.
  - **CSS** — baseline `#preview dl / dt / dd` rules in the inline `<style>`, themeable via `--md-dl-accent` / `--md-dl-term-color` / `--md-dl-desc-color` / `--md-dl-indent` / `--md-dl-pad` / `--md-dl-gap` / `--md-dl-term-weight` / `--md-dl-term-style` (the `--md-message-*` convention). Indent and accent rule use **logical properties** (`margin-inline-start` / `border-inline-start`) so they land on the correct edge under `tategaki.css`'s `vertical-rl`. Two marp-core leaks are deliberately neutralized by the baseline (its bundled GitHub-markdown CSS ships `dl dt { font-style: italic }` and `dd { margin-left: 0; padding: 0 16px }`), so the same document looks identical in both pipelines. The dark default is declared as `body.dark-mode { --md-dl-accent: … }` — **on `body`, not `body.dark-mode #preview dl`** — so it is merely *inherited* and a theme setting the variable directly on the `<dl>` still wins (the higher-specificity form would override `classical.css`'s own dark palette). Print CSS adds `dl` to the `page-break-inside: avoid` list plus `dt { break-after: avoid-page }` so a term is never orphaned at a page bottom. **No Rust change** (`pulldown-cmark` only does heading extraction / `_toc.md`). Samples: `samples/deflist.md`, the *Definition List* section in `samples/sample.md`, and the 定義リスト slide in `samples/marp.md`.
- **Ruby / 振り仮名** (`｜猫《ねこ》` / `漢字《かんじ》` / `{吾輩|わがはい}` → `<ruby>猫<rt>ねこ</rt></ruby>`) — でんでんマークダウン-compatible ruby annotation, in both pipelines. Four forms live in **one** alternation, `RUBY_ALT_SRC` in `assets/index.html`, from which three views are constructed so they cannot drift: `RUBY_START_RE` (non-global, for marked's `start()`), `RUBY_TOKEN_RE` (`^`-anchored, for the tokenizer) and `RUBY_SCAN_RE` (global, for the Marp scan). `rubyMatchToHtml(m)` turns a match into HTML and is fed **both** a `RegExp` match array and `String.replace`'s argument list — the `[full, p1…p7, …]` layouts coincide, which is what lets one function serve both pipelines. `buildRubyHtml(base, reading)` is the single source of truth for the markup, in the same role `buildSpanStyle()` plays for the styled span, and returns `''` to mean "not a ruby — leave the source alone".
  - **Mono ruby fires only when the segment count equals the base's character count** (でんでん's rule); anything else joins the segments into one group-ruby annotation. Splitting uses `Array.from()` so a surrogate-pair base splits by character. Half-width `|` and full-width `｜` are both accepted as the reading separator.
  - **The short form's `start()` must report the offset of the kanji run, not of `《`.** marked clips the preceding text token at that index, so an offset pointing at `《` would emit the base twice — once as text, once inside the `<ruby>`. That is why the short-form alternative is written `kanji+《…》` rather than anchoring on `《`; `.exec()`'s leftmost match then lands on the base. Pinned by the `start():` cases in `tools/preview-harness/ruby-model.test.cjs`.
  - **The base is NOT recursively inline-parsed** (unlike `styledSpan`): mono ruby splits it per character, and `**bold**` inside would have no well-defined split point. Wrap the whole ruby instead — `**｜強調《きょうちょう》した語**` works.
  - **Marp** — a one-line pre-pass (`__rewriteMdLines(markdown, ln => rubyifyMdLine(ln))`) placed right **after** the styled-span pre-pass, so a styled span whose attribute value contains `|` is already collapsed and cannot be misread as a brace-form ruby. It emits raw `<ruby>`, which marp-core renders because `getMarp()` runs with `html: true` — no sentinel machinery is needed (that is only required for *block*-level constructs, where CommonMark passes HTML-block content through verbatim). 1 line in → 1 line out, so it is line-count preserving and the slide→source-line map stays exact. `rubyifyMdLine()` additionally **skips inline code spans**, which `__rewriteMdLines()` does not do: marp-core renders `` `｜漢字《かんじ》` `` as literal text, and without this a slide documenting the syntax (ours does) would show rendered ruby instead of the source. The normal pipeline gets that for free — marked runs no inline tokenizer inside a code span, and `$…$` math never reaches the extension because `extractMathInto()` masks it first.
  - **CSS** — baseline `#preview ruby` / `#preview rt` in the inline `<style>`, themeable via `--md-ruby-position` / `--md-ruby-align` / `--md-ruby-size` / `--md-ruby-color` (the `--md-message-*` convention). The `letter-spacing: normal` / `font-feature-settings: normal` resets on `rt` are load-bearing, not cosmetic: `tategaki.css` sets `letter-spacing: 0.02em` and `"palt" 1` on `#preview` and both inherit into the annotation, where they visibly wreck the kana fitting. In a vertical writing mode `ruby-position: over` resolves to the **right** of the column, which is where 縦組みのルビ belongs, so one declaration serves both axes and `tategaki.css` needs **no ruby rule at all**.
  - **`bunko.css` and the 行取り grid.** A ruby annotation reserves space *outside* the line box, so a line carrying one is taller than `--bunko-line` and the fixed 16行 page stops being 16 lines (measured: a 3-line paragraph goes 89.25px → 94.25px at the default 17px / 1.75). **`line-height` on `ruby` or `rt` does not help** — Chromium sizes the reservation from `rt`'s `font-size`; only shrinking `rt` below ~0.3em did, which is unreadable. The one thing that works is cancelling the reservation with a negative margin, so `bunko.css` declares `#preview rt { margin-block-start: -1em }` — `1em` is the annotation's own font size (`--md-ruby-size`), so the cancellation tracks the ⚙ setting automatically. The annotation then overhangs into the leading, which is how a real 文庫本 sets ruby; with a tight 行送り it sits close to the neighbouring line, so ruby-heavy prose wants 行送り ≈ 1.9–2.1 from the ⚙. **This offset is bunko-only** — a fixed grid is bunko's contract; the Default theme and `tategaki.css` let the line grow, which is the typographically correct behaviour there.
  - **Known limitations**, all shared with でんでん and all documented in `samples/ruby.md`: the brace form cannot be used in a GFM table cell (`|` is the column separator and the table tokenizer runs first — use the bar or short form, or `\|`); a `《…》` quotation right after kanji is read as a short-form ruby (write `\《`); and a soft break falling **immediately before** a `<ruby>` leaves a stray space, because `applyCjkSoftBreakJoin()` walks single text nodes and cannot join across an element boundary — exactly the pre-existing behaviour of `<strong>` / `<code>` / a styled span, verified side by side, so it is not ruby-specific and was left alone.
  - **No Rust change**, and **no export pass**: `<ruby>` is inert DOM that `buildExportArtifact()`'s `cloneNode` carries verbatim, and its CSS lives in the document's first `<style>`, which the artifact inlines wholesale. - **Selection marker (highlighter behind text, auto-fade) — Marp only** — in **Marp mode** (`body.marp`), selecting text in a slide paints a translucent **highlighter band behind the glyphs** (so the text stays crisp on top and the band reads on any background, incl. dark slides) instead of the browser's blue selection, and the band **auto-fades after ~2s**. In **normal (non-Marp) previews the feature is off** — the native blue selection is kept (both the suppression CSS, scoped to `body.marker-supported.marp`, and `drawMarker()` bail out when `body.marp` is absent). Implemented purely webview-side in `assets/index.html` (no Rust changes) on the **CSS Custom Highlight API**: a single module-level `Highlight` (`__markerHighlight`, registered once via `CSS.highlights.set('marker', …)`) holds a *clone* of the live selection range, and the browser paints `::highlight(marker)` as the text background — so the band tracks the selection **smoothly as you drag** and stays aligned under the Marp deck-mode zoom/pan **automatically** (range-based; no manual coordinates / no overlay / no per-rect math, unlike the earlier `getClientRects()` band approach). The selection **range is kept while the marker is visible** — so `Ctrl+C` copies during that ~2s window — and is **auto-cleared together with the marker** when it fades (the `clearMarker(dropSelection)` fade-completion path calls `removeAllRanges()`, guarded to a still-in-`#preview` selection so it never wipes a selection the user has since made elsewhere). The native selection color is suppressed only inside `#preview` **and only when the API is available** (`body.marker-supported #preview ::selection { background: transparent }`, the class added at init after feature-detecting `Highlight`/`CSS.highlights`), so unsupported engines keep their normal selection. **Color**: `::highlight()` pseudos don't inherit custom properties in Chromium, so `var()` won't resolve there — instead `__resolveMarkerRGB()` reads the `--marker-color` custom property (from the element containing the selection first, then `:root`; default highlighter yellow `#ffd60a`) via a throwaway probe to normalize any CSS color to `[r,g,b]`, and `__setMarkerFill(alpha)` writes the literal `::highlight(marker){background-color:rgba(r,g,b,alpha)}` rule into a dedicated `<style id="marker-style">`. A Marp theme or user style can rebrand it by setting `--marker-color` on `section` / `#preview`, exactly like `--laser-color` brands the laser pointer. `drawMarker()` (wired to `selectionchange`) re-adds the cloned range on every change (single range, no stacking) and clears on a collapsed / out-of-`#preview` selection. `armMarkerFade()` waits the ~2s visible period (`__MARKER_LIFE_MS`) then animates the fill alpha `0.55→0` over `__MARKER_FADE_MS` via `requestAnimationFrame`, with a **guaranteed-clear `setTimeout` safety** (`__markerFadeSafety`) so the marker still vanishes if rAF is throttled (window occluded mid-fade). The fade is armed based on mouse-button state (`__markerMouseDown`): the marker stays solid (and grows) during a drag-select and (re)arms on `mouseup`; keyboard / programmatic changes happen with the button up so they arm directly in `drawMarker()` (each change restarts the countdown). No `resize` handling is needed — the range-based highlight re-paints natively on layout changes.

## Companion Editor Window

Opened by pressing `E` in the preview. Paired editor window (`assets/editor.html`) loading CodeMirror 6 bundled at `assets/libs/editor/editor.iife.js`.

### Spawning & pairing

1:1 paired with the preview window via `EditorRegistry` in `src/editor_registry.rs` — no broadcast, no WebSocket, so multiple preview/editor pairs cannot cross-talk. `spawn_editor_window` is called once on the first `E` keypress; the editor window registers `editor:save:` / `editor:cursor:` / `editor:change:` / `editor:close:` / `editor:listdir:` IPC handlers that dispatch `CustomEvent`s back to the main event loop. Strict path filter on `editor:cursor:` and `push_jump_to_editor` so messages can only flow between the matched pair. The editor follows the preview: switching files in the preview reloads the editor (with a confirm dialog if the buffer is dirty). `editor.css` is excluded from the preview's `M`-key style cycle by name.

**Cursor lands where the preview is looking** — the `E` keypress carries the source line currently shown at the top of the preview viewport: `window.currentPreviewLine()` (the inverse of `applyEditorScroll`, in `assets/index.html`) returns the `data-line` of the block ~25% in from the viewport's reading-start edge (the top, or the **right** edge under a vertical-writing theme — see *Live preview channel* below) — or, in Marp deck/list mode, the boundary line of the active slide (`__marpDeckIndex`); Marp scroll mode falls through to the generic nearest-block scan over the slide SVGs' `data-line`. The preview posts `openeditor:<line>`; `CustomEvent::OpenEditorWindow { line }` carries it to `spawn_editor_window(..., initial_line)`, which injects it into the `__initialFile` payload (`{path, content, line}`). The editor (`tools/build-editor/entry.js`) calls `window.__previewScrolledTo(line)` on next frame after the initial `loadFile`, reusing the same cursor-jump path as a preview click. When `E` is pressed while the editor is **already open**, the handler additionally calls `push_jump_to_editor(&path, line)` so the open editor re-syncs its cursor instead of only focusing.

### Save channel (`editor:save:`)

`Ctrl+S` (or Vim `:w` / `:wq`) saves. Rust's `editor:save:` handler writes to disk, adds the path to `suppressed_saves` for 1.5s so the `notify` watcher doesn't loop, and pushes the saved content back to the preview in-memory (`CustomEvent::EditorSavedContent`) for flicker-free re-render. The editor's `dirty` flag flips back to `false` on save (and on file-switch via `push_file_to_editor`).

### Live preview channel (`editor:change:`)

Every `docChanged` update fires a debounced (~150 ms) `editor:change:` IPC carrying `{path, content, line}`. Rust routes it as `CustomEvent::EditorLiveContent`, which re-renders the preview from memory (no disk write, no `suppressed_saves`, no title change) and immediately calls `window.applyEditorScroll(line)` so the DOM rebuild stays anchored on the cursor. `dirty` / `savedDoc` are untouched by the live channel, so the title-bar dirty-dot and the file-switch dirty-confirm dialog still gate on actual saves. `doSave()` cancels any pending live debounce so a save is the canonical post-save render. `applyEditorScroll` in `assets/index.html` lands the cursor's `[data-line]` block ~1/4 in from the reading-start edge of the preview viewport so the reader keeps upstream context before the active line.

**Both directions are axis-aware, and the axis is measured rather than inferred.** `applyEditorScroll` and its inverse `currentPreviewLine` branch on `__previewScrollsHorizontally()` — the same helper `capturePreviewAnchor` / `restorePreviewAnchor` use — because under a vertical-writing theme (`tategaki.css`, `bunko.css`) the preview runs leftward: the reader's "top of the viewport" is the container's **right** edge, the scroll axis is `scrollLeft`, and `scrollTop` never moves. Written against `rect.top` / `scrollTop` / `clientHeight` alone, editor→preview scrolling was a **silent no-op** under those themes and the `E`-key reverse jump always reported the same stale line. Two details:
- **The horizontal branch adjusts `scrollLeft` relatively** (`scrollLeft += (targetRect.right - containerRect.right) + margin`), exactly as `restorePreviewAnchor` does, rather than computing an absolute target. WebView2 leaves `scrollLeft` unnormalized for a right-to-left flow (0 is the visual *left*, i.e. the **end** of the content), so an absolute value would need a sign assumption; solving for the delta needs none and the engine clamps it. The relation it solves is `newRight = oldRight - delta`, which also fixes the sign of the **sub-block interpolation**: advancing into a block means moving *leftward*, so the `frac * width` term is **subtracted** (`delta = (targetRect.right - frac*width) - containerRect.right + margin`). Adding it instead is not a small offset error — it makes every cursor step onto a line between two stamped blocks (typically the blank line between paragraphs) scroll **backward**, with the next real line snapping forward again, so the preview visibly oscillates as the cursor is stepped line by line.
- **`currentPreviewLine`'s scan needs a 1px tolerance** (`dist <= threshold + 1`). `applyEditorScroll` lands the block's start edge at *exactly* `threshold`, but the engine snaps the resulting scroll offset to device pixels, so it settles a fraction past it (measured: 290.5 against a 290 threshold) — an exact comparison then breaks the scan at the very block just scrolled to and reports the one **before** it. This was wrong on the vertical axis too, i.e. the open→edit→reopen round-trip the function exists to keep stable was off by one block on both axes. Regression net: `tools/preview-harness/synccheck.py`.

The live channel can be disabled via the **ライブプレビュー** toggle in the settings modal (persisted in `localStorage.editor:livePreview`, default ON) — useful for large documents where mermaid / KaTeX re-renders on every keystroke are too costly. When OFF, `schedulePushLive()` is a no-op and any pending debounce is cancelled, so the preview only refreshes on explicit save (`Ctrl+S` / `:w` / `:wq`). Flipping back to ON immediately flushes the current buffer once via `pushLiveNow()` so the preview re-syncs without waiting for the next edit.

### Dirty close handling

When the editor window is closed while the buffer is dirty (Vim `:q!`, the window X button, etc.), the preview reverts to the on-disk version. Rust tracks a `dirty: bool` on the editor registry state — flipped to `true` in the `editor:change:` IPC branch and back to `false` on save / file-switch. Both close paths (`EditorCloseRequested` for Vim `:q`, `WindowEvent::CloseRequested` for the X button) call `EditorRegistry::close_take_dirty_path()`, which `take()`s the state and returns the paired path only when dirty; the main loop then calls `load_and_render` to re-render the preview from disk. Clean closes return `None` and skip the re-render to avoid flicker.

The editor JS also pushes every dirty-flag transition over the `editor:dirty:<true|false>` IPC; the Rust handler calls `window().set_title("• <name> — Editor")` (or without the bullet when clean) so the OS window title bar and taskbar entry advertise the unsaved state — the auto-hiding status bar would otherwise be the only indicator while the cursor is in the editing area.

### Vim & default keybindings

The Vim extension (`@replit/codemirror-vim`) is swapped in/out of a CodeMirror `Compartment` by the settings modal's Vim toggle (default **OFF** — pure CodeMirror 6 keybindings). When ON, NORMAL mode begins immediately and the `:w` / `:wq` / `:q` / `]]` / `[[` / `za` / `zA` / `gs*` / `gt*` mappings activate. **`C` is deliberately never bound** — it is Vim's change-to-EOL operator (see the comment next to the char-count modal in `entry.js`).

**Tab / Shift+Tab** インデント／アンインデントは `@codemirror/commands` の `indentWithTab` を `mathInputAssistKeymap()` の直後（`searchKeymap`/`defaultKeymap` より前）に挿入することで実現している。これにより数式コンテキスト（`$`+Tab / `\begin{}`+Tab 等）は引き続き YaTeX 風展開が先勝ちし、未マッチ時のみ通常インデントへフォールスルーする。これが無いと WebView2 が未捕捉 Tab をフォーカス遷移として扱い、ステータスバーのトグル等へフォーカスが飛んでしまう。

**数字付きリスト対応インデント** — `mathInputAssistKeymap()` と `indentWithTab` の間に `numberedListIndentKeymap()`（`tools/build-editor/numberedListIndent.js`）を挟み込み、カーソル上方に `^(\s*)(\d+)\.\s` の数字付きリスト祖先が存在するときは Tab / Shift+Tab のインデント単位をマーカーのテキスト幅（`<digits>.` + 半角スペース、例: `1. ` → 3 / `10. ` → 4）に切り替える。CommonMark / GFM が要求する「子要素はマーカー直後のカラムに揃える」規約に合わせるためで、これが無いとデフォルト `indentUnit = 2` のせいで `1. item1` 配下に `- subitem` を書いても `marked` / `pulldown-cmark` 双方で別段落扱いになりリストがネストしない。空白のみの行頭ではマーカー幅倍数のタブストップにスナップし、行頭が `^\s*(?:[-*+]|\d+\.)\s` でカーソルがマーカー内/直後にある場合は行全体を 1 段下げてサブリスト化する（`Enter` で生成された `2. ` を即 `Tab` でデモートする典型シナリオ）。祖先が見つからない通常段落や、行頭以外の位置の `Tab` は `false` を返して `indentWithTab` にフォールスルーするので従来挙動は維持される。フェンス内 (``` / ~~~) は数字付きマーカー探索の対象外。

**日本語ワード境界対応** — `w` / `b` / `e` / `W` / `B` / `E` / `ge` / `gE` および INSERT モードの `<C-w>`、加えて `dw` / `cw` / `yw` / `daw` / `diw` / `vw` などのオペレータ保留形を、漢字 (CJK) / ひらがな / カタカナ / ASCII 単語 / 記号 の文字クラス境界で停止させる。`tools/build-editor/jpWordMotion.js` が upstream `@replit/codemirror-vim` の `findWord` / `moveToWord` を移植して `Vim.defineMotion('moveByWords', ...)` で丸ごと差し替える形で実装。`W` / `B` / `E` の big word は ASCII 単語と ASCII 記号を 1 クラスに潰しつつ日本語 3 クラスは独立、というハイブリッド。長音符 `ー` (U+30FC) はカタカナ固定（`ラーメン` は 1 単語）。Vim OFF 時の CodeMirror 標準 word motion には影響しない。

**OS-clipboard yank/paste (`unnamedplus`)** — plain `y` / `d` / `c` / `x` mirror their text to the **OS clipboard**, and `p` / `P` paste from it, so copy/paste works across editor windows and with other applications (each editor window is a separate WebView2 with its own in-process register, and the OS clipboard is the shared medium — no editor↔editor channel). Implemented in `tools/build-editor/clipboardSync.js` (`installClipboardSync({Vim, ipcSend})`, called once next to `installJpWordMotion`). Three parts: (1) since the editor runs on the insecure `app://` scheme where `navigator.clipboard` is unavailable (and `execCommand('paste')` is disabled), it **replaces `navigator.clipboard.writeText`/`readText`** with IPC-backed shims — `writeText` posts `editor:clipboard:set:<text>` (raw text, not JSON), `readText` posts `editor:clipboard:get:<id>` and resolves when Rust calls back `window.__clipboardResult(id, text)` (mirrors the `editor:listdir:`→`__listDirResult` round-trip; this also makes the package's own `"+y`/`"+p` reliable). (2) Copy side: it wraps the shared register controller's `pushText` (`Vim.getRegisterController()`) so that on any **default-register** push (`!registerName`) it sends the unnamed register's text to the OS clipboard. (3) Paste side: on **window `focus`** (and once at boot) it pulls the OS clipboard *into* the unnamed register (charwise) so `p`/`P` paste external/cross-editor text via the package's normal synchronous paste path — guarded by `__lastLocalClip` so it never clobbers a locally-yanked **linewise** register (`yy`→`p` stays linewise; external text is inherently charwise, which is correct). The Rust side (`src/clipboard_win.rs`, `clipboard-win` crate) does the Win32 clipboard work; the `editor:clipboard:set:` handler runs on a worker thread so a transiently locked clipboard never blocks the IPC thread (see `src/editor_registry.rs`).

### Math input assist (YaTeX 風)

- `$`+Tab → `$|$`
- `$$`+Tab → fenced display block
- `\begin{env}`+Tab → matching `\end{env}`
- in-math command stubs: `\frac` / `\sqrt` / `\sum` / …
- `a.` / `b.` / `g.` → `\alpha` / `\beta` / `\gamma` greek shortcuts inside inline math
- **`\left<delim>` 自動ペア挿入** — 数式コンテキスト内で `\left` の直後に区切り文字 (`(` `[` `\{` `\|` `|` `<` `/` `.` `\langle` `\lfloor` `\lceil` `\lgroup` `\lmoustache` `\backslash`) を入力すると、即座に対応する `\right<closer>` がカーソル後ろに自動挿入される（例: `\left(` → `\left(|\right)`、`\left\langle` → `\left\langle|\right\rangle`、`\left.` → `\left.|\right.`）。カーソルは開き直後にとどまる。Tab は不要。`mathInputAssist.js` の `leftRightAutoPair()`（`EditorState.transactionFilter`）で実装。コードフェンスや通常文中では発火しない（`isInsideMath` で判定）。発火条件は 3 段構えで、いずれも**実挙動の不具合を受けて**入っている:
  - **「実際に挿入したか」ガード** — `isUserEvent('input.type')` に加えて、そのトランザクションが**カーソル位置で終わる単一の純粋な挿入**であること（`tr.changes.iterChanges` で削除・置換・複数変更を除外）を要求する。「カーソル直前がたまたま `\left(` で終わっている」だけでは発火しない。`@replit/codemirror-vim` は**削除を含む全ての Vim 編集**をアダプタ経由で `userEvent: "input.type.compose"` として dispatch する（`dist/index.js` の `dispatchChange()` / `replaceRange()`）ため、このガードが無いと Vim で自動挿入された `\right)` を `d$` / `7x` / `df)` などで消した瞬間にカーソルが `\left(` 直後に来て再挿入され、**永久に消せなくなる**。Vim の INSERT モードの通常タイプはアダプタを通らず（マッチしないキーは CM6 のネイティブ入力経路へフォールスルー）純粋な `input.type` 挿入になるので、自動ペアは従来どおり働く。IME 変換確定（`input.type.compose` かつ純粋な挿入）も従来どおり発火する。副作用として貼り付け (`input.paste`) と補完確定 (`input.complete`) では発火しなくなった（意図的）。
  - **前方の未対応 `\right` 検出** — カーソル以降を囲っている数式領域の終端（`$$` / 未エスケープ `$` / `\end{` まで、上限 4000 文字）までスキャンし、`\left` と対応の取れていない `\right` が既にあれば挿入しない（`hasUnmatchedRightAhead()`）。既存の `\left(x + y\right)` の開き側を打ち直したときの二重挿入を防ぐ。旧実装はカーソル直後 8 文字しか見ていなかったため、`\right` が離れていると重複した。トークン判定の否定先読み `(?![a-zA-Z])` により `\rightarrow` / `\leftarrow` は数えない。
  - **Backspace でペアごと削除** — カーソルが対応する `\left<open>` と `\right<closer>` のちょうど間にあるとき、Backspace 1 回で両トークンを削除する（`leftRightBackspace()`、`closeBrackets` の `deleteBracketPair` 相当）。それ以外は `false` を返して通常の Backspace にフォールスルーする。`mathInputAssistKeymap()` は `entry.js` で `defaultKeymap` より前に展開されているのでフォールスルーが効き、Vim 有効時も `keys.Backspace` → `runScopeHandlers(..., 'editor')` 経由で到達する。

### Marp slide helpers

`tools/build-editor/marpSlides.js` adds slide-unit aware editing for Marp documents (mirrors the previewer's `renderMarp()` boundary logic: front-matter `marp: true`, slides separated by `---` / `***` / `___`, separators inside fenced code blocks and the front-matter block itself ignored). `scanSlides()` returns `{fmEnd, fmLastLine, seps, docLen}` in one pass; `slideAt(state, pos, scan)` resolves the slide unit containing the cursor (the leading `---` belongs to the slide it introduces; the first slide has none; the front-matter is reported as `inFrontMatter` and protected).

- **Insert slide** — opens a small **class-picker modal** (reuses the `cc-modal` shell + `.slide-class-grid` / `.slide-class-btn` styles in `assets/editor.css`) listing `none / title / section / lead / invert / split` (split-3/4 omitted — edit the `_class` line by hand for those). Picking one calls `insertSlideAfter(view, class)`, which inserts a new slide **after the slide under the cursor** (`\n---\n\n<!-- _class: NAME -->\n\n`, or no comment line for `none`) and parks the cursor on the new empty body line.
- **Copy / Cut slide** — `copySlide(view)` / `cutSlide(view)` write the current slide (leading `---` included) to the system clipboard (`navigator.clipboard.writeText` → synchronous hidden-textarea `execCommand('copy')` fallback for WebView2's custom scheme). Cut additionally removes the slide together with **one** separator so the deck is never left with a dangling `---` (handles first / last / only-slide cases); both no-op when the cursor is in the front-matter so `marp: true` is never destroyed. Edits go through `view.dispatch`, so the existing live-preview channel reflects them — no IPC.
- **Triggers** (chosen to avoid any Vim conflict): three status-bar buttons (`+ Slide` / `⧉ Slide` / `✂ Slide`) shown **only for Marp documents** (`updateMarpButtons()` re-checks via `isMarpDocument()` on file load, debounced on edit, and once at boot); Vim ex-commands `:slide` / `:slideyank` / `:slidecut`; Vim NORMAL-mode `gs` leader `gsi` (insert) / `gsy` (yank) / `gsd` (cut) — `gs*` is unused by `@replit/codemirror-vim`'s default keymap and by the existing `]] [[ za zA`, and isn't bracket-prefixed so it can't hit the `]<char>` / `[<char>` catch-all motions; and non-Vim `Ctrl+Alt+N` / `Ctrl+Alt+C` / `Ctrl+Alt+X` (added before `defaultKeymap`).

### Markdown table helpers

`tools/build-editor/mdTable.js` adds GFM pipe-table support: insert a rows × columns template, and background-tint the cell of the cursor's column in every row of the table under the cursor. Same module split as `marpSlides.js` (pure logic + a keymap factory in the module; modal / status bar / Vim wiring in `entry.js`), and edits go through `view.dispatch` so the live-preview channel picks them up with no IPC.

**The column resolver is syntax-tree based, not hand-rolled.** Under `markdown({ base: markdownLanguage })` `@lezer/markdown` **already emits** `Table` / `TableHeader` / `TableRow` / `TableDelimiter` / `TableCell` nodes, so `resolveInner(pos)` + walking up to `Table` costs O(tree depth) with no document scan and no fence bookkeeping (a table inside a ` ```md ` fence produces no `Table` nodes at all — verified). Three parser facts the implementation depends on, all measured against the installed `@lezer/markdown` — don't "simplify" them away:

1. **Cell boundaries come from the row's `TableDelimiter` children (the pipes), NOT from `TableCell`.** An **empty cell emits no `TableCell` node**, and a freshly inserted template is all-empty cells, so a `TableCell`-based resolver would fail on exactly the tables this feature creates. Pipes are always present.
2. Because an escaped `\|` stays inside a `TableCell` and never becomes a `TableDelimiter`, the pipe-derived spans are **automatically escape-correct**. (A `|` inside a code span *does* split cells — GFM-spec behaviour, matching what `marked` renders in the preview, so it must not be "fixed".)
3. `resolveInner(pos, -1)` is tried first (so a cursor just past a cell's text lands in that cell) with a **side +1 fallback** for the boundary case where nothing lies to the left — notably offset 0 of a document that opens with a table.

**`tableColumnHighlight()` is a `ViewPlugin`, deliberately not `EditorView.decorations.compute(['doc','selection'])`**: the decorations also depend on the **syntax tree**, which CodeMirror's parser advances asynchronously, so a facet keyed only on doc+selection would not recompute when the parse catches up and the highlight would stay missing after an initial cursor jump (`window.__previewScrolledTo`) past the first parsed chunk. The plugin's `update()` therefore also tests `syntaxTree(u.startState) != syntaxTree(u.state)`. It reads state only (no viewport), so rows scrolled out of view stay marked and there is no flicker while scrolling. The **header row is tinted** (it labels the column) with its own class, the **delimiter row is not** (`---` has no content), and a cursor outside any table yields `Decoration.none`. An empty range would make `Decoration.mark` throw, so a `to > from` guard covers a hand-typed `||`.

- **Insert** — `buildTableTemplate(rows, cols, {align})` emits a column-padded template; `rows` counts the **header** row (the delimiter row is structural and never counted), clamped 1..50 × 1..20. `insertTable()` adds a blank-line trailer because a table must be terminated by a blank line or EOF — otherwise the following prose is absorbed as a one-cell row. The cursor parks in the first header cell **with no selection** (a selection would drop Vim into VISUAL right after an insert).
- **Toggle** — the highlight lives in a `tableColComp` **`Compartment`**, which is required rather than optional: gating it behind a plain flag would leave stale decorations on screen until the next edit, because the `ViewPlugin` only recomputes on doc / selection / tree change. Reconfiguring to `[]` destroys the plugin and drops its marks in the same transaction. Pref `editor:tableColHighlight` (`on` / `off`), default **on**.
- **Triggers** — the `⊞ Table` status-bar button, **always visible** (unlike the Marp trio: inserting a table is meaningful in any document). The column highlight is a *preference*, so it lives in the settings modal rather than on the bar. Vim ex-commands `:table` / `:tbl` / `:tablecol`, plus `:set tablecolumn|tcol|notablecolumn|notcol`. Vim NORMAL `gt` leader: `gti` (insert) / `gtc` (toggle). Non-Vim `Ctrl+Alt+T` / `Ctrl+Alt+H`. **`gt*` and `gm*` are both free** in `@replit/codemirror-vim` (real Vim's `gt`/`gT` tab-switching is not bound here) — `gm*` is now taken by cell mode's `gmc` (see *Jupyter 風セルモード*); never add a bracket-prefixed mapping, since `]<char>` / `[<char>` are catch-all motions.
- **`:table` argument forms** — `3 4` / `3x4` (also `X` `*` `,`) / `4` → 4×4 / an optional trailing `left|center|right` (or `l|c|r`); no args or unparseable args open the modal instead of erroring. The two size forms consume a different number of arguments, so the alignment argument's index differs — the parser handles each form explicitly rather than joining them, which is what made a naive `:table 3 4` silently mean 3×3.
- **CSS** lives in `assets/editor.css` (not the `EditorView.theme` block in `entry.js`) for three reasons, the last decisive: that theme block sits *outside* `themeComp` so a dark variant would need duplicating; all other editor chrome theming is already keyed on `body.theme-dark` there (the IME-caret rules are the precedent); and `editor.css` is loaded directly by `editor.html`, so colour tuning needs only a reload instead of an `npm run build`.
- **Tests** — `tools/build-editor/mdTable.test.mjs` runs the state layer under plain `node` (no browser, no bundle): `cd tools/build-editor && node mdTable.test.mjs`. It pins the three parser facts above plus the negative cases (in-fence, absorbed prose row, paragraph above a table).

### 貼り付けで表に変換 (Office 表 → GFM パイプ表)

`Ctrl+V` でクリップボードの表を GFM パイプ表に自動変換する (`tools/build-editor/tablePaste.js`)。プレビュー側の「Copy table」(*Preview Pipeline → Copy table for PowerPoint*) の**逆方向**で、Excel / Word / PowerPoint / ブラウザ、そしてこの previewer 自身がコピーした表を貼り戻せる。表でなければ従来どおり素のまま貼られる。

- **Rust の変更は無い。** 本物の DOM `paste` イベントの `clipboardData` は WebView2 が OS クリップボードから組み立てるので `text/html` (Win32 `CF_HTML` 由来) が既に載っている。`src/clipboard_win.rs` は `CF_UNICODETEXT` のみだが、そちらは `clipboardSync.js` の `readText`/`writeText` シムを支える別経路で、この機能は触らない。
- **`Prec.highest(EditorView.domEventHandlers({paste}))`。順序は配列位置では決まらない。** `@codemirror/view` 組み込みの `handlers.paste` は `computeHandlers()` が**全プラグインの後ろに**無条件で追加する (Prec の枠外) ので、プラグイン登録の paste ハンドラは既にその前にいる。`Prec.highest` が必要なのは `@codemirror/lang-markdown` の `pasteURLAsLink` (`markdown({base})` を無指定で呼んでいるので**有効**) に勝つため。したがって**辞退時は必ず `false` を返す**こと — 返さないと選択範囲への URL 貼り付けがリンクにならなくなり、通常の貼り付けも壊れる。`runHandlers()` は truthy 返却時に `preventDefault()` を代行するので明示呼び出しは不要。`stopImmediatePropagation()` は**呼ばない** (`@replit/codemirror-vim` が `contentDOM` に自前の paste リスナを持つ — INSERT に入るだけで `preventDefault` はしない)。
- **`event.defaultPrevented` は「自分が処理した」の判定に使えない。** 組み込みの `handlers.paste` も通常の貼り付けで `preventDefault()` するため常に true になる。`pastecheck.py` が結果ドキュメントで判定しているのはこのため。
- **YAML front matter は構文木ノードを持たない。** `@lezer/markdown` は `---\ntitle: x\n---` を `HorizontalRule` + `SetextHeading2` と解釈するので `resolveInner` では見えず、front matter ガードだけは `mdBlocks.js` の `FM_RE` で行う (他の防護 — フェンス / インラインコード / 既存の表 / HTML ブロック / リンク先 — は構文木)。`syntaxTree` ではなく **`ensureSyntaxTree`** を使う: パースは非同期に進むので、大きな文書では木が貼り付け位置に届いておらずフェンスを見落とす。
- **TSV の誤爆防止述語 (5 条件)** — (1) タブがある、(2) 途中に空行が無い、(3) **全行**が空白/タブで始まってはいない、(4) 2 列以上、(5) 厳密に矩形。(3) が `some` ではなく **`every`** なのは、先頭セルが空の Excel 範囲もその行がタブで始まるから。均一にタブインデントされたコードは矩形なので (5) では捕まらず、(3) だけが止められる。CSV (カンマ区切り) は誤爆しやすいので**対象外**。
- **HTML 側のデータ欠落ガード** — Word の選択範囲は表と周囲の文章を同時に含みうる。表だけ変換すると文章が黙って消えるので、`<table>` 外にテキストがあれば**辞退**して素の貼り付けに落とす (2 つの表を含む選択も同様)。
- **`<tr>` 断片は `<table>` で包んで再パースする。** HTML パーサは table 文脈の外の `<tr>`/`<td>` を**捨てる**ので、素直にパースするとセルのテキストだけが残り行が全部消える。
- **結合セルは展開**して複製する (GFM に rowspan/colspan は無い。空にするより情報が残る)。ヘッダは正規化後の 0 行目 (GFM がヘッダを要求するため)。セル内容はプレーンテキスト — `<br>` とブロック境界はスペースに畳み、インライン書式は**保持しない**。
- **`userEvent: 'table.paste'`** — `/^(input\.type|delete)($|\.)/` にマッチしない名前なので、変換全体がちょうど 1 回の `Ctrl+Z` で戻る。**カーソルは末尾の空行の後ろ**に置く: 表の最終文字は `Table` ノードの**内側**で、そこに置くと直後の貼り付けが自前のコンテキストガードに弾かれる。
- **逃げ道** — `Ctrl+Z` 1 回、または **`Mod-Shift-V`** (「今回は素のまま貼る」。keymap コマンドは**`false` を返して**フラグを立てるだけで、ネイティブの貼り付けをそのまま走らせる。フラグは 1500ms で失効し、**変換対象が見つかったときだけ消費する** — Chromium の `Ctrl+Shift+V` は実際に paste イベントを発火するので、先に消費すると次の貼り付けに漏れる)。恒久 OFF は `:set notablepaste` / `:set notpaste` (pref `editor:tablePaste`、既定 ON)。**ステータスバーのボタンは出さない** — バーには既に 7 個あり、ほぼ常に正しい挙動のために 8 個目は割に合わない。
- **Vim** — INSERT モードの `Ctrl+V` は DOM paste イベントを出すので変換が効く (`commandMatches` の insert コンテキストフィルタによる)。NORMAL モードの `<C-v>` は visual-block なので paste イベントは出ない。**Vim の `p` は変換しない** (意図的): `clipboardSync.js` 経由の unnamed レジスタはテキストのみで HTML を見られないうえ、レジスタを書き換えると `yy`→`p` の linewise 往復やマクロ再生が壊れる。
- **エミッタは `mdTable.js` に一本化** — `emitTable(rows, opts)` / `escapeTableCell` / `displayWidth` (CJK=2) を追加し、`buildTableTemplate()` はその薄いラッパになった。これらは `assets/index.html` の `tblDisplayWidth` / `tblEscapeCell` / `tblPadCell` / `tblEmitRow` (~7941-8069) の**ミラー実装**で、`isParagraphLine` / `__isMdParagraphLine` と同じ「同期を保て」規約に従う (index.html はモノリスで ES モジュールを import できず、そもそも別ウィンドウ)。エスケープとパディングは**別ステップ**である必要がある — `escapeTableCell` は trim するので、先にパディングするとテンプレートの空セルが潰れる。
- **Tests** — `cd tools/build-editor && node tablePaste.test.mjs` (純粋層: TSV 述語の受理/**拒否**コーパス、行列正規化、`pasteContextBlocked` — front matter のケースが「構文木だけに単純化」への回帰網)。`python tools/preview-harness/pastecheck.py` (DOM が要る半分: Excel/Word/結合セル/`<tr>` 断片の実 fixture、単一 undo、`Mod-Shift-V`、`pasteURLAsLink` の非回帰、Vim INSERT/NORMAL、そして**実クリップボード + 実 `Ctrl+V`** で `text/html` フレーバが本当に来ることの確認)。

### Jupyter 風セルモード

An opt-in second editing model in which **`---` delimits a "cell"** — the same unit `renderMarp()` turns into a slide, so **cell N is preview slide N by construction**. Applies to every `.md`, not only Marp decks. Toggle: the セルモード checkbox in the settings modal, `:cellmode` / `:set cells|nocells`, or Vim NORMAL **`gmc`** (the `gm*` leader previously held in reserve). Pref `editor:cellMode`, **default off**; when off the feature contributes *zero* extensions. Modules: `tools/build-editor/mdBlocks.js` (shared scanner) + `cells.js` (everything else). Sample: `samples/cells.md`.

- **`Prec.highest(keymap.of(…))` is NOT enough to beat Vim — the gate must be a `Prec.highest(EditorView.domEventHandlers({keydown}))`.** Verified in the installed dists: the whole `keymap` facet is served by ONE `Prec.default` DOM handler (`@codemirror/view`: `handleKeyEvents = Prec.default(EditorView.domEventHandlers({keydown}))`), so `Prec` on a `keymap.of()` only reorders bindings *inside* it; `vim()` returns an un-`Prec`-wrapped ViewPlugin array and `entry.js` lists it first, so its keydown runs earlier; and in non-insert mode Vim **swallows every single-character key** (`return !vim.insertMode && (key.length === 1 || …) ? function(){return true;} : undefined` — a truthy handler, hence `preventDefault`). A ViewPlugin at `Prec.highest` lands in the highest bucket and therefore precedes `vimPlugin`. `Esc` is the exception Vim explicitly declines in NORMAL ("Let '<Esc>' be handled normally"), but the gate handles it too so it can inspect pre-Vim state. **If `handleKeyEvents` stops being `Prec.default`, or `vim()` gains a `Prec` wrapper, Command mode silently loses every letter key to Vim** — the regression net is the "Vim ON: Esc then j moves by CELL" case in `cellcheck.py`.
- **Three layers, one per axis** — ON/OFF is a **Compartment** (`cellComp`; off ⇒ the gate is not even registered, the strongest form of "cannot affect a user who never enables it"); Edit/Command + the `dd`/`gg` pending latch is a **`StateField`** (an effect *is* a transaction, so the `entry.js:449` "flag leaves stale decorations" argument does not apply to a field; and it makes the latch testable with no `EditorView`); the Edit/Command *look* is a **body class** (`body.cellmode-command|-edit`, like `body.ime-open`), so a mode flip costs one `classList.toggle` with no transaction and no decoration rebuild. The latch has **no timeout** — the field clears it on any edit or cursor move, so a mouse click can never complete a half-typed `dd`.
- **`userEvent` must be `cell.*`.** `@codemirror/commands`' `joinableUserEvent` is `/^(input\.type|delete)($|\.)/`, so a `delete`-tagged dispatch lets two nearby ops collapse into one undo step. With `cell.*` every operation is exactly one undo step for `Mod-z` and Vim `u` alike. The same latent bug was fixed in `marpSlides.js`'s `cutSlide` (`'delete'` → `'slide.cut'`).
- **Planner / dispatcher split.** Every operation is a pure `planX(state, …) → {changes, cursor} | null` plus a 3-line dispatcher, which is the only reason `cells.test.mjs` can exist (`marpSlides.js`'s `cutSlide` mixes the two and is untestable headlessly). `planMove` **swaps the two cells' body content and re-derives each slot's padding from `slotShape()`** rather than swapping raw slot text or relocating separators — separator kinds differ (`---`/`***`/`___`), the first cell has none, and the last cell's body ends with one newline while every other ends with a blank line, so a raw swap drops the blank before a separator and turns it into a setext heading.
- **Separator hygiene (INV1–INV5).** Every separator line is preceded by a blank line; no separator is immediately followed by another; the front-matter block is never modified; the caret lands on the target cell's first body line. The three delete cases live once, in `mdBlocks.unitDeleteRange()`, shared with `cutSlide`. The asymmetric cases that break every naive implementation — insert/paste **above cell 1** and `moveCellUp` **from cell 2** — put the new separator *after* the body (the mirror of the "first unit" delete case) and have their own tests.
- **The setext rule, and why `assets/index.html` changed too.** A `---` directly after a paragraph line is a CommonMark setext `<h2>` underline, so marp-core does **not** split there. Counting it pushed a phantom entry into `renderMarp()`'s `slideStartLines`, and because the stamping is positional (`svg[i]` ↔ `slideStartLines[i]`) **every following slide's `data-line` shifted**, breaking editor↔preview sync in both directions. Cell mode makes users type `---` constantly, so this went from rare to routine. Both sides now apply the guard: `isParagraphLine()` in `mdBlocks.js` and `__isMdParagraphLine()` in `assets/index.html` — **mirror implementations, keep in sync**. `***` / `___` can never be setext underlines, so it is dash-runs-only.
- **`FM_RE` must not use `\s*` before `(\n|$)`.** `\s` matches newlines, so a greedy `\s*` swallowed the blank line *after* the closing `---` and inflated `fmEnd` by a line, disagreeing with `renderMarp()`'s front-matter end (`__curStart = i + 2`) — which let a cell inserted at the top of a deck be absorbed back into the front matter. Now `[ \t]*`. Which documents match is unchanged (group 1 is lazy and bounded by `\n---`), so `isMarpDocument()` is unaffected.
- **`FENCE_RE` tracks the marker kind.** The old `/^\s*(```|~~~)/` + `inFence = !inFence` toggle let a ` ``` ` line close a `~~~` block, misclassifying every following `---`. `makeLineScanner()` is a port of `assets/index.html`'s `__makeMdLineScanner`, which already got this right. Fence *length* and indentation are still ignored on both sides — pre-existing, and fixing one side only would create a new divergence.
- **"Run" = preview sync, with no new Rust IPC.** `Shift+Enter` runs and advances, `Ctrl+Enter` runs and stays, `Alt+Enter` runs and inserts a cell below (inserting **first**, so the preview renders the document that contains the new cell). `runCell()` cancels the 150 ms live debounce — otherwise it fires straight after with the *cursor's* line and undoes the scroll — and sends **`editor:cursor:` instead of `editor:change:` when the document is unchanged**: that skips a re-render, but more importantly the `editor:change:` handler calls `mark_dirty()` while JS pushes `editor:dirty:` only on *transitions*, so a spurious `mark_dirty()` is never corrected and `close_take_dirty_path()` would reload an unedited file from disk on close. `pushLiveNow()` has no `liveState` gate, so **`Live: OFF` + cell mode is a fully manual, run-driven preview**.
- **`cellRunLine()` sends the cell's first *body* line, i.e. `sepLine + 1`.** A slide `<svg>`'s `data-line` is its separator's line + 1, so sending the separator's own line lands **one slide early**. This is pinned twice: a unit test on the formula, and an end-to-end assertion in `cellcheck.py` that drives the real gesture and compares the line in the posted IPC against the `data-line` the preview stamped.
- **The `applyEditorScroll` stale-DOM latch.** `EditorLiveContent` emits one script — `loadFileFromRust(...)` then `applyEditorScroll(line)` — but `loadFileFromRust` is `async`, so the scroll always ran at the first microtask boundary against the *previous* render's `[data-line]` elements. Invisible while typing; wrong for `Alt+Enter`, where the new cell does not exist yet. `applyEditorScroll` now defers into `__pendingEditorScrollLine` while `__loadingFile`, and `loadFileFromRust` drains it after the render (after clearing the flag, or it would re-stash itself).
- **Visuals.** `Decoration.line` classes `cm-cell` / `-first` / `-last` / `-active` / `-fm` / `-gap`, emitted over `view.visibleRanges` only (a per-line decoration on a 5000-line document would rebuild thousands of ranges per keystroke) by a `ViewPlugin` whose predicate includes `viewportChanged` — the same shape as `tableColumnHighlight` but for a *different* reason than the comment at `mdTable.js:248` (cell boundaries are regex-based and touch no syntax tree). CSS in `assets/editor.css` has three hard rules: **never `margin` on `.cm-line`** (CodeMirror derives block height from the border box, so a margin drifts the caret cumulatively), edges via **`inset box-shadow`** not `border` (zero layout cost, and per-cell `padding-left` would skew `drawSelection`'s wide rectangles, which sample the first line's horizontal padding), and the tint via **`background-image`** not `background-color` so `highlightActiveLine()` still shows through. The Command-mode caret hiding **needs `!important`**: CodeMirror shows it from its base theme via a 5-class generated selector that outranks anything reasonable we can write. The separator line is kept visible and merely dimmed — `Decoration.replace` was rejected because CodeMirror does not keep the cursor out of a replaced range without `EditorState.atomicRanges` (which Vim's motions ignore), so `j`/`k`/`G` would land inside it with an invisible caret.
- **`onModeChange` is NOT called from the decoration plugin's constructor.** That constructor runs *during* `new EditorView(...)`, before `entry.js`'s `const view = …` is initialized, so a callback touching `view` throws a TDZ `ReferenceError` — and CodeMirror catches plugin exceptions and silently **deactivates the plugin**, which killed the decorations and the mode class for the whole session. Caught only by running it; now asserted by `cellcheck.py`.
- **Cell clipboard is both.** `c`/`y`/`x` fill an internal buffer *and* the OS clipboard; `v`/`V` read the buffer **synchronously** (Jupyter's `v` must be instantaneous, and `clipboardSync.js`'s read shim is an async IPC round trip with a 1 s timeout), falling back to one `navigator.clipboard.readText()` only when the buffer is empty — which buys cross-window cell paste.
- **Command-mode keys** — `Esc` `Enter` `i` · `j`/`k`/`↓`/`↑` · `gg`/`Home` · `G`/`End` · `a`/`b` · `dd` · `x`/`c`/`y` · `v`/`V` · `M` · `1`–`6`/`0` (heading level — the one Jupyter key with an exact Markdown analogue) · `z`/`u`/`Z`/`Ctrl+r` · `s` · `l` · `f` · `h` (help) · `m` (Marp `_class` picker, hinted rather than silent in non-Marp docs). Deliberately unbound: `y`/`r` (there are no cell *types* — every cell is Markdown; `y` is reused as a copy alias), `o` (no outputs), `p`/`ii`/`00`. `Shift+J`/`K` (multi-cell selection) is phase 2 but its state is reserved now: `planDelete` already takes a range and `cellModeField` already carries `anchorIndex`; phase 2 must render the range with its own decorations and **no editor selection**, since a selection drops Vim into VISUAL. `CELL_HELP` in `cells.js` is the single source of truth for the help modal, which must also be added to the hard-coded newest-first Esc chain in `entry.js`.
- **Navigation stays in the body.** `j`/`k`/`Home` skip the front-matter pseudo-cell (the caret can start or be clicked there, but never *selected* there), which is what stops an operation ever targeting it.
- **Tests** — `cd tools/build-editor && node cells.test.mjs` (118 assertions: scanner + setext + fence, `cellIndexAt` at every boundary, every planner incl. the asymmetric first-cell cases, a move round-trip that must be byte-identical, an invariant sweep over every op × every index, the mode field, and the `marpSlides` re-export contract). Plus `python tools/preview-harness/cellcheck.py` — a Playwright end-to-end that stands in for the Rust host and asserts the pre-Vim gate, single-step undo per op, the visuals, and cell N == slide N.

### Autocomplete

Provided by `@codemirror/autocomplete` via five custom sources in `tools/build-editor/`:

- `frontMatterComplete.js` — completes **YAML front-matter keys and values**. Fires **only** when the cursor sits inside the leading `---\n … \n---` block (line 1 is the opening `---`, cursor above the closing fence; returns `null` everywhere else so the other sources are unaffected). Two modes like `spanStyleComplete.js`: **key mode** (no `:` yet on the line) offers keys — always `marp` / `confidential` / `watermark` (free-text) / `title`, plus the Marp-only set (`theme` / `paginate` / `header` / `footer` / `size` / `class` / `_class` / `backgroundColor` / `backgroundImage` / `color` / `style` / `math`) **gated on the block already declaring `marp: true`** (same `/^\s*marp\s*:\s*true\s*$/m` matcher as `isMarpDocument`); accepting a key inserts `<key>: ` and, for enum-valued keys, re-triggers completion via `setTimeout(startCompletion)` (the `pathComplete.js` pattern). **Value mode** (after `key:`) offers per-key value menus: `marp`/`confidential` → `true`, `paginate` → `true`/`false`, `size` → `16:9`/`4:3`, `math` → `katex`/`mathjax`, `_class` → `title`/`section`/`lead`/`invert`/`split`/`split-2..4`, and `theme` → the marp-core built-ins `default`/`gaia`/`uncover` **merged with the user themes** in `window.__marpUserThemes`. That global is injected by the Rust host (`spawn_editor_window` in `src/editor_registry.rs`) — `scan_marp_theme_names()` reads each `assets/marp/*.css` file's `/* @theme <name> */` header (mirroring the webview-side extraction) and ships the names into the editor's `__initialFile` init script, so `theme:` completion matches the preview's own theme picker. Free-text keys (header/footer/title/style/color/class/watermark) yield no value menu. **Blank-field auto-open** — so the user doesn't need to know the option names, the popup opens *automatically* when the caret lands on an empty front-matter field (a key line with nothing typed, or a `key:` line whose enum value is still empty): the exported `frontMatterBlankFieldAt(state, pos)` predicate (`res.from === res.to` from the source = options found but no partial to replace) is checked in the editor's `modeListener` (`entry.js`), which calls `startCompletion(view)` (deferred via `setTimeout`) guarded by `completionStatus()` and a last-position latch (`fmLastAutoPos`) so an `Esc` that closed the popup at the same caret position doesn't immediately reopen it. A partial being typed is left to `activateOnTyping`.
- `fencedDivComplete.js` — triggers on a line beginning with `:::` (optionally followed by a partial keyword) and lists the Pandoc-style fenced-div keywords (`center` / `right` / `left` / `message` / `vcenter` / `columns` / `columns-2` / `columns-3` / `columns-4`). Accepting an option keeps the typed `:::` (inserting a separating space if the user triggered on a bare `:::`), inserts the keyword, a blank body line, and the matching closing `:::`, parking the cursor on the blank body line. **columns** variants additionally seed the implied number of `+++` column dividers (`columns`/`columns-2` → 1, `-3` → 2, `-4` → 3). Fires in **any** markdown document (not Marp-gated) — both the alignment forms and `columns` are now renderable in the normal pipeline (see *Preview Pipeline → Text alignment → Inline columns in the normal pipeline*). A **closing-context guard** (`inOpenFencedDiv()`) suppresses the popup when a *bare* `:::` is typed inside an already-open fenced-div (counting opener/closer balance above the line, skipping code fences) so pressing Enter to close a block doesn't accidentally accept a keyword; typing `:::<partial>` for a nested opener still shows the menu.
- `texEnvComplete.js` — triggers right after `\begin{` and lists KaTeX environments (`equation`, `align`, `matrix`, `cases`, …). Accepting an option inserts `name}\n  \n\end{name}` and parks the cursor on the indented body line; envs needing a column-spec (like `array` / `alignat`) land the cursor inside `{}` after the name instead.
- `katexCommandComplete.js` — triggers on `\` followed by zero-or-more ASCII letters when the cursor is inside a math context (`isInsideMath` from `mathInputAssist.js` — covers `$…$`, `$$…$$`, and `\begin{}…\end{}`). Lists ~200 KaTeX-supported commands grouped by `detail` category (greek / operator / relation / arrow / big-op / function / decoration / font / delim / spacing / env / symbol). Apply behavior: plain symbols (`\alpha`, `\to`, `\infty`) insert as-is; one-arg decorations and fonts (`\sqrt`, `\hat`, `\mathbb`, `\text`) insert `\name{}` with the cursor inside the braces; two-arg commands (`\frac`, `\binom`, `\dfrac`) insert `\name{}{}` with the cursor in the first brace; big operators (`\sum`, `\int`, `\lim`) insert `\name_{}^{}` with the cursor inside `_{}`; `\begin` / `\end` insert `\name{}` so `texEnvComplete` can pick up the env-name completion. Never fires outside math (code fences and inline code are excluded by `isInsideMath`).
- `pathComplete.js` — triggers inside the URL portion of markdown links / images (`[label](…` or `![alt](…`) and lists sibling files & folders relative to the currently-edited file's directory. Filtered to `.md` / `.markdown`, image extensions, and video extensions (`.mov`/`.mp4`/`.m4v`/`.webm`/`.ogv`/`.ogg`); when `!` is present only media (image + video) is shown. Selecting a directory appends `/` and re-queries so the user can drill down. A synthetic **`../` (親フォルダへ)** entry is offered whenever the typed prefix after the last `/` is empty (right after `(` or a `/`); accepting it inserts `../` and reopens the popup, so the user can drill **up** into parent directories — matching the preview's support for `../` file references. Backed by an editor↔Rust IPC channel: JS posts `editor:listdir:` + `{id, base, sub}`, Rust validates that `base` equals the parent directory of the paired file, then reads `base.join(sub)` and pushes results back via `window.__listDirResult(id, entries)`. **`sub` may contain `..` segments** (so completion can climb above the file's own dir); only `base` is pinned to the paired file's directory.

`completionKeymap` is registered as its own `Prec.highest(keymap.of(completionKeymap))` layer (separate from the main `keymap.of([...])`) — Tab is *not* claimed by the completion popup, so math-input-assist's Tab handler continues to win when the popup is closed; Enter accepts the highlighted suggestion. The `Prec.highest()` wrap is required so the popup's Enter (`acceptCompletion`) beats `@codemirror/lang-markdown`'s list-continuation Enter (`insertNewlineContinueMarkup`, registered at `Prec.high`) — otherwise accepting a completion *inside a list item* would insert a new bullet instead of confirming the suggestion. `acceptCompletion` and the other completion-keymap handlers return `false` when no popup is open, so normal Enter (newline / list continuation) is unaffected.

### 文字サイズ / フォント (font zoom)

`Ctrl` + `=` / `-` / `0` and **`Ctrl`+ホイール** scale the **editing text only** — the CodeMirror content and its gutters. The status bar, the modals and the Vim ex prompt are chrome and stay at their fixed sizes (VS Code's model, and the reason `.cm-panels .cm-vim-panel`'s `font-size: 16px` in `editor.css` is deliberately left alone). Size is clamped to **9–32 px**, default **15**; font family is picked from a fixed list. Both persist (`editor:fontSize` — the file's only numeric pref — and `editor:fontFamily`). Pure logic lives in `tools/build-editor/editorPrefs.js`; the modal / status bar / localStorage stay in `entry.js`, the same split as `mdTable.js`.

Four facts, each of which was verified rather than assumed and each of which a future edit can silently break:

- **CSS custom properties, NOT a Compartment.** `:root` carries `--editor-font-size` / `--editor-font-family`; `entry.js`'s `EditorView.theme` reads them via `var()` on `&` and `.cm-scroller`, and `setFontSize` / `setFontFamily` just write the variables. Font size holds no state and renders no decorations, so there is nothing to go stale — the rule `setTablePaste` already follows. A Compartment would cost a transaction and a ViewPlugin teardown per keystroke for one variable write. Corollary: **only** those two selectors reference the variables, which is exactly what confines the zoom to the editing surface.
- **`view.requestMeasure()` after every change is mandatory.** CodeMirror caches character width and line height in its `heightOracle`, and `EditorView.lineWrapping` is on, so skipping it leaves the wrap points and the caret drifting away from the rendered glyphs. `setFontFamily` needs it too — a different family means a different advance width.
- **A plain `keymap.of([...])` layer suffices even with Vim on.** `@replit/codemirror-vim` swallows a key in non-insert mode only when its name is a **single character** (`dist/index.js`: `key.length === 1 || (CM.isMac && /<A-.>/.test(key))`); `<C-=>` / `<C-->` / `<C-0>` are longer. `cells.js`'s pre-Vim gate independently returns `false` for any ctrl/meta/alt combo except `Ctrl+r`, and the document-level Esc chain bails on modifiers. So **none** of the `Prec.highest(EditorView.domEventHandlers)` machinery cell mode needed applies here. `prefscheck.py`'s "works in Vim NORMAL" case is the regression net if a dependency bump widens that condition.
- **`Mod-Shift--` must never be bound here.** `cells.js` owns it for "split cell at cursor". Zoom-out is the **shift-less `Mod--`** only — one modifier away, so this is asserted twice: `editorPrefs.test.mjs` checks the binding is absent, and `prefscheck.py` drives the real gesture and checks a cell still splits without the font changing. Zoom-in binds three aliases (`Mod-=` / `Mod-Shift-=` / `Mod-+`) because on a Japanese keyboard `=` is reached only with Shift.

`Ctrl`+ホイール is an `EditorView.domEventHandlers({wheel})` that `preventDefault`s (one notch = one step, regardless of `deltaY`). There is no WebView2 browser zoom to fight: the editor's `WebViewBuilder` has no `.with_hotkeys_zoom()`, and wry defaults `zoom_hotkeys_enabled` to `false` → `SetIsZoomControlEnabled(false)`. The `preventDefault` is only to stop the scroll.

The **cell-number gutter** (`.cm-cellNumbers .cm-gutterElement`) uses `font-size: 0.733em` (≈ the historical 11 px at 15 px) rather than a fixed px, so it tracks the text like the line numbers, which carry no `font-size` and already inherit it. Vim: `:fontsize 17` / `:fontsize +2` / `:fontsize -2` / `:fontsize` (reset).

### Status bar

Sits as an `absolute` overlay at the top of `#root` (so the editing area fills the whole window) and **auto-hides**: slides in only when the mouse enters the top 8 px hot-zone (`.status-hotzone`), when the bar itself is hovered, while a Vim ex/search panel is open (`body.vim-panel-open`, set by a `MutationObserver` watching for `.cm-vim-panel`), or while any modal is open (`body.status-pinned` — settings, char count, the Marp slide-class picker, the table size picker, the cell key list).

**The bar carries ACTIONS only; every preference lives in the settings modal.** It had grown to seven controls, which is what previously forced `editor:tablePaste` to be reachable through `:set notablepaste` alone with no UI at all. Right-aligned: **`⚙ 設定`** (opens the modal, also `:pref`), **`⊞ Table`** (insert a table — an action, visible in every document), then the three Marp-only slide buttons (`+ Slide` / `⧉ Slide` / `✂ Slide`, shown by `updateMarpButtons()`).

### Settings modal

Reuses the `.cc-modal` / `.cc-panel` shell, in three sections:

- **表示** — 文字サイズ (`−` / 値 / `+` / 戻す), フォント (select), テーマ, 行番号
- **編集** — Vim キーバインド, セルモード, 表の列ハイライト, 表の貼り付け変換
- **連携** — ライブプレビュー

**It only ever calls the existing setters** (`setVim` / `setLineNo` / `setTheme` / `setLive` / `setTableCol` / `setTablePaste` / `setCells` / `setFontSize` / `setFontFamily`), so the Vim `:set` / `gtc` / `gmc` paths keep working untouched and each pref still has exactly one owner. `updateToolbar()` became **`updateSettingsUI()`**: every setter calls it, so a pref changed from anywhere — an ex-command, a mapping, a `Ctrl+=` — is reflected the next time the modal opens.

Three things a new modal must register, and **omitting any one is a bug**: `isModalOpen()` (so cell mode's key gate stands down), the hard-coded newest-first Esc chain (the settings modal goes **first**), and `body.status-pinned` on open/close.

Two non-obvious details:

- **`refocusEditor()`.** Setters normally `view.focus()` so a click doesn't strand the caret. That is wrong while the modal is up — it would pull focus out from under the control just clicked and send the next keystroke into the document behind the backdrop — so the setters route their focus restore through a helper that no-ops while the modal is displayed. Asserted in `prefscheck.py` with a **real** `page.click()`; a programmatic `element.click()` does not move focus in Chromium and would make the assertion vacuous.
- **Each row states its shortcut / ex-command.** Before the consolidation the status-bar buttons' `title=` tooltips were the only documentation surface for `Ctrl+Alt+T` and friends, so these hints are load-bearing, not decoration.

Every color is an existing `var(--…)` token, so `body.theme-dark` is inherited with no dark-specific rules — same approach as `.table-size-form`.

All prefs persist via `localStorage` keys `editor:vim` (`on` / `off`), `editor:lineNumbers` (`absolute` / `relative` / `off`), `editor:theme` (`light` / `dark`), `editor:livePreview` (`on` / `off`), `editor:tableColHighlight` (`on` / `off`), `editor:tablePaste` (`on` / `off`), `editor:cellMode` (`on` / `off`), `editor:fontSize` (a number — validated by `clampFontSize`, not the enum-only `readPref`) and `editor:fontFamily` (a key from `FONT_FAMILIES`, so the enum validator still applies and no arbitrary CSS string can ever be stored).

### IME (Windows) integration

WebView2 exposes no JS API to read or set the OS IME open-status, so the editor uses a Rust-side bridge in `src/ime_win.rs` that wraps Win32 IMM32 (plus `SendInput` as a last-resort fallback):

- **Auto half-width on Vim NORMAL** — we subscribe to the CM5 adapter's `vim-mode-change` event via `getCM(view).on('vim-mode-change', ...)` (the global `Vim.onChangeMode` from earlier `@replit/codemirror-vim` releases does **not** exist in the bundled version — only the per-cm5 event works). On any transition out of INSERT (Esc, `<C-[>`, `:stopinsert`, visual entry, …) the editor JS posts `editor:ime:off` IPC; the Rust handler in `editor_registry.rs` then calls `ime_win::set_ime_open(hwnd, false)`. The CM5 adapter is created/destroyed by the `vimComp` Compartment, so the listener is (re)attached from `setVim(true)` and once at boot — `__vimSubAttached` dedupes.
- **`set_ime_open` strategy** — `set_ime_open` casts a wide net because Chromium's TSF backend often ignores IMM messages aimed at the tao top-level HWND:
  1. Gather candidate HWNDs: focused descendant (`GetGUIThreadInfo`) → every child of the tao window (`EnumChildWindows`) → the tao window itself.
  2. For each candidate: `ImmGetContext` + `ImmSetOpenStatus` (direct API) **and** `SendMessageW(ImmGetDefaultIMEWnd, WM_IME_CONTROL, IMC_SETOPENSTATUS)` (control-message API).
  3. Re-read open-status; if any candidate still reports the opposite state, `SendInput` a synthetic `VK_KANJI` (0x19, 半角/全角) keystroke — the only path that reliably reaches WebView2's TSF-backed IME on most setups.
  Bails immediately if no descendant of the editor's GUI thread has keyboard focus, so the SendInput fallback never yanks IME state away from another foreground app.
- **Full-width cursor tint** — alongside the editor a 200 ms polling thread reads `ImmGetOpenStatus` (with the same multi-HWND candidate sweep) and sends transitions to the main loop as `CustomEvent::EditorImeStatus(bool)`; the main loop pushes the bool to JS via `window.__setImeOpen`, which toggles `body.ime-open`. `assets/editor.css` colors `.cm-cursor` / `.cm-cursor-primary` (INSERT thin caret) and `.cm-fat-cursor` (NORMAL block caret) amber when the class is on, with brighter equivalents under `body.theme-dark`. The poller exits cleanly when `IsWindow(hwnd)` reports the editor window is destroyed; it also no-ops when the editor isn't the focused window.
- **Forensic log bridge** — the editor webview also has an `editor:log:<msg>` IPC handler that writes to `md-previewer.log`, mirroring the preview's `app://__log/…` GET channel. Useful for diagnosing future IME / Vim-mode issues without an attached debugger.

## Styles & Theming

- **`M`-key dark/light toggle** — flips `body.dark-mode` and re-initializes mermaid with the matching theme (`dark` vs `default`). Persisted in `localStorage.darkMode` (`'true'` / `'false'`). Orthogonal to the user-style selection: e.g. `parchment.css` + dark mode compose freely.
- **`S`-key style picker** — opens a modal table listing every `.css` in `assets/` (excluding `editor.css`) plus a `Default` row. Clicking a row applies it and persists the selection in `localStorage.styleName` (`Default` clears the key). User CSS files are loaded as `<link id="user-style">`; styles compose with dark mode (e.g. `tategaki.css`'s vertical layout stays put when `M` flips colors). The Rust host scans `assets/*.css` once at startup and exposes the filename list as `window.__userStyles`. Rows whose CSS declares `@user-vars` also carry a **⚙** opening that style's settings pane (see below).
- **Scroll axis is measured, not inferred** — `__previewScrollsHorizontally()` (`previewContainer.scrollWidth > clientWidth + 1`) is what `resetPreviewScrollToStart()` / `capturePreviewAnchor()` / `restorePreviewAnchor()` branch on, instead of the old `wm.startsWith('vertical-')` test. Both bundled vertical themes happen to scroll horizontally today, but the writing mode does not imply the axis (a paginated variant of bunko scrolled vertically while still being `vertical-rl`), and measuring is correct either way.
- **Page division — the `--md-page-lines` convention** (`paginatePreview()` in `assets/index.html`) — a theme divides the body into fixed-length pages by declaring `--md-page-lines: <n>` on `#preview` and styling the `.md-page-break` element the pass inserts at each boundary. The gutter's size is entirely the theme's business: the pass **re-measures after every insertion**, so it never reads it. Absent or `< 1` ⇒ complete no-op, which is every theme except `bunko.css`.
  - **It exists because CSS cannot express it.** The only CSS mechanism that fragments a text flow is multicol, and its columns are ordered along the container's inline axis — downward in any vertical writing mode, never along the direction lines advance. So a horizontally-scrolling 縦組み book has to be paginated in JS.
  - At each boundary it does what a typesetter does: break between two blocks if one starts there, otherwise **split the paragraph that straddles it**. The split point is found by bisecting each text node on the Range's block-axis position (monotonic within a block), then `Range.extractContents()` moves the head into a shallow clone — which is what makes an inline element spanning the split come out well-formed on both sides. The tail keeps the original element, **drops its `data-line`** (editor sync resolves `[data-line]` by value and the head is the block's real start) and takes `.md-page-cont` so the theme can suppress the paragraph indent on a continuation.
  - Only `<p>` is split; a heading, figure or table is moved whole, and one that is both unsplittable and taller than a page is allowed to overflow rather than spin the loop.
  - **Two ordering facts it depends on, both discovered by it silently doing nothing.** (1) It must `await __userStyleReady` — until the user stylesheet lands, `--md-page-lines` reads as empty. (2) On the *initial* load `renderMarkdown()` finishes while `#app-container` is still `display: none`, so every rect is zero and there is nothing to measure; `loadFileFromRust()` therefore calls it again right after showing the container. Splitting is **not idempotent** (a second pass would insert a second break at every boundary), so the function returns early when the DOM already contains a `.md-page-break` — that guard is what makes the double call safe, and a re-render is safe because `#preview` is rebuilt wholesale.
  - **`paginatePreview()` is two passes: `__paginateSplit()` then `__wrapPages()`.** The second groups each run of siblings between gutters into a `<div class="md-page">`, so a "page" is a real box — which is what the ノンブル hangs off and what the PDF export packs onto a sheet. The gutters stay as siblings *between* the wrappers (they are the theme's contract; `--bunko-gap` sizes them).
    - The wrapper must be **layout-neutral**, because the boundaries were computed before it existed. `position: relative` creates no BFC, so margins still collapse straight through it — the interior geometry is genuinely unchanged. What *does* change is which element `#preview > :first-child` matches: it now matches the wrapper, whose own margin is already 0, and the heading's `margin-block-start` collapses out of the wrapper and becomes the wrapper's used margin. So **all three** first-child rules need a one-level-deeper twin (`assets/index.html` ~`:170`, `assets/tategaki.css`, `assets/bunko.css`) or the first page slides along by `2 × --bunko-line`. Do **not** write a blanket `.md-page > :first-child { margin-block-start: 0 }`: pages 2..N are correct by construction because the split pass re-anchors `pageStart` *after* that margin, and zeroing it would invalidate every boundary it just computed.
    - **The geometry guard belongs to both passes.** It lives in `paginatePreview()` itself. On the initial load `renderMarkdown()` finishes while `#app-container` is still `display: none`, so the splitter declines — and the wrapper has to decline too. An earlier revision let it run there and it bundled the whole undivided document into one page box; the later call that *did* have geometry then saw a single unsplittable child and paginated nothing at all.
    - **Never stamp `data-line` on a wrapper.** `__tableLocate()`'s `lineEl.contains(tableEl)` guard would match every table in the document and refuse to edit any of them.
  - **ノンブル (page number) — the `--md-nombre-display` convention.** The base `<style>` ships `#preview .md-page::after { display: var(--md-nombre-display, none); content: counter(md-page); … }`, off unless a theme opts in — the same "theme declares, the app implements" shape as `--md-page-lines`. `top: 100%` places it just outside the page box, i.e. in `#preview`'s own bottom padding, which is the 地 of the page in a vertical-writing theme. The on/off switch **is** the `display` value because a `@user-vars` `select` writes its value through verbatim (`applyStyleVars`), so one variable is both the toggle and the value; `--md-nombre-size` / `-color` / `-opacity` tune it. `counter-reset: md-page` is declared on **`body`**, not `#preview`: `body.numbered #preview { counter-reset: num-h2 }` is more specific and `counter-reset` does not accumulate across rules, so declaring it on `#preview` would make the page numbers silently depend on whether `N`-key numbering is on.
  - A page-size change re-runs it through `__schedulePaginateRefresh()`, which re-renders (debounced) rather than trying to un-split the DOM. `__setStyleVar()` gates that call on `__styleVarAffectsLayout(spec)` — a colour or the ノンブル toggle only repaints, and a full re-render for those is pure waste. The predicate defaults to "affects layout", so a new variable is safe-but-slow rather than fast-but-stale.
- **A freshly opened document is scrolled to its reading start** — `loadFileFromRust()` now calls `resetPreviewScrollToStart()` on a fresh open (not a reload, and only when no history line / heading anchor is pending). Previously that helper was reachable **only** from a workspace file-tree click, so a `vertical-rl` document opened at the container's resting `scrollLeft: 0` — which is the visual left, i.e. the **last** page of a right-to-left text. The call is deferred behind **`__userStyleReady`** (the promise `applyUserStyle()` now records) because until the user stylesheet lands the preview is still `horizontal-tb`, and the helper would measure the wrong layout and do nothing. This was a pre-existing bug affecting `tategaki.css` too.
- **Legacy localStorage migration** — the previous single-axis `styleName` schema (`'light'` / `'dark'` / `<filename>`) is migrated on startup: `'dark'` → `darkMode='true'` + clear `styleName`, `'light'` → `darkMode='false'` + clear `styleName`, filename → kept as-is.
- **Per-style settings — the `@user-vars` convention** — a user style can declare *which of its own CSS custom properties the reader may adjust*, and the previewer builds a settings form from that declaration. The set of controls therefore differs per CSS file (`bunko.css` exposes 10, `tategaki.css` 3, the other themes none). **No Rust change** — the whole feature lives in `assets/index.html`.
  - **Declaration** — a JSON array inside a `/* @user-vars … */` comment anywhere in the CSS (by convention at the end of the file), e.g. `{ "var": "--bunko-chars", "label": "1行の文字数", "type": "number", "min": 15, "max": 60, "step": 1, "default": 39, "unit": "字" }`. Four types: **`number`** (emitted bare, so the CSS can use it as a `calc()` coefficient — this is what `bunko.css` needs), **`length`** (number + the declared CSS `unit`), **`select`** (one of the declared `options`, each `{value,label}`), **`color`**. `unit` is a real CSS unit for `length` and a display-only suffix (`字` / `行` / `倍`) for `number`.
  - **Reading it** — `__loadStyleVarSpec(name)` `fetch()`es the CSS by the same relative href the `<link>` uses (the trick `renderMarp()` already uses to read `/* @theme */` out of a Marp theme) and caches the parsed spec in `__styleVarSpecCache`. A file with no such comment yields `[]`, i.e. no ⚙ — that is also what every parse/network failure degrades to.
  - **Applying it** — `applyStyleVars()` writes one `<style id="style-vars-style">` declaring the properties on `#preview, #preview [data-marpit-svg] section` with `!important`. Same mechanism, and the same reason, as `applyWatermarkLabel()`'s `#confidential-label-style`: the property must be stamped on the very elements that resolve it, so it wins wherever the theme happened to declare it (`:root` / `body` / `#preview` / `section`). Called from **inside `applyUserStyle()`**, so startup, the S-key picker and the Marp-exit re-apply all pick it up with no call of their own; in Marp mode it clears itself alongside the user-style `<link>`.
  - **Validating it** — `__styleVarCssValue()` resolves every stored value against its declaration and falls back to the CSS file's own default for anything unproven (out of range → clamped, non-numeric → default, not a declared option → default, not a `CSS.supports('color', …)` value → default); a key absent from the spec is dropped entirely. This matters because the value is interpolated into an injected `<style>`: `__styleVarValueSafe()` is the backstop that rejects `;{}<>\` and comment delimiters. Consequently a theme can change or drop a variable without a stale localStorage entry ever producing invalid CSS.
  - **Persistence** — `localStorage['styleVars:<cssFileName>']`, one JSON object per style, so each CSS keeps its own settings independently.
  - **UI** — no new shortcut key. `__decorateStyleRowsWithGear()` adds a **⚙** button to each S-key row whose CSS declares `@user-vars` (asynchronously, since the spec comes from a fetch; the `td.gear` cell is always emitted so the column stays aligned). Clicking it **activates that style if it isn't already active** — configuring a style you cannot see is meaningless — and swaps the list for `#style-vars-pane` inside the same modal, the arrangement the help modal already uses for `#licenses-pane`. Controls live-apply on `input` and persist on `change`; since only custom properties move, **no re-render happens** — the reader's paragraph is pinned back afterwards with `restorePreviewAnchor()`. 「既定に戻す」clears the localStorage entry, 「← 一覧へ」returns to the list, and `setStyleModalOpen()` always closes the pane so `S` never reopens mid-form.
  - **Not carried into export** — `buildExportArtifact()` only snapshots the document's *first* `<style>`, so the injected `#style-vars-style` does not reach the artifact and an exported HTML/PDF renders with the theme's own defaults. Fixable the same way the watermark label was (append its text explicitly, alongside the `wmCss` handling), if it becomes a real complaint.
- **Bundled starter themes**:
  - `parchment.css` — warm cream / antique-paper theme.
  - `hakuro-modern.css` — modern sans theme built on a `--hk-*` token palette (light-only by design).
  - `tategaki.css` — Japanese vertical-writing theme (`writing-mode: vertical-rl`, mincho fonts, kinsoku 禁則 / tate-chu-yoko 縦中横 / palt 約物詰め, with `pre` / `table` / `img` / math / mermaid kept as horizontal islands; intentionally color-agnostic so it composes with both Light and Dark). Its font size / line height / letter spacing are `var(--tategaki-*, <従来値>)` and declared in a 3-entry `@user-vars` block, so they are adjustable from the ⚙ without changing the default appearance.
  - `bunko.css` — **文庫本レイアウト**. `@import url("tategaki.css")` for the vertical-writing base, then fixes the line length at **39字** and divides the body into **16行** pages separated by a real gutter. Reading is **horizontal scroll**, right→left, exactly like tategaki.
    - **The only structural change from tategaki is how the line length is decided.** tategaki uses `height: calc(100vh - 40px)`, so the characters per line depend on the window; bunko uses `height: calc(var(--bunko-chars) * 1em)`. Under `vertical-rl` the inline axis runs top→down, so `height` *is* the line length — reproducing a 文庫's 字詰め is nothing more than fixing it.
    - **The 16行 boundary is a real gutter, produced by the `--md-page-lines` pass in `assets/index.html` — not by CSS.** CSS cannot do it: the only mechanism that fragments a text flow is multicol, and its columns are ordered along the container's **inline** axis, which for any vertical writing mode runs *downward*, never along the direction lines advance. Multicol therefore yields a vertically-scrolling pagination for free but cannot produce a horizontally-scrolling one. (Verified empirically: a `horizontal-tb` + `direction: rtl` multicol *does* order columns right→left, but then the fragmentainer breaks vertically while vertical text must break horizontally, so each paragraph seizes a whole column and text stops flowing.) An intermediate revision marked the boundary with a hairline instead; it was replaced on request with the real gutter.
    - **行取り (grid alignment) is what makes the pages come out exactly 16 lines.** Any block whose block-axis extent isn't a whole number of body lines pushes the following text off the rhythm, so a page would end mid-line. Three rules enforce it, and each was needed:
      - `line-height` is set as an **absolute length** (`--bunko-line`, = 行送り × 文字サイズ) rather than a unitless multiplier, so descendants with a different `font-size` (footnotes at `0.9em`, headings) keep the same 行送り instead of recomputing it.
      - That absolute value is **re-asserted on `p` / `li` / `dt` / `dd` / `blockquote` / `h1`–`h6`**, because the baseline ships `#preview p { line-height: 1.6 }`, whose `(0,1,1)` specificity beats a declaration on `#preview`.
      - All block-axis margins are multiples of `--bunko-line` (headings 2 before + 1 after, blockquote 1, lists 0, `hr` exactly 1 counting its own 1px width).
    - **Heading size is capped at `calc(0.68 * var(--bunko-line))` via `min()`.** A line box grows to fit the font's ink box (ascent + descent, ≈ 1.29em for Japanese faces), so a heading too large for the 行送り silently inflates its own line and knocks the page off a whole number of lines. `--bunko-line-height` has a floor of **1.5** for the same reason.
    - **The 版面 is vertically centred when the window is taller than it.** Its height is a fixed function of 字数, so a tall window leaves dead space below. `#preview-container` becomes a flex container with **`align-items: safe center`** — `safe` is the load-bearing part: plain `center` overflows *upwards* when the window is shorter than the 版面, putting the top of every line out of scroll reach. `safe` falls back to start-alignment exactly in that case. `#preview` also needs **`flex: 0 0 auto`**, or the default `flex-shrink: 1` squashes a 版面 that is (always) wider than the container. The plain `center` is kept as a preceding declaration so an engine without `safe` still centres.
    - **`box-sizing: content-box` is mandatory** (index.html's global `* { box-sizing: border-box }` would let the 天地 padding eat into `height` and silently shrink the character count).
    - **`#preview p { margin: 0 }` is not cosmetic.** tategaki sets `margin: 0 0 1em 0`, a *physical* bottom margin — which under `vertical-rl` lands at the **line end**, shortening every line of the paragraph by 1em and knocking the grid off by one character. 文庫 body text has no inter-paragraph space anyway, only the 1字下げ.
    - `letter-spacing: 0` and `font-feature-settings: normal` by default, because tategaki's `0.02em` and `palt` both break the exact character grid; palt is offered as a `select` for readers who prefer the tighter look.
    - **Known limit**: images, code blocks, tables and display math have content-determined sizes that can't be rounded to whole lines, so a page containing one ends short. 文庫 layout is for prose.
    - **ノンブル** — each page carries its number, centred at the 地, by setting `--md-nombre-display: var(--bunko-nombre, block)` (default on). It sits inside `#preview`'s bottom padding (`--bunko-margin`, default 24px); at `0.62em ≈ 10.5px` it fits, but setting 天地の余白 to 0 pushes it outside the 版面.
    - **Printing** — `--md-print-pages-per-sheet: 2` asks the PDF export for a 見開き and `--md-print-gap: 4em` widens the gutter into a ノド (see *Export → PDF export → vertical-writing themes*). The page count is an upper bound, not a promise: the export measures each page and drops to one per sheet when a figure has made a page too wide. `--bunko-line` and `font-size` are both multiplied by `var(--md-print-scale, 1)`, which is what lets the export shrink the 版面 to fit a 20mm paper margin — unset on screen, so it is a no-op there.
    - Adjustable via ⚙: 字数 / 行数 / 文字サイズ / 行送り / 天地の余白 / 段落の字下げ / 書体 / 約物の詰め / ページ間の余白 / ノンブル.
    - Samples: `samples/短編小説.md` (an original short story, 23 文庫 pages over 10 sections, written to exercise this theme — long enough that each section spans 3–4 pages, so a section break is never mistaken for a page break) and `samples/縦書き長文.md`.
  - `classical.css` — 格調高い書籍風テーマ。本文セリフ (Palatino Nova → Palatino Linotype → Iwata Mincho Old → 游明朝)、見出しサンセリフ (Optima → Candara → Iwata Gothic Old → 游ゴシック)、強調語 (`strong` / `b` / `em` / `i` / `mark`) はサンセリフで「ゴチ起こし」風に。淡いアイボリー × 深ワインレッドのアクセント。`body.dark-mode` 下のダーク用パレットも CSS 変数で持つので M キーと直交合成。
- **Auto section numbering** (`N` key) — toggles `body.numbered`, persisted in `localStorage.numbered`. Baseline counter rules (CSS counters `num-h2 / num-h3 / num-h4` rendering as `1.`, `1.1`, `1.1.1` prefixes on h2/h3/h4) live in the inline `<style>` block in `assets/index.html` so numbering works on every theme by default. Themes can override the `::before` content/styling for a custom presentation. `body.numbered` is also propagated into the exported HTML artifact when active.
- **Full-width layout** (`W` key) — toggles `body.wide`, persisted in `localStorage.wide`. The baseline `#preview { max-width: 900px; margin: 0 auto }` is overridden by `body.wide #preview { max-width: none; padding: 40px 48px }` (the 48px keeps a minimal readability margin) in the inline `<style>` block in `assets/index.html`. The rule is placed *before* the `body.marp #preview { max-width: none; padding: 0 }` rule (same specificity), so in Marp mode the later marp rule wins and the toggle is a natural no-op for slides. Pure body-class toggle (no re-render), following the same pattern as `N` / line-numbers; orthogonal to dark mode and user styles. `body.wide` is also propagated into the exported HTML artifact when active.
- **Per-style HTML exporters** — any user style `assets/<base>.css` can ship a sibling `assets/<base>_export.js` ES module that exports `async function exportStyle({ currentMarkdown, currentFilePath, preview })`. At startup the Rust host probes every discovered `.css` for the matching `_export.js` and emits the resulting map as `window.__styleExporters` (same injection point as `__userStyles` / `__marpThemes` in `src/main.rs`). When `X` is pressed, `exportHtml()` looks up the active style in this map and, if present, dynamically `import()`s the module and delegates to its `exportStyle`; otherwise it falls through to the general `buildExportArtifact()` pipeline. Any import or invocation error logs a warning and also falls through, so missing / broken exporters can never block the standard export.
- **Confidential mark / arbitrary watermark** (front-matter `confidential: true` or `watermark: <text>` → `body.confidential`) — a document opts into a diagonal "透かし" overlay via its YAML front-matter (per-document; no keyboard toggle, no localStorage). Two front-matter keys drive it, resolved once at the top of `renderMarkdown()` by **`watermarkSetting(md)`** in `assets/index.html` (a sibling of `isMarpDocument()`, same leading-`---` block regex): `confidential: true` (`/^\s*confidential\s*:\s*true\s*$/im`) turns the overlay on with the theme's default label, while **`watermark: <text>`** (`/^\s*watermark\s*:\s*(.+?)\s*$/im`, one surrounding matched quote-pair stripped) turns it on with that arbitrary string as the label (e.g. `DRAFT` / `社外秘`). If both appear, the `watermark:` string wins. `watermarkSetting()` returns `null` (off) or `{ label }` (`label===null` = theme default). The class is set/cleared via `document.body.classList.toggle('confidential', !!setting)` so it never lingers when navigating away, and the custom text is applied by **`applyWatermarkLabel(label)`**, which writes (or clears, on `null`) a dedicated `<style id="confidential-label-style">` declaring `--confidential-label: "<text>" !important` on `#preview` / `#preview [data-marpit-svg] section` (same injected-`<style>` pattern as the laser `#marker-style`). The `!important` on those very elements is required because the `::before` resolves the `var()` on `#preview` (normal) / each `section` (Marp), so a per-doc override must be stamped there to beat a theme's non-important `--confidential-label` (declared on `:root` / `#preview` / `section`). **The overlay's look is otherwise defined entirely in CSS — `index.html` only manages the class + the label text.** The baseline (which doubles as the *Default* theme's definition and the overridable base) draws a diagonal watermark via `::before` `content`, whose label / color / size / angle / font / opacity come from the `--confidential-*` custom properties (`--confidential-label` default `"CONFIDENTIAL"`, `--confidential-angle` default `-30deg`, etc.). Two renderers, both `#preview`-scoped so they reach Marp slides and HTML/PDF export: (1) **normal docs** → `body.confidential:not(.marp) #preview::before` (`position: fixed`, so it stays centred while scrolling and repeats on every printed/PDF page); (2) **Marp docs** → `body.confidential.marp #preview [data-marpit-svg] section::before` (`position: absolute; inset:0` inside each slide's SVG coordinate box, so it zooms/pans/exports per-slide; `section::before` is unused by the bundled Marp themes). The mark is anchored to `#preview::before` / `section::before` (both descendants of `#preview`) rather than `body::before`, so a theme can set the `--confidential-*` variables on `:root` / `body` / `#preview` / `section` — any of them inherit down — and the override always wins (var() fallbacks carry zero specificity). Each bundled theme sets its own palette: `parchment.css` (sepia), `classical.css` (wine-red serif, dark re-point), `hakuro-modern.css` (rose sans), `tategaki.css` (relabels to vertical 「社外秘」), and the Marp `marp/magenta.css` (magenta on `section`); any theme can disable the mark with `--confidential-opacity: 0`. Export propagation: `buildExportArtifact()`'s `bodyClasses` allow-list pushes `confidential` alongside `marp` / `dark-mode` / `numbered` / `wide`, the baseline CSS ships in the artifact's inline `<style>`, and — because the injected `#confidential-label-style` is *not* the document's first `<style>` (so it isn't captured by the `baseCss` snapshot) — its text is appended explicitly to the artifact CSS, so both the mark and any custom `watermark:` label carry into standalone HTML and PDF automatically. Samples: `samples/confidential.md` (`confidential: true`) and `samples/draft.md` (`watermark: DRAFT`).

## Marp Mode

When a markdown document begins with a YAML front-matter block containing `marp: true`, the previewer switches to a slide-rendering pipeline backed by `@marp-team/marp-core` (bundled as a single IIFE at `assets/libs/marp/marp.iife.js`).

- **Themes** — slides render as 16:9 sections using Marp's built-in themes (`default` / `gaia` / `uncover`, selected via the `theme:` directive). Additional user-defined themes can be dropped into `assets/marp/*.css` (each file must begin with a `/* @theme <name> */` header) and selected by name via the same `theme:` directive — the Rust host scans `assets/marp/` at startup and exposes the file list as `window.__marpThemes`, which `renderMarp()` fetches once and registers via `marp.themeSet.add()` before rendering. A `magenta.css` (magenta accent + teal rule, inheriting `default`) is bundled as a starter.
- **Extension inheritance inside slides**:
  - `[^id]` footnotes — extracted before passing markdown to marp-core and restored as `<sup>` tags afterward. Each footnote's body is rendered **at the bottom of the slide it is referenced on** (compact style: small font + top rule, no heading / back-links), via `renderMarpSlideFootnotes()` + a post-pass in `renderMarp()` that runs *after* the figure-centering / split passes so the block lands as the section's last child and (in the flex-column slide layout) is pushed to the bottom by `margin-top:auto`. Numbering is **global / continuous** across all slides (matches the in-text `<sup>`), so a footnote referenced on multiple slides repeats its body on each with the same number. Because that means N rendered copies, the canonical `id="fn-…"` anchor target is stamped only on the **first** copy (a caller-owned `emitted` Set threaded into `renderMarpSlideFootnotes(ids, emitted)`), while **every** copy carries `data-fn-id` — the attribute the hover tooltip resolves against, so it can prefer the copy on the reader's own slide. Sections carrying footnotes get a `marp-has-footnotes` class; split slides get `grid-column: 1 / -1` on the block. Carries into HTML export automatically (the per-slide blocks live in the serialized `#preview` DOM).
  - ` ```mermaid ` and ` ```csv ` / ` ```tsv ` code blocks — post-render DOM substitution, reusing the same renderers as the regular pipeline.
  - GitHub task lists (`- [ ]` / `- [x]`) — marp-core has no task-list plugin, so a `renderMarp()` DOM post-pass (`applyTaskLists`, shared with the normal pipeline) converts the literal `[ ]` text into disabled checkboxes — see *Preview Pipeline → GitHub task lists*.
  - Definition lists (`用語` / `: 説明`) — marp-core has no deflist plugin *and* runs `breaks: true`, so a `⦃DL⦄`/`⦃DT⦄`/`⦃DD⦄`/`⦃/DL⦄` sentinel pre-pass (sharing `scanDefList()` with the normal pipeline) plus a DOM post-pass builds the `<dl>`; it must run before the `.marp-fit-body` wrapper — see *Preview Pipeline → Definition lists*.
  - Video / YouTube image-syntax embeds — `applyVideoEmbeds()` runs inside `renderMarp()` (just before `applyImageSizing()`) so `![](clip.mp4)` / `![](youtube-url)` become `<video>` / `<iframe>` in slides too.
  - `highlight.js` for syntax-coloring.
  - KaTeX math and Marp directives like `paginate` work out of the box.
- **Figure horizontal centering** — when a non-split slide contains a `.mermaid` / `.csv-table` / native `<table>` / `.abc-notation` / `.plotly-block` / `.markwhen-timeline` / `.tikzcd-diagram` / `.tikz-diagram` / `<video>` / `iframe.video-embed` / image-(or video-)only `<p>` (a paragraph whose sole meaningful child is `<img>` / `<video>` / `<iframe>`) as a **direct child** of `<section>`, a post-pass in `renderMarp()` tags each such element with the class `.marp-fig`, and CSS centers it **left-right** in normal document flow. Three centering mechanisms: (1) **inline-SVG containers** (`.mermaid` / `.markwhen-timeline` / `.abc-notation`) and image-only `<p>` via `text-align: center`; (2) **tables** (native `<table>` + `.csv-table`) via `width: fit-content; max-width: 100%; margin-left/right: auto` — the `fit-content` is essential because the general `#preview table { width: 100% }` rule (ID specificity) would otherwise force a marp table to full slide width, making `margin: auto` a no-op (no free space) so the table hugs the left; reasserting content width gives `margin: auto` room to center, and `max-width: 100%` caps a table wider than the slide. A `<table>` deliberately gets no `text-align` so its cell text isn't centered; (3) **Plotly** (`.plotly-block`) via `align-items: center` on its `body.marp .plotly-block` flex column (not `margin: auto`, which is inert on a full-width flex block) — this centers a width-fixed chart (`layout.width` < slide) while an autosizing chart is NOT shrunk (Plotly measures the full-width container and writes an explicit width onto the rendered SVG, so the now-definite-size flex item still spans the slide). The same `width: fit-content` is applied to `.md-vcenter > table` / `.csv-table`, and vcenter Plotly is centered by the shared `align-items: center`. The figure stays in document order; there is **no vertical centering and no sweeping of following siblings**. Split slides (`split` / `split-2` / `split-3` / `split-4`) are excluded. **The automatic *vertical* centering was removed** — the old version wrapped the first figure and all following siblings into a `flex:1` `.marp-figure-stage` with `justify-content:center`, but when the figure was taller than the remaining space, flexbox center-overflow spilled the figure's top over the heading/text above it (the "大きな Mermaid 図が文中にあると上下の文章と重複する" bug). Now figures flow normally and the body autofit (`A` key, *Auto-shrink*) scales an overflowing body instead of overlapping it; **`::: vcenter`** is the explicit opt-in when vertical centering is wanted (see *Preview Pipeline → Text alignment*).
- **Column layout** (`<!-- _class: split -->` / `split-2` / `split-3` / `split-4`) — break a slide into 2 / 2 / 3 / 4 equal-width columns. Authors separate columns with a `+++` line at the start of a line; a `renderMarp()` pre-pass replaces each `+++` with a `⦃COL⦄` sentinel paragraph (skipping fenced code blocks so e.g. ```diff stays intact), and a post-pass groups direct children of `section[class*="split"]` into `<div class="split-col">` buckets at every sentinel `<p>`. Leading `<h1>` / `<h2>` of the first bucket are pulled out as a full-width header row (`grid-column: 1 / -1`) so all columns start at the same y. CSS applies `display: grid` with `repeat(N, 1fr)` and per-class gap. Runs after footnote restoration (so `<sup>` refs stay in their column) and before mermaid / csv / plotly substitution (so those land inside the correct column). The figure horizontal-centering pass explicitly skips these sections.
- **Inline column region** (`::: columns` … `+++` … `:::`) — switch to multi-column **partway through** a slide and back to single-column, without making the whole slide a `split`. Uses the same Pandoc-style fenced-div family as text alignment (`::: center`): `::: columns` (or `::: columns-3` / `columns-4` to force a count) opens the region, a `+++` line divides columns inside it, and a bare `:::` closes it (returning to full-width single-column). Column count is the explicit `columns-N` if given, else the number of `+++`-delimited buckets (clamped 2..4). Because `:::` closes either an alignment or a columns block, the alignment pre-pass was generalized into a single **fenced-div pre-pass** that keeps a `fenceStack` of the open block kinds so each `:::` emits the correct close sentinel (`⦃/ALIGN⦄` vs `⦃/COLS⦄`) for the innermost block — this also lets `::: center` nest inside a column. Inside a `columns` region a lone `+++` is emitted as the same `⦃COL⦄` sentinel the split pre-pass uses (the split `+++` pre-pass stays untouched and is inert on a non-split slide, so it leaves the region's `+++` for the fenced-div pass). The post-pass (run right after the split post-pass, before the alignment post-pass) finds each `⦃COLS⦄` / `⦃COLS:N⦄` `<p>`, replaces it with a `<div class="inline-cols">` (`.inline-cols-3` / `-4` for ≥3 columns), and walks the following siblings into `<div class="split-col">` buckets (reusing the split column class + CSS) at every `⦃COL⦄`, stopping at `⦃/COLS⦄`. CSS gives `.inline-cols` a `display:grid` `repeat(N,1fr)` layout scoped under `#preview` (generalized from `body.marp #preview` so the same grid CSS serves the normal-pipeline `columnsDiv` extension below). Carries into HTML export automatically (serialized DOM + inline CSS). **Normal (non-Marp) documents now also render `::: columns`** — see *Text alignment → Inline columns in the normal pipeline* below. Sample: the "スライド途中からのカラム" slide in `samples/marp.md`.
- **Theme picker via S key** — in Marp mode, pressing `S` opens the same modal as the regular style picker but lists Marp themes instead: marp-core built-ins (`default` / `gaia` / `uncover`) plus every user theme discovered under `assets/marp/*.css` (theme name extracted from each file's mandatory `/* @theme <name> */` header). Selecting a row rewrites the front-matter `theme:` line of the *current file on disk*: `applyMarpTheme()` calls `setMarpTheme()` on **`currentMarkdownRaw`** (the canonical un-rewritten source; see *Preview Pipeline → Image serving via the `/userfile/` protocol → Raw vs. content channel* — kept as defensive practice so any future display-only source rewrite can never leak into the `.md`) to splice / replace the line (preserving LF vs CRLF), then posts `savefile:<json>` IPC to the Rust host. The new `savefile:` handler in `src/main.rs` does the same disk-write + 1.5s `suppressed_saves` dance as `editor:save:`, additionally pushing the new content to the paired editor (via `EditorRegistry::push_file_to_editor`) so its buffer doesn't drift from disk, and finally re-renders the preview via the existing `EditorSavedContent` event path.
- **Auto-shrink overflowing slides to fit — body-only scaling** (`A` key, default on, persisted in `localStorage.marpAutofit`) — marp-core renders each slide as a fixed `1280×720` logical box (`<svg viewBox><foreignObject width=1280 height=720><section>`); content taller than the slide is otherwise clipped by the `foreignObject`. The goal is to shrink an overflowing slide's **body only**, keeping the **title (H2) / header / footer at their natural size** so titles stay consistent across slides (the earlier version scaled the whole `<section>`, shrinking the title too). Two pieces:
  - **Body-wrapper post-pass** — a pass at the end of `renderMarp()` (after the figure / split / footnote passes) walks each non-`split` `<section>` and wraps its **body** content into `<div class="marp-fit-body">` (adding class `marp-has-fitbody`). Body = everything except the *fixed head* (leading `<header>`(s) + the leading heading run = the title) and the *fixed tail* (trailing `<footer>`). Any `<footer>` is first hoisted to be the section's last direct child via a `:scope footer` descendant scan (a footer left inside a scaled `.md-vcenter` wrapper would shrink — a transformed wrapper becomes the containing block for its absolute footer; footers are usually `position:absolute` so moving them in the DOM doesn't change where they paint). The `.md-vcenter` and `.marp-footnotes` blocks are swept **into** the wrapper (body content), so they scale with the body. `split` / `split-*` (grid) slides are skipped — they fall back to uniform section scaling.
  - **`fitMarpSlides()`** — for each `<section>` (all logical-coordinate measurements): resets prior inline styles on the wrapper and the section, then, **if a `.marp-fit-body` wrapper exists**, computes the height available to the body = `H − topUsed − bottomUsed`, where `topUsed` (space above the body: header + title) is `(bodyRect.top − sectionRect.top) / scale` with `scale = sectionRect.height / section.offsetHeight` (display/logical ratio, so it's correct under the svg display scaling) and `bottomUsed` = section `padding-bottom` + any in-flow (`static`/`relative`) footer height. The body's **natural** content height is measured by momentarily neutralizing the flex clamp (`flex:none; height:auto; overflow:hidden`) — the `flex:none` is required because on `::: vcenter` / footnote slides the wrapper is `flex:1 1 auto; min-height:0`, which would otherwise clamp `scrollHeight` and hide an overflowing figure inside the `flex:1` `.md-vcenter`; and the **`overflow:hidden` must not be `visible`** — it makes the wrapper a **block formatting context, exactly like the `overflow-y:auto` the fit then applies**. Under `visible` the leading child's `margin-block-start` and the trailing child's `margin-block-end` *collapse through* the wrapper's edges and are absent from `scrollHeight`, so the instant the fit is applied the BFC contains them and the content is taller than the box that measurement sized — leaving a scrollbar on a slide the fit report calls fitted. The trailing margin of a body ending in a `<p>` / `<ul>` / `<dl>` is 16px, which is exactly how much the `samples/marp.md` 定義リスト slide overshot by. **Measure in the box model you apply**: a future edit that changes the applied `overflow` must change this measurement with it. (Also note the measurement is taken at the *natural* width while the applied state widens the box to `(100/f)%`; a reflow there can only make ordinary text flow *shorter*, and anything that does grow falls back to the scroll region below.) When it overflows (`contentH > avail + 1`) only the **wrapper** is scaled + made a scroll region: `f = __marpAutofit ? max(0.5, avail / contentH) : 1` (autofit ON shrinks to the `__MARP_FIT_MIN = 0.5` floor; **autofit OFF uses `f = 1`, i.e. no shrink** — the reorder that dropped the old early `if (!__marpAutofit) return` so the wrapper path now runs regardless), `transformOrigin: top left`, `width: (100/f)%` (fills after the horizontal scale), `height: (avail/f)px` (renders at exactly `avail` after `scale(f)`; locks layout height so no extra space is reserved / an in-flow footer isn't pushed down), `overflow-y: auto` + `overflow-x: hidden`, `transform: scale(f)` (only when `f !== 1`). Because the box is `avail/f` and the content is `contentH`: autofit ON & unfloored → `avail/f === contentH` so the box holds the whole body and **no scrollbar appears** (unchanged look); autofit ON & floored at 0.5 → box `2×avail < contentH`; autofit OFF → box `avail < contentH` — the last two show a **scrollbar** so the reader reaches the rest, with the title/header/footer (outside the wrapper) staying fixed and full-size. Plain (non-Ctrl) wheel is not `preventDefault`ed outside vertical-writing mode, so the wrapper scrolls natively in deck / scroll / list modes. **Fallback** — a section with no wrapper (split / inline-cols grid slides) keeps the old uniform whole-section scaling (enlarge box to `1/f` then `scale(f)` so the rendered box snaps back to `1280×720` and the background still covers the slide; the title scales too there).
  - **CSS** — `.marp-fit-body` is `display:block` by default (so a non-overflowing normal slide preserves the theme's own vertical layout); `section.marp-has-vcenter > .marp-fit-body` and `section.marp-has-footnotes > .marp-fit-body` are `flex:1 1 auto; min-height:0; display:flex; flex-direction:column` so the nested `.md-vcenter`'s `flex:1` vertical centering still works and footnotes (`margin-top:auto`) stay pinned to the body's bottom.

  The pass is idempotent (reset → measure → re-apply). When `__marpAutofit` is off, body-wrapper slides still get the `f = 1` scroll treatment (bounded to `avail` with `overflow-y: auto`) so an overflowing body is scrollable rather than clipped; only the **fallback** whole-section (split / grid) path early-returns when off (those revert to being clipped by the `foreignObject`, since they have no fixed title/footer to scroll under). Called from `__marpUpdateDeck()` (so the slide just made `.active` in deck mode — the others are `display:none` and measure 0, so they get fitted when navigated to) and once more via `requestAnimationFrame` at the end of `renderMarp()` (after the async mermaid / abc / plotly renders so their final heights are accounted for). Orthogonal to the deck-mode `Ctrl+Wheel` zoom, which transforms the **svg** (this transforms the inner **`.marp-fit-body`** / section), so they compose; `__resetMarpZoom()` clears only the svg transform, leaving the fit intact. Carries into HTML export automatically — `buildExportArtifact()` serializes the post-pass `#preview` DOM, so the `.marp-fit-body` wrapper and its inline `transform/width/height` ride into the artifact. Sample: the 自動縮小 slide in `samples/marp.md`.
- **Three view modes** (cycled by `P`: scroll → deck → list → scroll):
  - **Scroll mode** (default) — stacks every slide vertically.
  - **Deck mode** (`body.deck-mode`) — one slide at a time, navigated by `←` / `→` / `PgUp` / `PgDn` / `Space` / `Home` / `End`, with a counter overlay in the bottom-right and `F` to toggle fullscreen. **Cursor-anchored zoom** — `Ctrl+Wheel` zooms the active slide centered on the mouse pointer (drag to pan once zoomed); implemented in `assets/index.html` as a CSS `transform: translate()+scale()` (origin `0 0`) on the active slide `<svg>`, with `__marpZoom`/`__applyMarpZoom`/`__clampMarpPan` state and a non-passive `wheel` listener that `preventDefault`s WebView2's built-in `Ctrl+Wheel` browser zoom *only* while in deck mode (so scroll/list keep the native zoom). Each wheel tick **animates** to the target scale via a `transform 0.16s ease-out` CSS transition (`__MARP_ZOOM_ANIM`, set inline on the active svg); the transition is set to `none` during drag-pan so dragging tracks the cursor with no easing lag. To keep the cursor-focal math accurate *during* an in-flight animation, the identity-state geometry (`{left,top,w,h}` at scale 1) is cached once in `__marpZoomBase` (measured via `getBoundingClientRect` on the first zoom, when the transform is still cleared) and the rendered box is then derived logically as `base + (tx,ty)` rather than re-measured — a live `getBoundingClientRect` would return the mid-transition box and corrupt the focal point / pan clamp. `tx/ty` are accumulated in screen px. Zoom auto-resets to 1:1/centered (and `__marpZoomBase` is dropped) on slide change, deck entry, re-render (all via `__marpUpdateDeck()`), on leaving deck mode (`setMarpView()`), and on window resize (cached base would otherwise go stale). **Laser pointer** — pressing `Z` in deck mode toggles a software laser pointer that follows the mouse with a glowing head dot + a short fading **comet trail** (and hides the OS cursor over the slide). Implemented in `assets/index.html` as a viewport-fixed `<canvas id="laser-canvas">` overlay (`pointer-events:none`, `z-index:9500`) driven by a `requestAnimationFrame` loop (`__laserLoop`): a `window` `mousemove` listener pushes timestamped `{x,y,t}` samples (screen `clientX/clientY`) into `__laserPoints`, the loop drops samples older than `__LASER_TRAIL_MS` (550ms) and strokes them as a width/alpha-tapering trail then a glow (`shadowBlur`) head dot with a white core. Because it tracks the physical cursor it is correct regardless of the zoom/pan transform on the active slide, and it never `preventDefault`s so `Ctrl+Wheel` zoom / drag-pan keep working underneath. The canvas backing store is sized to `devicePixelRatio` (`__resizeLaserCanvas`, also re-run on window resize). The color is **CSS-specified** via the `--laser-color` custom property: `__laserColor()` reads it from the **active slide's** `<foreignObject> section` first (so a Marp theme can brand it — e.g. the bundled `nwc-modern` / `nwc-academic` set it on `section`), falling back to the `:root` default `#ff2d2d` in `assets/index.html`. State lives in `__laserOn` / `setLaser(on)` (toggles `body.laser-on`); the laser is **deck-mode only** and auto-disabled by `setMarpView()` when leaving deck mode and by the Marp-exit cleanup in the render path.
  - **List mode** (`body.list-mode`) — every slide as a clickable 16:9 thumbnail in a responsive CSS grid; clicking a thumbnail jumps into deck mode focused on that slide.
- **Persistence** — the active mode is persisted to `localStorage.marpView` (`'scroll' | 'deck' | 'list'`); the legacy `localStorage.deckMode` boolean is read once for back-compat.
- **Slide TOC sidebar** — in non-workspace Marp mode the TOC sidebar shows a **slide table of contents** in **scroll / list** modes (hidden in **deck** mode so the slide stays immersive, via `body.marp:not(.workspace).deck-mode #toc-sidebar { display:none }`). `generateMarpTOC()` in `assets/index.html` (called at the end of `renderMarp()`) mirrors `generateTOC()` but uses each slide `<svg data-marpit-svg>` as the scroll/highlight unit (slides live inside `foreignObject`, so this avoids relying on `scrollIntoView` of inner heading elements — the same model as `applyEditorScroll`'s Marp branch). It lists every `section h1`–`h6` (level-indented like the normal TOC); each item carries `data-target=<heading id>` (export / a11y) and `data-marp-slide=<index>` (live nav). Clicking scrolls the slide `<svg>` into view (scroll mode) or jumps into the deck focused on that slide (list mode, like a thumbnail click). A scroll-spy `IntersectionObserver` over the slide `<svg>`s highlights the active slide's headings. Carries into HTML export automatically (the populated `#toc-sidebar` is serialized; the export's inline scroll-spy keys off `data-target`). Workspace Marp keeps the file tree (no slide TOC), unchanged.
- **Constraints** — in Marp mode section numbering and the `M`-key dark toggle are no-ops (Marp themes win — a toast explains). The `S` key is repurposed to the Marp theme picker described above instead of being disabled. **Editor-sync** *does* work in deck / scroll modes: marp-core's SVGs carry no `data-line`, so `renderMarp()` stamps each slide `<svg>` with the source line of its starting `---`/`***`/`___` boundary, and `applyEditorScroll(line)` advances the deck (or scrolls) to the slide whose stamped line is the largest `<= line`. The `slideStartLines` scan that produces these line numbers must run on the **original** source markdown (not the footnote-extracted / `+++`-expanded copy, which shifts line numbers) and must skip fenced code blocks (so a `---` inside ``` isn't counted as a phantom boundary) — the separators' count/order are preserved by the pre-passes, so the i-th boundary still maps to the i-th slide. List mode has no scroll target and bails. The user-style `<link id="user-style">` is also stripped from `<head>` on entering Marp mode (so generic `body` / `#preview` / heading rules from `parchment.css` / `tategaki.css` etc. don't cascade into slide `<foreignObject>` text); `localStorage.styleName` is preserved, and the link is re-injected automatically when the next non-Marp document is rendered.

## Workspace (Directory) Mode

Entered by passing a directory as the CLI arg, dropping a folder onto the window, or right-clicking a folder in Explorer (when the installer has registered the folder context-menu entry under `HKCU\Software\Classes\Directory`).

- **Workspace payload** — `build_workspace` in `src/main.rs` builds a `Workspace { root, tree, fromToc, firstFile }` payload and pushes it to the webview via `window.loadDirectoryFromRust(workspace)`.
- **`_toc.md` parsing** — if `<root>/_toc.md` exists it is parsed (via `pulldown-cmark`) as a nested markdown bullet list of `[Title](relative/path.md)` links — sub-lists become folder groups; files present on disk but absent from `_toc.md` are appended under a synthetic `Other` group. Otherwise the tree is built by recursive walk (dirs first then files, alphabetical; skips dot-prefixed names plus `node_modules` / `target` / `dist` / `build`).
- **Heading extraction** — during tree construction each file is also parsed for its heading list. `extract_headings_from_md` walks the `pulldown-cmark` event stream; the first `h1` becomes the file's `title`, every heading gets a `slug` produced by `slugify`, a Rust port of the `generateHeadingId` algorithm in `assets/index.html` — **keep the two in sync**. ⚠️ They have **already diverged for accented non-CJK headings**: Rust's `regex` treats `\w` as Unicode-aware while JS's `\w` is ASCII-only, so `# Café` slugs to `café` in Rust but `caf` in JS — an exported artifact's sidebar anchor (Rust-generated) then misses the in-page id (JS-generated). The current Rust behavior is pinned by `slugify_unicode_word_class_diverges_from_js_generate_heading_id` in `main.rs`'s tests; fixing it is a behavior change needing its own change window.
- **File-tree UI** — rendered into a `#file-tree` section that replaces the per-document `#toc-nav` in workspace mode (the legacy heading ToC is hidden by `body.workspace #toc-content { display: none }`). Each file appears as a foldable `<details>` whose `<summary>` is the document's `h1` title (filename if none), with `h2`–`h6` headings as child links indented by level. Folder groups (from `_toc.md` nesting or directory layout) wrap their members in an outer `<details>`; **nested folder depth is shown by progressive left-indentation** — `#file-tree details.ft-group > ul { padding-left: 12px }` indents each group's child container, so the indent compounds naturally through the nested `<ul>`s (the rule's `.ft-group` class beats the flat `#file-tree details ul { padding-left: 0 }` reset by specificity; file-heading sub-trees keep their own per-level padding and inherit the ancestor folders' accumulated indent). Open state is persisted per node in `localStorage.ft:<root>:<relPath>` for groups and `ft:<root>:<relPath>#` for files. Clicking a file title posts the existing `openmd:` IPC; clicking a sub-heading sets `pendingHeadingSlug` then posts `openmd:` so the post-load handler scrolls the target heading into view by id after rendering. The first file (depth-first) auto-loads on open; the active file gets `.ft-item.active` highlighting via `window.__setActiveFile`. **Right-click context menu** — `setupFileTreeContextMenu()` in `assets/index.html` wires a `contextmenu` listener on the stable `#file-tree` container (so it survives the per-render rebuild of `#file-tree-root`) offering **「すべて閉じる」/「すべて開く」** — it sets `.open = false` / `true` on every `<details>` in the tree at once (folders *and* file heading sub-trees). Because each toggle fires its `persistDetails` listener, the collapsed/expanded state is persisted to the same `ft:` localStorage keys, so it survives reload. Mirrors the math menu's popup pattern (`.ft-context-menu` / `.ft-menu-item` CSS, cursor-positioned + clamped, dismissed on outside-click / Esc / scroll); the menu only opens when the tree has collapsible nodes, so right-clicking outside workspace mode falls through to WebView2's native menu.
- **Watcher** — the `notify` watcher switches to `RecursiveMode::Recursive` for the root. Edits to the active file fire `FileChanged` → auto-reload as before, while create / rename / delete events fire `DirectoryChanged` → `build_workspace` rerun + `window.refreshFileTree`.
- **Sample workspace** at `samples/workspace/`.

## MDX Bundle Format

An `.mdx` file is a **ZIP archive** bundling a Markdown entry document together with its relative-path resources (images / CSV / video / …) into a single shippable file. Implemented in `src/mdx.rs` (`mod mdx;` in `src/main.rs`); depends on the `zip` and `tempfile` crates (added to `Cargo.toml`).

- **Extract-to-temp design** — the rest of the app is built entirely around real filesystem paths (`current_dir`, the `/userfile/` route, the `notify` watcher, editor pairing). So opening an `.mdx` simply **extracts the archive into a fresh temp directory** (`tempfile::TempDir`, auto-deleted on `Drop`) and treats the extracted entry `.md` as an ordinary single file — image/CSV/video serving via `/userfile/`, rendering, and HTML export then work unchanged with **no other code aware of the bundle**. `mdx::open_mdx()` does the extraction with a **zip-slip guard** (`ZipFile::enclosed_name()` rejects absolute / `..` paths). The entry document is chosen as root-level `index.md` → root-level `README.md` (case-insensitive) → else, if exactly one `.md` exists anywhere, that one (else error).
- **`MdxSession` state** — `Arc<Mutex<Option<mdx::MdxSession>>>` in `main()` holds `{ mdx_path, temp: TempDir, entry }`. The held `TempDir` keeps the extraction alive; it's replaced (old temp dropped/cleaned) when another `.mdx` opens, and cleared (`= None`) when a plain `.md` opens. The session maps the temp entry back to the original `.mdx` for: (1) **title** — `load_and_render_named(path, display_name, …)` (a thin wrapper added beside `load_and_render`, which now delegates with `None`) shows the `.mdx` filename instead of the extracted `index.md` while keeping the real temp `path` for `current_file` / editor pairing; (2) **watcher** — the original `.mdx` is watched (not the temp entry), so external edits to the archive fire `FileChanged(<mdx>)`; (3) **save-time repacking**.
- **Open paths** — `.mdx` is recognized via `mdx::is_mdx_ext()` in: the CLI/initial-load match (`main()`), the wry drag-drop handler (priority dir > md > **mdx** > image), and the `OpenFile` event handler (extract → store session → swap the single-file watcher to the `.mdx` → `load_and_render_named` with the `.mdx` name). Cross-file `openmd:` links to an `.mdx` route through `OpenFile` and are handled identically.
- **Edit → repack** — both save channels funnel through the `EditorSavedContent` event (editor `Ctrl+S` via `editor:save:`, and the Marp theme picker via `savefile:`), which writes the temp entry on disk. The handler then calls **`maybe_repack_mdx(saved_path, &mdx_session, &suppressed_saves)`**: if `saved_path` is the session's entry (or lives inside its temp dir), `mdx::repack_mdx()` rezips the whole temp dir back into the original `.mdx` (writes a sibling `*.mdx.tmp` then `fs::rename`s over it). The `.mdx` path is added to `suppressed_saves` for ~1.5s (same mechanism as `editor:save:` / `savefile:`) so the repack write doesn't trigger a watcher reload loop. The `EditorSavedContent` handler also overrides the title to the `.mdx` name when the save belongs to a session.
- **External change** — when the watched `.mdx` is modified externally, the `FileChanged` handler detects `is_mdx_ext`, **re-extracts** into a fresh temp dir (replacing the session) and re-renders the entry.
- **Known limits** (accepted): the companion editor window's title/`__initialFile.path` show the temp `index.md` (the preview title is overridden to the `.mdx` name); HTML-export's suggested filename derives from the temp entry.
- **Installer** — `installer/md-previewer.iss` registers a `MdPreviewer.mdx` ProgID + `.mdx` association and context menu (under the existing `assoc_md` / `ctx_file` tasks). Sample: `samples/bundle.mdx` (zip of `index.md` + an image + a CSV). Unit tests for `open_mdx` / `repack_mdx` / entry-selection live in `src/mdx.rs` (`#[cfg(test)]`).

## Export to standalone HTML / PDF (`X` key)

Opens a native Save-As dialog (via the `rfd` crate) offering **two filters — HTML and PDF** — so the output format is chosen right in the dialog by the selected extension. HTML writes a self-contained `.html` artifact suitable for hosting on any static HTTP server; PDF prints the live document (see *PDF export* below).

**Open after export (既定のプログラムで開く)** — after a successful export the generated file is automatically opened with its OS default program via the shared `open_with_default(path)` helper in `src/main.rs` (mirrors the `openinstalldir:` pattern — `std::process::Command::new("explorer").arg(path).spawn()`; `explorer <file>` uses the associated default handler, needs no UI thread / COM). It is called: (a) in the `exporthtml:` HTML branch right after `std::fs::write` succeeds; (b) in the `exportdir:` workspace branch after the root `index.html` is written (opens that `index.html`); (c) in the `PdfExportDone` handler only when `ok` (alongside the existing `__pdfExportDone` toast). A failed write / failed PDF opens nothing (existing error `eprintln!` paths are preserved).

- **Single file mode** — webview posts `exporthtml:<json>` IPC, Rust handler runs the dialog on a worker thread and writes the bytes. Artifact contains: the rendered `#preview` DOM (mermaid as inline SVG, KaTeX as pre-rendered spans, images re-inlined as base64 at export time — see *Preview Pipeline → Image serving via the `/userfile/` protocol*), the active style baked inline, and the `#toc-sidebar` with an inline script wiring up collapse-toggle, scrollspy (active TOC item highlights as the body scrolls, click-to-smooth-scroll), and Wikipedia-style footnote hover/tap popups. The artifact loads CSS for KaTeX and highlight.js from `cdn.jsdelivr.net` only when those features are actually used by the document.
- **Workspace mode** — in workspace mode `X` calls `exportWorkspace()` instead: it fetches each `.md` via the existing `app://localhost/userfile/...` route, renders it through the live pipeline, snapshots the artifact via `buildExportArtifact({pageRelPath})` (file-tree anchors are rewritten to `.html` paths relative to the page being exported), and posts `exportdir:` to Rust which `rfd::pick_folder()`s an output folder and writes one `.html` per source file (preserving directory layout) plus a root `index.html` that meta-redirects to the first page. Cross-file `.md` link rewriting carries over: links to sibling `.md` files become `.html` siblings.
- **Marp mode** — the live DOM (including marp-core's CSS injected as `<style id="marp-style">`) is serialized into the artifact.
- **Local video files** — `buildExportArtifact()` scans cloned `<video[data-video-file]>` embeds, resolves each local source to an absolute path (relative paths resolved against the source `.md`'s directory), rewrites the clone's `<source src>` to a `media/<basename>` relative path (deduped per artifact; for workspace pages prefixed with the right `../` depth), and returns a `mediaFiles: [{src, dest}]` list. `exportHtml()` forwards it as `media` in `exporthtml:`, and `exportWorkspace()` aggregates all pages' media (deduped by `dest`) into the `exportdir:` payload. The Rust handlers deserialize it into `Vec<MediaItem>` and call `copy_export_media()` to copy each file next to the output HTML (single-file) / under the chosen output folder (workspace). YouTube `<iframe>`s are skipped — their `https` URLs need no copying. Caveat: a per-style `_export.js` exporter bypasses this (it builds its own artifact), so styles that ship an exporter won't copy videos.
- **`@import` is spliced, not shipped** — the active theme is inlined by fetching its text into a `<style>`, at which point a **relative `@import` no longer resolves**: it would be looked up against the *artifact's* location. `bunko.css` is `@import url("tategaki.css")` plus overrides, so the export silently lost the entire vertical-writing base and came out **horizontal** while every bunko-owned property (字数 / 行数 / ノンブル) still looked right — which is why it went unnoticed. `__inlineCssImports(cssText, baseHref)` in `assets/index.html` now recursively splices every **same-origin** import in place (depth-capped, cycle-guarded); a cross-origin import, or one carrying a `layer()` / `supports()` condition that splicing cannot reproduce, is left as written. A media condition is preserved by wrapping the spliced text in `@media`. It does **not** rewrite relative `url()` inside the imported text — those are exactly as (un)resolvable as the importing file's own, a separate pre-existing limitation of inlining a theme at all. Regression net: `tools/preview-harness/exportcheck.py`.
- **Per-style exporter delegation** — when an active style ships an `_export.js`, `exportHtml()` dynamically `import()`s it and delegates (see *Styles & Theming → Per-style HTML exporters*).
- **PDF export** (single-file, non-workspace only) — the same `X` flow. `exportHtml()` still posts `exporthtml:<json>` (the HTML artifact is built regardless); the Rust handler's Save dialog now has both an `HTML` and a `PDF` filter. When the chosen path ends in `.pdf`, the handler **discards the HTML bytes** and posts `CustomEvent::PrintPdf(path)`. Because the print captures the **live DOM**, videos must first be rasterized to still frames (see *video frames* below): `PrintPdf(path)` **stashes the path** in a shared `pending_pdf: Arc<Mutex<Option<PathBuf>>>` and runs `window.__beforePdfPrint()` in the preview; when that finishes it posts a `pdfprintready:<json>` IPC → `CustomEvent::PrintPdfNow { page_px }`, whose handler takes the path back and calls `pdf_win::print_current_to_pdf()` which prints the **live webview** (not the artifact) to PDF via WebView2's **DevTools-Protocol `Page.printToPDF`** (`ICoreWebView2::CallDevToolsProtocolMethod`, in `src/pdf_win.rs`). The handshake is a no-op (immediate ready) for a plain document with no videos. CDP — not `ICoreWebView2_7::PrintToPdf` — is used because it accepts **`generateDocumentOutline: true`**, which builds PDF **bookmarks (しおり) from the heading structure** (this SDK's `PrintToPdf` settings expose no outline option). Internal anchor links (`href="#id"` — inline links, footnote refs/backlinks, and the sidebar TOC anchors, which already carry real `href`s) plus external links become **clickable PDF link annotations automatically**; `printBackground:true` keeps themed / code backgrounds; output is vector with selectable text, A4 portrait for an ordinary document and the slide box for a Marp deck (see *Marp: one page per slide* below). The CDP call is async: the completion handler (UI thread) receives `{"data":"<base64 PDF>"}` as a ready `String`, base64-decodes it, writes the file, and posts `CustomEvent::PdfExportDone { ok, path }` → the main loop calls `window.__afterPdfPrint()` (restore, see below) then `window.__pdfExportDone(ok, name)` (in `assets/index.html`) which toasts. **Video frames** — a printed `<video>` is a blank/black placeholder with controls, so at print time `__beforePdfPrint()` (in `assets/index.html`) swaps each `#preview video.video-embed` for a still `<img>` of a chosen frame and hides the video, awaiting `img.decode()` before posting `pdfprintready:` (in a `finally`, so it always fires); `__afterPdfPrint()` (called from the `PdfExportDone` handler) removes the imgs and unhides the videos. The frame is captured via `<canvas>.drawImage(video)` → `toDataURL('image/png')` in `__captureVideoFrame(v, time)`: if the video carries a `data-pdf-frame-time` (from the `|t=<time>` alt token) it seeks there first (awaiting `seeked`; the `/userfile/` route's `Range` support makes seeking work), else it uses the current frame; capture is best-effort (returns null for an undecodable codec → `videoWidth 0`, or a tainted canvas — the video is then left in place). **High-resolution image downscaling** — riding on the *same* swap/restore mechanism, `__beforePdfPrint()` also shrinks unnecessarily high-res `<img>`s so the printed PDF doesn't embed a 4000px photo shown at a few-hundred-px width at full resolution (Chromium's print engine embeds the live DOM's decoded bitmaps verbatim). It walks `#preview img:not(.pdf-video-frame)` and calls `__downscaleImageForPdf(img)`, which — when the natural long edge exceeds the print target by more than the slack — canvas-`drawImage`s the image at reduced size and returns a data URL: PNG/GIF sources keep `image/png` (transparency preserved), everything else re-encodes to `image/jpeg` (quality `__PDF_IMG_JPEG_QUALITY = 0.82`, over a white matte). The **target long edge** is the absolute cap `__PDF_IMG_MAX_EDGE = 1600` (≈ A4 print width at high DPI, robust for hidden/zero-size images like inactive Marp deck slides), tightened to the displayed CSS long edge × `__PDF_IMG_TARGET_SCALE = 2` when measurable; images already within `× __PDF_IMG_SLACK = 1.25` of target are left untouched (no needless re-encode). The swap stashes `{img, origSrc, origSrcset}` in `__pdfImgSwaps` (mirroring `__pdfSwaps`), clears `srcset`, sets `img.src` to the data URL, and adds the new `img.decode()` to the same 1500 ms-bounded `decodes` race that gates `pdfprintready:`; `__afterPdfPrint()` restores the original `src`/`srcset`. External cross-origin images taint the canvas → `toDataURL` throws → caught, left as-is (`/userfile/` and `data:` are same-origin `app://`, so they never taint). **PDF only** — HTML export's `buildExportArtifact()` still inlines images verbatim (no resize). Frame images affect **PDF only** — HTML export keeps the playable `<video>` (and `buildExportArtifact()` strips the `data-pdf-frame-time` attr from the clone). YouTube `<iframe>`s can't be frame-captured (cross-origin) and are unaffected. **`base64`, `webview2-com` (0.19, pinned to wry's version so the `ICoreWebView2` types match), and `windows` (0.39) are the Rust deps.** Existing `@media print` CSS governs pagination (`#toc-sidebar` stays hidden — navigation is provided by the PDF bookmarks). **Marp: one page per slide, no margins** — for a Marp document the paper *is* the slide: `__marpPrepareForPdf()` (`assets/index.html`, called at the top of `__beforePdfPrint`) reads the real slide box off the first slide's `<foreignObject>` `width`/`height` (so `size: 4:3` yields 960×720, not a hardcoded 1280×720), and the `pdfprintready:` ack carries it as `{"pageW":…,"pageH":…}` — `parse_pdf_page_size()` in `src/main.rs` turns that into the `page_px` argument of `pdf_win::print_params()`, which converts CSS px → inches (`/96`) and sets **all four margins to 0**; `{}` / anything unparseable falls back to the historical A4 + 0.4in. The size travels over **two channels that must agree**: those params, and an injected `<style id="pdf-page-style">@page { size: Wpx Hpx; margin: 0 }</style>` — `preferCSSPageSize:true` was already set, so whichever Chromium honours yields the same geometry (the CSS one avoids the px→in→px rounding entirely). The layout itself is **not** built in `@media print`: `fitMarpSlides()` measures the on-screen DOM and writes inline transforms, so a size that only existed inside the print stylesheet would leave those measurements describing a layout the printer never sees. Instead `__marpPrepareForPdf` resizes each slide `<svg>` to the true box with inline styles and re-runs `fitMarpSlides()` — the same move `__prepareCapture()` makes for `--export-png` — leaving the print CSS (`body.marp.pdf-print` rules, scoped to the class this function adds) only the app-shell padding/background reset and a **`svg + svg { break-before: page }`** (adjacent-sibling `break-before`, not `break-after` on every slide, which would emit a blank final page). Two ordering facts: the Marp prep runs **before** the image downscale loop, because `__downscaleImageForPdf` sizes each image against its *displayed* box and in list mode that box is a ~280px thumbnail; and the teardown runs **last** in `__afterPdfPrint` (after images/videos are restored), because it ends in a `fitMarpSlides()` that measures them. Any view mode works — `__marpEnterScrollLayout()` (extracted from `buildExportArtifact()`, which had the identical need and now shares it) drops `deck-mode` / `list-mode` and returns the restore closure, so a deck no longer prints as a single page and a list no longer prints as a thumbnail grid. The dark-mode print overrides that force a white page are scoped `body.dark-mode:not(.marp)`, since a slide's colours come from its own theme. **Known limit**: a slide the autofit couldn't fit even at its 0.5 floor is clipped rather than continued on a second page — `.marp-fit-body` is an `overflow-y:auto` scroll region, matching the on-screen and `--export-png` behaviour. Regression net: `tools/preview-harness/pdfcheck.py`. **Vertical-writing themes: A4 landscape, N pages per sheet** — `__verticalPrepareForPdf()` (`assets/index.html`, called from `__beforePdfPrint` when `__marpPrepareForPdf()` returned null) handles `tategaki.css` / `bunko.css` and any other theme whose `#preview` computes to a `vertical-*` writing mode.
  - **Why the obvious approach cannot work.** A `vertical-rl` `#preview` is an **orthogonal flow** inside a `horizontal-tb` page box: the page fragments downward while the text advances leftward. The printer emits one page holding the first paper-width of the column and **silently drops the rest** — measured on `samples/短編小説.md`: 1906 of 4473 characters. Forced breaks inside an orthogonal flow are not honoured either, so `break-after: page` on the gutters is a no-op. This is why the completeness assertion in `pdfcheck.py` is the load-bearing one.
  - **What does work** is making the **page box itself** vertical. The principal writing mode is taken from the root element, so an injected `@media print { html, body, #app-container, #preview-container { writing-mode: vertical-rl !important } }` turns the fragmentation axis right-to-left; the column then paginates naturally, in document order, with page 1 on the right of each spread. **No DOM restructuring at all**, so the teardown (`__pdfVerticalRestore`) is just "remove the two injected `<style>`s, the two body classes, `#preview.pdf-vertical-src` and the `.md-sheet-end` marks" — no re-render, no lost scroll anchor.
  - **Paper is A4 landscape floored to whole CSS px: `1122 × 793`, margin `76` (≈20mm).** `@page` and the paper the host derives from the `pdfprintready:` ack must describe the *same* box; a sheet a hundredth of a pixel taller than the page emits a blank page after every sheet (`src/pdf_win.rs:96` carries the same warning for the Marp slide box). **No Rust change** — `parse_pdf_page_size` already accepts any `pageW`/`pageH`, and `paperWidth > paperHeight` is what makes it landscape (the CDP `landscape` flag stays hard-coded false).
  - **The 版面 is scaled to the paper — `--md-print-scale`.** A fixed 版面 is a fixed number of CSS px (bunko: 39字 × 1em tall, 16行 × 行送り wide) and A4 landscape has barely more than that, so a generous margin — or a wider gutter — simply would not fit. But every one of those lengths derives from **one** font size, so multiplying that single value shrinks the whole 版面 uniformly **without reflowing a word**: the line stays 39 characters because the character advance shrank with it. A theme opts in by routing its own font size through `var(--md-print-scale, 1)` (see `bunko.css`'s `--bunko-line` and `font-size`); a theme that doesn't is never scaled, and the variable is unset on screen so the fallback `1` applies. `__verticalPrepareForPdf()` computes `f = min(1, innerH / 版面inline, 0.995 × innerW / nominalSpread)` floored at `__PDF_V_MIN_SCALE = 0.5`. This is also what stops a reader who set 字数 to 60 from getting a clipped PDF — the 版面 no longer has to fit the paper as authored.
  - **`--md-print-gap`** lets a theme widen the gutter on paper, where it reads as the ノド between two facing pages (`bunko.css`: `4em` vs `3em` on screen). Applied in the phase-1 style below, so the packing measures the printed gutter.
  - **Sheet packing is measured, not counted.** A first `<style id="pdf-vertical-style">` is injected **before** the measurement (an `@media print` block would not apply yet) to zero the block-start **and block-end** margins of `#preview.pdf-vertical-src > .md-page`'s first/last child, and to collapse a `.md-sheet-end` gutter to `block-size: 0` (`display: none` is not an option: it would remove the very element `break-after` is attached to). The leading margin makes a heading-led page 2 lines wider than the rest; **the trailing one is worse, because it is not inside the wrapper's border box at all** — it collapses out and pushes the gutter along, so an extent-based measurement under-counted the sheet by a line and the spread overflowed onto an extra page. For the same reason the packing measures **positions, not extents**: each page's `stop` is where the following gutter *begins*, so a sheet's width is simply `stop[last] − start[first]` and everything between is counted. Greedy, capped by the theme's `--md-print-pages-per-sheet`. Measuring is what keeps a page carrying an oversized figure from overflowing its sheet — it simply gets a sheet to itself.
  - **Line length follows the paper.** A fixed 版面 (`bunko`, `height: 字数 × 1em`) is centred on the page's inline axis via computed `padding-top/bottom`; a window-sized one (`tategaki`, `height: calc(100vh - 40px)`) is given `height: auto` so it fills the paper — which is what makes tategaki's characters per line, and hence its lines per page, follow the sheet rather than the window.
  - **`#preview-container`'s `overflow` must be killed with `!important`.** `applyUserStyle()` appends the theme's `<link>` *after* the document's inline `<style>`, so `tategaki.css` / `bunko.css` `#preview-container { overflow-x: auto }` wins on source order over the base print rule. A fragmentation break does not propagate out of a scroll container, so leaving it produces a **one-page PDF that looks exactly like the orthogonal-flow failure**. Marp escapes this only because `body.marp` suppresses the user stylesheet entirely.
  - **Ordering**: unlike the Marp prep (which must run *before* the image downscale), this runs **after** the image/video swaps, because it measures page extents and a video swapped for a still can change them. A throw inside it restores and returns null, so a half-applied layout is never printed.
  - **Known limits**: a page whose figure makes it wider than a whole sheet is clipped (same class as the existing "figures break 行取り" limit); the leftover slack on a sheet sits at the block-end (left) edge rather than being centred, since a fragmented flow cannot be centred per sheet.

**Not covered**: workspace-mode `X` (still exports an HTML folder) and styles that ship a per-style `_export.js` (those short-circuit before `exporthtml:` is posted, so PDF isn't offered). `generateDocumentOutline` needs a reasonably recent evergreen WebView2 runtime; older runtimes ignore the unknown param (degrades to no-bookmarks, never crashes) — clickable links are runtime-version-independent.

## Headless PNG capture for agents (`--export-png`)

A **non-interactive CLI mode** so an AI agent authoring Marp decks can *see* its own rendering — render → PNG → inspect layout → fix the Markdown → repeat — without any GUI interaction. Also emits a cheap, deterministic **layout report** so the agent can triage which slides are broken before ever looking at an image.

**Command**: `md-previewer.exe <file.md|.mdx> --export-png <outdir> [--slides 1,3,5-7] [--png-scale 2]`. Flags are parsed in `main()` alongside the existing single positional path (back-compatible; the first non-`--` arg is still the file/dir/mdx). `--slides` is a 1-based spec (`parse_slides_spec()` → deduped 0-based indices, out-of-range dropped; omitted = all slides; Marp only). `--png-scale` (default **2**) is the CDP `clip.scale` zoom — a Marp slide's logical 1280×720 box becomes a 2560×1440 PNG (further multiplied by the display DPR, so at 125% you get 3200×1800). Output: Marp → `slide-NN.png` (1-based, zero-padded) per selected slide; non-Marp → a single full-page `page.png`; **always** a `layout.json`.

**`layout.json`** (`{ marp, slides: [ {index, file, overflow, scale, flooredAtMin, contentH, avail} ] }`, non-Marp = `{ marp:false, slides:[] }`) — the metrics come **free** from `fitMarpSlides()` (`assets/index.html`), which already computes each slide's available body height `avail`, natural content height `contentH`, and applied autofit scale. `overflow` = body exceeded the box; `scale` < 1 = the body had to shrink; **`flooredAtMin` = even at the 0.5 shrink floor it still overflows (the definite "needs fixing" signal)**. `fitMarpSlides()` records per-slide metrics into a module-level `__marpFitReport[]` (index = slide order) on every run; `__prepareCapture()` reads the entry for the slide it's isolating.

**Flow** (mirrors the PDF-export event/CDP plumbing):
1. `main()` builds a `CaptureConfig` and creates the window **hidden** (`with_visible(false)`) — a throwaway render surface, no flash. The init script injects `window.__captureConfig = { scale }` so the preview knows it's in capture mode.
2. `renderMarkdown()` calls `__emitRenderDone(isMarp)` once the initial render (incl. async Marp/mermaid/KaTeX) settles → posts `renderdone:{marp,slides}` IPC. **Hidden windows freeze `requestAnimationFrame`** (it only fires while painting), so the capture path uses `setTimeout` (not rAF) for its settle delays — this was the key gotcha.
3. Rust `renderdone:` → `CustomEvent::CaptureStart` → resolves the slide index list, creates `CaptureState` (`Arc<Mutex<Option<…>>>`, owned by the event loop), and asks the preview to isolate the first slide via `evaluate_script("window.__prepareCapture(i)")`.
4. `__prepareCapture(index)` adds `body.capturing` (hides `#toc-sidebar` / `#slide-counter` / laser / toast), positions the target slide `<svg>` `position:fixed` at the origin sized `1280×720` (all others `display:none`), re-runs `fitMarpSlides()`, and posts `captureready:{index, clip, layout}` (clip = `{0,0,1280,720}` for Marp, `#preview`'s own box for non-Marp). Numeric layout fields are coerced to **finite** values first (`getBoundingClientRect` can yield `NaN` in a hidden window; `JSON.stringify(NaN)==="null"` would break the host's `f64` deserialize).
5. Rust `captureready:` → `CustomEvent::CaptureReady` → the event loop (which owns the webview lock, COM-STA) calls `png_win::capture_clip_to_png()` (CDP `Page.captureScreenshot`, `captureBeyondViewport:true` so the full 1280×720 box is captured regardless of the hidden window's viewport). The async completion handler writes the PNG and posts `CustomEvent::CaptureDone`.
6. `CaptureDone` advances the cursor: next slide → `__prepareCapture(next)`; done → writes `layout.json` and sets `ControlFlow::Exit` (process exits 0).

**Non-Marp `page.png`** captures the whole `#preview` column as one tall PNG. The app shell scrolls an inner container (`#preview-container`, `overflow:auto`, viewport height), so `#preview` — taller than the viewport for any non-trivial document — is visually **clipped** to that box; a CDP clip covering the full `scrollHeight` would then render a blank tail below the viewport. `__prepareCapture`'s non-Marp branch fixes this by walking `#preview`'s ancestors and neutralizing every overflow clip (`overflow:visible; height:auto; max-height:none`) before measuring the clip rect (the window is a throwaway capture surface, so mutating layout is safe). (Earlier this was misattributed to mermaid inflating the measured height — the real cause is the overflow clip; mermaid only matters because it makes a doc tall enough to exceed the viewport.)

**Known limitations**: Running two capture processes back-to-back can transiently collide (WebView2 teardown / user-data lock); run them sequentially. Forensic progress (`capture: start/ready/done`, per-slide CDP invoke) is written to `md-previewer.log` since release builds have no console. For a **build-free** alternative that also produces PNGs (rendered by a real headless browser, no `cargo build`), see `tools/preview-harness/shoot.py` in *Browser preview harness for AI iteration*.

## Browser preview harness for AI iteration (`tools/preview-harness/`)

A **fast, build-free feedback loop** so an AI agent (or a human) can open the *whole* previewer UI in a browser and inspect what it renders — **without any `cargo build`**. This is the complement to `--export-png`: the harness is for quick iteration on rendering/styling/layout; `--export-png` remains the highest-fidelity, actual-WebView2-binary path (use it — especially for final Marp deck layout — when byte-exact rendering matters).

- **`tools/preview-harness/serve.py`** — a single-file **stdlib-only** Python `ThreadingHTTPServer` (no pip deps) run from the repo root. It serves the **real** `assets/index.html` and reproduces, at serve time, the three things the Rust+WebView2 host normally does so the page boots unchanged:
  1. **Injects a bootstrap `<script>` right after `<head>`** (the on-disk `index.html` is never modified) that sets the host globals — `window.__appVersion` (read from `Cargo.toml`), `window.__userStyles` (scan `assets/*.css` minus `editor.css`), `window.__marpThemes` (scan `assets/marp/*.css`), `window.__styleExporters = {}` — matching Rust's init-script (the `window.__appVersion = …` block in `src/main.rs`), and installs a **logging IPC shim** (`window.ipc.postMessage = m => console.debug('[ipc]', m)`) so the guarded IPC flows become visible no-ops instead of throwing. `window.__captureConfig` is deliberately **not** set, so the `--export-png` capture path never triggers.
  2. **Auto-loads a document from a `?file=<ABS>` query param**: the bootstrap polls for `window.loadFileFromRust` (mirroring Rust's 100 ms retry), `fetch`es the raw markdown from **`/__doc?path=<ABS>`**, and calls `loadFileFromRust({ filename, filepath, content, raw })` — the same entry point Rust uses (`window.loadFileFromRust` in `assets/index.html`; `struct FileData` in `src/main.rs`, where `content === raw === source text`). With no `?file=` the app just shows its normal drop zone.
  3. **Serves local images / CSV / video through `/userfile/<path>`** exactly like Rust's route (the `/userfile/` branch of the `with_custom_protocol("app")` handler in `src/main.rs`): resolves relative paths against the current document's directory (component-walking `..`/`.`), passes absolute `/userfile/C:/…` paths through, sets the right MIME (incl. `csv`/`tsv`/`md`/`mov`/`m4v`/`webm`/`ogv`), and honors HTTP **`Range` → 206** so video scrubbing works. The doc's directory (the `/userfile/` base) is set from the `?file=`/`/__doc` path — **one document at a time**; to view another, navigate a new `?file=` URL. `/__log/…` returns 200 to swallow the preview's forensic logging fetches.
- **Launch config** — `.claude/launch.json` has a `preview-harness` entry (`python tools/preview-harness/serve.py --port 8770`). Start it (in the Browser pane: `preview_start {name:"preview-harness"}`), then open `http://localhost:8770/index.html?file=<ABSOLUTE .md path>`. See `tools/preview-harness/README.md`.
- **Intentional no-ops under the harness** (each just logs an `[ipc]` line; there is no Rust host): the companion editor (`E`) — *from the preview*; `cellcheck.py` drives `editor.html` directly instead, see below — save, HTML/PDF export (`X`), headless PNG capture, and cross-file `openmd:` navigation — to open another file use a new `?file=` URL. Everything *rendering-related* is fully live: Marp, themes/dark mode, mermaid, KaTeX, csv/tsv, plotly, abc, markwhen, footnotes, alignment/columns, inline styled spans, image sizing, video/YouTube embeds.
- **How the agent "sees" it** — `read_page` (rendered text/structure/attributes), `javascript_tool` (computed CSS, element geometry, and app state such as `window.__marpFitReport` = per-slide overflow/scale metrics, the same numbers `--export-png` writes to `layout.json`), `read_console_messages`, and `read_network_requests` (confirm `/userfile/` 200s). **Note:** in some environments the Browser pane's `computer {action:"screenshot"}` times out; the readers above are the reliable inspection surface, and `tools/preview-harness/shoot.py` (below) or `--export-png` is the fallback when actual pixels are required.
- **`tools/preview-harness/shoot.py`** — **actual-pixel capture** driven by Playwright + a system Chromium (Edge/Chrome, launched via `--channel` so no `playwright install` is needed). It starts the harness server in-process, loads the doc in a **real headless browser** (so fonts / `/userfile/` images / KaTeX / mermaid / Marp autofit all paint correctly — unlike a hidden WebView2 window or a `<img>`-rendered SVG), waits for async figures to settle, and writes PNG file(s) an agent can `Read`: `slide-NN.png` per (selected) slide **+ `layout.json`** for Marp, or `page.png` for a normal doc. For normal docs it first neutralizes the `#preview` overflow clip so nothing is cut off (the same clip that caused the old `--export-png` blank tail). Usage: `python tools/preview-harness/shoot.py <file.md> [--out DIR] [--slides 1,3,5-7] [--scale 2] [--channel msedge|chrome] [--full]`. This is the reliable pixel path when `computer {action:"screenshot"}` is unavailable; `--export-png` remains the byte-exact actual-WebView2-binary path.
- **`tools/preview-harness/cellcheck.py`** — the same harness pointed at the **editor** window (`assets/editor.html` + the `editor.iife.js` bundle) instead of the preview, standing in for the Rust host with an injected `window.__initialFile` and a recording `ipc` shim. It exists because the cell-mode facts that matter most are invisible to a unit test: whether the `Prec.highest` DOM keydown gate still precedes `@replit/codemirror-vim` (a dependency bump can invert that with no compile error), whether each cell op is exactly one undo step, whether the decorations / cell gutter / Command-mode caret-hiding actually compute, and whether each cell's "run" line equals the `data-line` the preview stamped on the matching slide (it opens `index.html` in a second page to compare). Note `add_init_script` takes a *script body*, so the injected globals must be an IIFE — a bare `() => {…}` is evaluated and discarded, which silently boots the editor with an empty document. Usage: `python tools/preview-harness/cellcheck.py [--channel msedge|chrome]`.
- **`tools/preview-harness/prefscheck.py`** — the same shape, for the editor's font zoom and settings modal. Beyond the assertions listed under *Tools* above, two harness mechanics are worth knowing before extending it: `add_init_script` calls **accumulate** and all of them re-run on every navigation in the order added, so the reset of a pref in an earlier script would wipe the value a later `page.reload()` is meant to read back — the persistence case therefore boots a **second page in the same context** (same origin, so it shares `localStorage`, but it carries only its own init script). And a focus assertion must use a real `page.click()`, since Chromium does not move focus on a programmatic `element.click()`. Usage: `python tools/preview-harness/prefscheck.py [--channel msedge|chrome]`.
- An earlier narrow markwhen unit harness (`assets/__cal_*`, loaded via the separate `assets-static` launch config) has been **deleted** — this full-UI harness replaces it. The `assets-static` launch config remains but now only serves `assets/` statically.

## Auto-update over an internal file share (opt-in, OFF by default)

An **opt-in** startup update check + background install, for **internal (intranet) distribution** — e.g. packaged by `..\nwc-addon` so the whole flow stays inside the company network. **OFF by default: base md_previewer ships no config file, so nothing runs and the app stays fully offline** (this is the deliberate gate — the capability is compiled into the binary but dormant). Windows-only (`src/updater.rs`, gated behind `#[cfg(windows)]` where it spawns the installer). No new crate dependency — the transport is a plain filesystem path (UNC `\\server\share\...` or local), read via `std::fs`; version parsing/compare and JSON use the existing `serde`/`serde_json`.

- **Config gate** — `updater::load_config()` looks for `update.json` next to the exe first, then in `assets/`. Absent / `enabled:false` / empty `source` / malformed ⇒ returns `None` ⇒ **no thread, no network**. Schema: `{ "enabled": bool, "source": "<UNC or local dir>", "manifest": "latest.json", "timeoutMs": 4000 }`. `assets/update.example.json` is a **non-functional example** (wrong filename on purpose); `nwc-addon` supplies the live `assets/update.json` via its existing `assets\*` overlay (no `.iss` change). The whole `assets/` tree is copied into installs, so the example file ships harmlessly but is never read.
- **Startup check** — in `main()` (right after `exe_dir`/`assets_dir` resolution and the global-injection block), when not in `--export-png` capture mode and a config loads, a **background thread** runs `updater::check_and_prepare(cfg, env!("CARGO_PKG_VERSION"))`: it reads `<source>/<manifest>` (via `read_with_timeout()` — the blocking read runs on a helper thread with `recv_timeout(timeoutMs)` so an unreachable UNC share gives up promptly instead of hanging for the SMB timeout), parses `{version, setup, notes}`, and semver-compares (`parse_semver`/`is_newer`, tolerant tuple compare; parse failure ⇒ "not newer"). When newer it **prefetches** the installer `<source>/<setup>` into `%TEMP%\mdp-update\` (so "今すぐ更新" is instant; on copy failure it falls back to running straight from the share), stashes the result in a shared `Arc<Mutex<Option<updater::UpdateReady>>>` (`update_ready`), and posts `CustomEvent::UpdateAvailable { version, notes }`.
- **UX = notify then update** — the event loop handles `UpdateAvailable` by calling `window.__updateAvailable({version, notes})` in the webview, which shows **`#update-banner`** (theme-aware, distinct from the transient `#toast`): a small **bottom-right card**, not a full-width top bar — an update is 「気づけばよい」 information, so it must not cover the first lines of the document nor carry modal-like weight. It reuses the help/style modal's `.panel` palette so it reads as native chrome, and carries a filled **「更新」** button, an absolutely-positioned **「×」** close in its top-right corner (that button keeps the id `update-later-btn`), and a small underlined **「今後表示しない」** text link. Its `z-index` (9600) sits *below* `#toast` (10000) and the modals (10001) so a notification arriving while the help modal is open never lands on top of it, and `body.marp.deck-mode` nudges it above `#slide-counter`. Appearance is a `@keyframes` animation rather than a transition, because the `.visible` class is added in the same frame as `display: none` → `flex`. 「今後表示しない」persists `localStorage['autoUpdate:optout']='true'` so a user can permanently suppress it on their machine even under a managed (nwc) build; the banner JS gates on that flag. `body.capturing` hides the banner so `--export-png` shots are unaffected.
- **The notification must survive arriving mid-page-load** — the check thread is spawned *before* the webview is created and finishes in well under a second, so `evaluate_script` routinely lands while `index.html` is still parsing. Both halves therefore stash instead of dropping, mirroring `loadFileFromRust`'s `DOMContentLoaded`+retry and the `__pendingWorkspace` stash: (1) **Rust** emits `if (typeof window.__updateAvailable === 'function') { … } else { window.__pendingUpdate = … }` — the previous bare `window.__updateAvailable && …` short-circuited to nothing when the function (defined ~line 2380) wasn't reached yet; (2) **JS** — `__updateAvailable` defers into an IIFE-scoped `pending` when `document.readyState === 'loading'` or `#update-banner` (~line 8420, ~6000 lines *after* the function) isn't parsed yet, and the existing `DOMContentLoaded` handler drains both `pending` and `window.__pendingUpdate`. Without both, the banner was silently lost until the next launch — the actual cause of the 「自動更新が働かない」 report, confirmed by CDP-inspecting a live 0.17.0 install (banner element present, `__updateAvailable` a function, opt-out unset, yet `className` empty).
- **Delivery is traceable in `md-previewer.log`** — the Rust handler logs `updater: banner dispatched (version=…)`, and the banner JS reports back over the existing `__dbgLog` (`/__log/`) bridge with `update banner shown v<ver>` / `update banner deferred (dom not ready)` / `update banner suppressed by optout`. Before these, the log stopped at `prefetched` and could not distinguish "shown", "user opted out" and "silently dropped" — which is why the race went unnoticed. A healthy run shows `banner dispatched` followed by `banner shown`.
- **Install + relaunch** — 「今すぐ更新」posts `update:install`; the IPC handler (next to `openinstalldir:`) reads `update_ready`, then on a worker thread calls `updater::launch_installer_and_relaunch(setup_temp, exe_path, current_file)`. That spawns a detached `cmd /S /C "…"` (CREATE_NO_WINDOW) that: waits ~1s (`ping -n 2 127.0.0.1 >nul` — console-independent, unlike `timeout`) so this app fully exits and releases its exe lock, runs the Inno installer `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART` (per-user, no UAC; stable AppId ⇒ in-place upgrade), then `start`s the (new) exe — reopening the current file if one was open. It then posts `CustomEvent::QuitForUpdate` ⇒ `ControlFlow::Exit`. (`skipifsilent` in the installer's `[Run]` means the installer won't relaunch the app itself, so the wrapper's `start` does it.)
- **Failure = silent no-op** — unreachable share, timeout, missing/invalid manifest all log to `md-previewer.log` (`updater: …` lines) and return `None`; the UI is never disturbed. Unit tests for `parse_semver`/`is_newer` live in `src/updater.rs` (`#[cfg(test)]`).
- **Distributor setup** (preparing the share, publishing a new version, editing `update.json`/`latest.json`) is documented in **`..\nwc-addon\README.md` → 社内自動更新のセットアップ**.

## Architecture

### Build / installer / icon

- `build.rs` + `app.rc` + `assets/icon.ico` — Windows icon embedding. `build.rs` invokes the `embed-resource` build-dep to compile `app.rc` (a one-line Win32 resource script: `IDI_ICON1 ICON "assets/icon.ico"`), which embeds the multi-resolution `.ico` into the release exe so Explorer / taskbar / window chrome / `.md` file thumbnails (via the registry `DefaultIcon` pointing at `md-previewer.exe,0`) all use it. Only compiles on Windows targets.
- `tools/make-icon/make_icon.py` — Pillow-only generator for `assets/icon.ico`. Draws each size (16/32/48/64/128/256) programmatically: rounded-square navy→blue gradient + bold white "M" + a small down-arrow on sizes ≥ 48. No SVG renderer dependency. Rerun (`python tools/make-icon/make_icon.py`) when changing the design; commit the regenerated `.ico`.
- `installer/md-previewer.iss` (+ `installer/README.md`) — Inno Setup 6 script for the per-user Windows installer. Installs to `%LOCALAPPDATA%\Programs\MdPreviewer\` (no admin needed), bundles `target/release/md-previewer.exe` + the entire `assets/` tree + the `samples/` tree (demo Markdown files surfaced via a Start-menu "Sample Documents" shortcut that opens `{app}\samples` in Explorer), creates Start-menu (and optional desktop) shortcuts, and writes opt-in `HKCU` registry entries (ProgID `MdPreviewer.md`, `.md`/`.markdown` association, folder & file context menus) under user-toggleable wizard tasks (`assoc_md`, `ctx_folder`, `ctx_file`, `desktopicon`). The repo-root **`HISTORY.md`** (user-facing per-version release notes, hand-authored & git-tracked — *not* a generated file) is bundled into `{app}` and **auto-opened in the previewer after install**: the `[Run]` launch entry passes `"{app}\HISTORY.md"` as the exe argument and carries the `postinstall skipifsilent` flags, so the wizard's final-page checkbox (checked by default) is the natural opt-out. A `更新履歴 / Release Notes` Start-menu shortcut re-opens it on demand. AppId GUID is fixed (`892BC24C-95B0-43BB-8480-087C91AC6316`) so successive versions upgrade in place. `AppVersion` must be bumped in lockstep with `Cargo.toml`'s `version =`. Build: `iscc installer\md-previewer.iss` → `dist\MdPreviewer-Setup-<ver>.exe`. Caveat: if Windows' "Default apps" Settings has an explicit user choice for `.md`, that overrides the HKCU default written by the installer.

### Rust source

- `src/main.rs` — Rust app entry. Handles: window / event loop (`tao`), WebView2 host (`wry`), markdown → HTML (`pulldown-cmark`), file watcher (`notify`, swappable between single-file `NonRecursive` and workspace-root `Recursive`), custom protocol handler for serving assets and user files (including images and videos via the `/userfile/` route), current-directory tracking via `Arc<Mutex<…>>` for relative-path resolution, and workspace (directory) state via `Arc<Mutex<Option<Workspace>>>`.
- `src/editor_registry.rs` — owns the (at most one) paired editor `WebView` and routes preview↔editor IPC.
- **Shared helpers in `src/main.rs`** (each replaced a hand-rolled duplicate): `write_suppressed` / `suppress_watcher` + `SAVE_SUPPRESS_MS` — mark a path as self-written so its own `notify` event is ignored, then write (4 call sites: `editor:save:` on both sides, `savefile:`, and the `.mdx` repack); `js_call` / `eval_js_fn` — build the `if (typeof window.X === 'function')` guarded call (used across `main.rs` and `editor_registry.rs`; a few sites deliberately stay hand-written — see the comments there); `build_load_file_script` — serialize a `FileData` into the `loadFileFromRust(…)` call shared by all three render paths; `current_file_dir` / `with_initial_dir` — seed native Save-As dialogs.
- **Tests** — `main.rs` has a `#[cfg(test)] mod tests` covering its pure functions (`parse_slides_spec`, `parse_byte_range`, `slugify`, `extract_headings_from_md`, `parse_toc_md`, `format_title`, `slide_png_name`, `paths_equal`, `get_mime_type`, `is_markdown_href`, `normalize_rel`, `js_call`); `mdx.rs` and `updater.rs` have their own. Run with `cargo test` (debug, fast) — this is the regression net for any change to those helpers.
- `src/clipboard_win.rs` — Win32 OS-clipboard helper (`clipboard-win` crate; Windows-only, mirrors `ime_win.rs`'s module shape). Exposes `get_clipboard()` / `set_clipboard()` for the editor's OS-clipboard yank/paste (`editor:clipboard:get:` / `editor:clipboard:set:` IPC). See *Companion Editor Window → Vim & default keybindings → OS-clipboard yank/paste*.
- `src/cdp_win.rs` — shared WebView2 DevTools-Protocol plumbing (Windows-only; `webview2-com` + `windows` crates), used by `pdf_win.rs` and `png_win.rs`. `cdp_call_to_file()` obtains the `ICoreWebView2`, invokes a CDP method with an async completion handler, base64-decodes the `{"data":…}` result, writes it to disk, and reports success to a callback — the single `unsafe` FFI block for both features. The two callers differ only in method name, params JSON, and which `CustomEvent` they post. The callback is held in a once-only cell (`OnceDone`) because the dispatch-failure path and the async handler are mutually exclusive in a way the compiler cannot see.
- `src/pdf_win.rs` — PDF export helper (Windows-only). `print_current_to_pdf()` prints the live webview via CDP `Page.printToPDF` (`generateDocumentOutline` for bookmarks, `printBackground`), base64-decodes the result, writes the file, and posts `CustomEvent::PdfExportDone`. Its params come from `print_params(page_px)` (unit-tested): `None` = A4 portrait + 0.4in margins, `Some((w, h))` = a paper of exactly that CSS-px size with zero margins, which is how a Marp deck gets one page per slide. See *Export to standalone HTML / PDF → PDF export*.
- `src/png_win.rs` — headless PNG capture helper (Windows-only; same shared `cdp_win` plumbing as `pdf_win.rs`). `capture_clip_to_png()` screenshots a CSS-px `clip` rectangle of the live webview via CDP `Page.captureScreenshot` (`captureBeyondViewport:true`, `clip.scale` for a crisp 2× image), base64-decodes, writes the PNG, and posts `CustomEvent::CaptureDone`. Used only by the `--export-png` CLI mode. See *Headless PNG capture for agents*.

### Assets (loaded at runtime)

- `assets/index.html` — preview UI template.
- `assets/editor.html` + `assets/editor.css` — editor window UI template. Loads `assets/libs/editor/editor.iife.js` and calls `window.MdEditor.create(root)`.

### Release automation (`main`-branch git hook)

Releases are automated by a tracked git hook that fires when the **`main`** branch is updated via a merge (`git merge` / `git pull`). The pieces:

- `tools/hooks/post-merge` — tiny POSIX-`sh` shim (Git for Windows runs hooks via its bundled `sh`). It only invokes `pwsh -NoProfile -File tools/release-on-main.ps1`, and short-circuits if `MDP_IN_RELEASE=1` is already set (re-entrancy guard). It always `exit 0`s so a failed release never blocks the merge.
- `tools/release-on-main.ps1` — the orchestrator, split into **two phases** so the release notes cannot be published unreviewed. It finds the previous release tag via `git describe --tags --abbrev=0 --match "v*"`, collects `git log --no-merges` subjects in `<lastTag>..HEAD`, and **exits silently when that range is empty** (so it never re-fires after its own release commit — the new tag sits at HEAD).

  **Phase 1 (default, what the hook runs)** — rewrites the version in **three places** (`Cargo.toml` `version =`, `installer/md-previewer.iss` `#define AppVersion`, and a new `## v<X.Y.Z>` section prepended to `HISTORY.md`) and then **stops**. No build, no commit, no tag. The generated section carries a `TODO(release-notes)` review marker.
  - **Commit classification.** Subjects are split by Conventional-Commit prefix: `feat:`/`fix:`/`perf:` and un-prefixed free-form subjects become **user-facing bullet candidates** (prefix stripped, so they read sensibly even unedited); `refactor:`/`test:`/`docs:`/`chore:`/`build:`/`ci:`/`style:` become **internal work**, listed inside the review comment as reference rather than as shippable bullets. The skip regex (this script's own `リリース v…` commits, `WIP`, `Merge`, …) is **anchored at the start** of the subject — it used to match `version`/`release` anywhere, which could silently drop a legitimate `feat: リリースノート生成に対応`.
  - **Bump heuristic.** Breaking (`破壊的`/`BREAKING`/`!:`) → major; a **user-facing** subject matching `追加`/`機能`/`対応`/`実装`/`新規`/`^feat` → minor; else patch. Internal commits no longer count toward minor — a refactor- or docs-only range is now correctly a patch. Override with `-Bump major|minor|patch`.
  - **`## 未リリース` folding.** A hand-written `## 未リリース` (or `Unreleased`) section is absorbed: its bullets are carried into the new version section *first*, and the heading is removed. Without this the script's insertion point (the first `^## v`) leaves that section stranded above the release with duplicate content.
  - **Re-run guard.** If a draft is still pending (marker present), phase 1 refuses — **even with `-Force`** — so the version can never be double-bumped. `-Force` means "I know the tree is dirty", not "bump me twice".

  **Phase 2 (`-Finalize`)** — refuses while the review marker or a `## 未リリース` heading remains, checks the three version sites agree and that the tag doesn't already exist, **then** runs `build-installer.ps1` (with `MDP_IN_RELEASE=1`) and, only on a successful build, stages just those files, commits `リリース v<X.Y.Z>`, and `git tag v<X.Y.Z>` — an ordinary commit (fires `post-commit`, not `post-merge`, so no loop). Building here rather than in phase 1 is the point: `installer/md-previewer.iss` bundles `HISTORY.md` and auto-opens it after install, so an installer built before the notes were edited would ship the raw draft.

  **`-Verify`** — mechanical pre-publish check, runnable any time: the three version sites agree, `## v<X.Y.Z>` exists, no review marker, no leftover `## 未リリース`, the tag is HEAD or an ancestor, and **the release notes bundled into the installer match the current `HISTORY.md`**. That last one compares a SHA-256 recorded by `build-installer.ps1` (`dist/…exe.notes.sha256`) rather than timestamps, so a `git checkout` that rewrites `HISTORY.md` byte-identically doesn't raise a false alarm; artifacts predating the stamp fall back to an mtime comparison.

  Push is never automatic unless `MDP_RELEASE_PUSH=1`. Other flags: `-DryRun` (phase-1 report only), `-SkipBuild` (`-Finalize` without the installer build), `-Force`.
- `tools/install-hooks.ps1` — sets `git config core.hooksPath tools/hooks`. This is **per-clone local config**, so it must run once after cloning; `install-deps.ps1` calls it automatically (right after `fetch-libs.ps1`, so even `-SkipNode` enables the hook).

#### The release flow in practice — merge, review, finalize

`HISTORY.md` is bundled into the installer and **auto-opened after install**, so a generated draft must never reach a user. The script therefore refuses to finalize while the draft is unreviewed; the steps below are what that gate expects, not a checklist you have to remember.

**1. (optional) Preview before merging.** Cheapest place to catch a wrong bump, since the version lands in three files:

```bash
pwsh -NoProfile -File tools/release-on-main.ps1 -DryRun -Force
```

**2. Merge into `main`.** The hook runs phase 1: versions bumped, a `## v<X.Y.Z>` draft written to `HISTORY.md`, nothing built, committed or tagged. It prints the next command. If the bump is wrong, discard and redo with `-Bump`:

```bash
git checkout -- Cargo.toml installer/md-previewer.iss HISTORY.md
pwsh -NoProfile -File tools/release-on-main.ps1 -Bump patch
```

**3. Write the release notes.** Open the `## v<X.Y.Z>` section. The draft gives you user-facing candidates as bullets and the internal commits as reference inside the `TODO(release-notes)` comment. Turn it into something a user benefits from reading:

- **Delete what a user cannot observe.** A range that was entirely internal gets one honest line — 「内部改善（動作の変更はありません）」— not fifteen `refactor:` bullets. Phase 1 already pre-fills exactly that when it finds no user-facing commits.
- **Describe the change, not the implementation.** Lead with a bold feature name, then what changed for the reader: 「**定義リストに対応** — `用語` の次の行に `: 説明` と書くと…」. Keep the `- **名前** — 説明。` shape and newest-first ordering used throughout the file.
- **Merge several commits that were one feature** into one bullet, and drop anything added and then reverted inside the same range.
- **Check the internal list for buried user-facing fixes.** Prefix-based classification is a heuristic: in v0.18.0 a workspace `_toc.md` bug fix sat under a `test:` commit and would have been dropped on prefix alone.
- Optionally summarize the internal work as a single `> 開発者向け:` line (v0.15.0 and v0.18.0 do this).

Then **delete the `TODO(release-notes)` comment block**.

**4. Finalize.** This is the gate: it refuses while the marker (or a leftover `## 未リリース` heading) remains, verifies the three version sites agree and the tag is free, then builds the installer — with your edited notes inside it — and creates the commit and tag:

```bash
pwsh -NoProfile -File tools/release-on-main.ps1 -Finalize
```

**5. Verify and publish.**

```bash
pwsh -NoProfile -File tools/release-on-main.ps1 -Verify
git push origin main && git push origin v0.18.0
```

`-Verify` is mechanical and re-runnable; it also catches the case where you edited `HISTORY.md` *after* finalizing, which leaves the built installer bundling stale notes (it compares the notes hash `build-installer.ps1` recorded at build time). If it reports that, rebuild and amend:

```bash
pwsh -NoProfile -File build-installer.ps1 -SkipBuild -SkipLicenses
git add HISTORY.md && git commit --amend --no-edit && git tag -f v0.18.0
```

(`git tag -f` is required — the tag still points at the pre-amend commit otherwise.)

**If the installer build fails during `-Finalize`**, there is no commit and no tag and the version edits stay in the working tree. Fix the build and re-run `-Finalize`; do not hand-commit.

## Build & Run Commands

**One-shot build (recommended):** `build.ps1` at the repo root wraps every step below — populate `assets/libs/`, generate the icon, run `cargo build --release`, and sync `assets\` into `target\release\assets\`. Idempotent (skips finished steps on re-run):

### Building the installer

For redistributable per-user installs, `build-installer.ps1` at the repo root wraps the full chain — runs `build.ps1` (which itself runs `install-deps.ps1` if needed, generates the icon, and `cargo build --release`s), regenerates `assets/THIRD_PARTY_LICENSES.txt`, then invokes `iscc`:

```powershell
.\build-installer.ps1                       # one-shot: build + licenses + iscc
.\build-installer.ps1 -SkipBuild            # skip build.ps1 (target\release is up to date)
.\build-installer.ps1 -SkipLicenses         # reuse the existing THIRD_PARTY_LICENSES.txt
.\build-installer.ps1 -Iscc 'C:\...\ISCC.exe'  # override ISCC location
```

`build-installer.ps1` finds `ISCC.exe` via PATH, falling back to standard install locations — per-user (`%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe`) is checked first, then machine-wide `Program Files (x86)\Inno Setup 6\ISCC.exe`. Output: `dist\MdPreviewer-Setup-<AppVersion>.exe` (AppVersion is read from `installer\md-previewer.iss`).

**Manual equivalent:**

```powershell
# one-time / when icon changes
python tools\make-icon\make_icon.py

# build the exe (build.rs embeds assets/icon.ico via app.rc)
cargo build --release

# regenerate license file (git-ignored)
pwsh -File tools\collect-licenses.ps1

# compile the Inno Setup 6 installer
iscc installer\md-previewer.iss
# -> dist\MdPreviewer-Setup-<version>.exe
```

The installer bundles `target/release/md-previewer.exe` + the full `assets/` tree into a single `.exe` that installs to `%LOCALAPPDATA%\Programs\MdPreviewer\` without admin rights. See `installer/README.md` for prerequisites and versioning rules.

## Git commit conventions

- **Start work on a dedicated branch, not `main`.** Before beginning any change, if the current branch is the default (`main`), create/switch to a work branch first (e.g. `git switch -c work` or a feature-named branch). This keeps `main` clean for the release flow — merging the work branch into `main` is what fires the `post-merge` release hook (see *Architecture → Release automation*). Do this at the *start* of the task, before editing files.
- **Messages are Japanese**, following the existing history: a concise `<type>: <要約>` subject (types like `feat:` / `fix:` seen in the log, or a plain Japanese summary such as `リリース v0.14.0`), a blank line, then Japanese bullet points for the details.
- **Multi-line messages via the Bash tool must use a Bash heredoc**, e.g. `git commit -F - <<'EOF' … EOF` (or repeated `-m` flags). **Do NOT use PowerShell here-string syntax (`@'…'@`)** — this repo's shell is PowerShell-primary, but commit messages are almost always authored through the **Bash** tool, where `@'` / `'@` are *literal* characters, not string delimiters. Passing `git commit -m @'…'@` leaks a stray `@` onto the subject line (and pushes the real subject to line 2). If it happens, fix with `git commit --amend -F - <<'EOF' … EOF`. When committing from the PowerShell tool instead, the `@'…'@` here-string *is* correct (see the PowerShell tool's own guidance) — the point is to match the syntax to the shell actually running the command.
- End every commit message with the trailer `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.
- Commit or push only when the user asks; if on the default (`main`) branch, note that the `post-merge` release hook fires on merges — see *Architecture → Release automation*.

# Files, media and navigation

**Owns:** the webview/host path boundary in `assets/index.html`: `/userfile/` URLs, images, video, links, history, drag and drop

- **Image serving via the `/userfile/` protocol (NOT base64)** — local images are served lazily through the `app://localhost/userfile/...` custom-protocol route (the same route videos use), **not** base64-inlined into the markdown. This was a deliberate performance change: inlining a large image set (e.g. an image-heavy Marp deck — ~40 MB of images) produced a ~53 MB data-URI string that had to be marshalled through `evaluate_script` as a JS source literal, parsed, and decoded synchronously on `innerHTML`, making startup very slow. Now the webview's `transformImagePath()` (in `assets/index.html`) rewrites every local image `src` (`img/foo.png` → `/userfile/img/foo.png` via `toUserfileUrl()`) so WebView2 fetches/decodes images in parallel off the UI thread with native caching; image `<img>`s also get `decoding="async"`. `transformImagePath()` skips external URLs / data URIs and **video** paths (those are left for `applyVideoEmbeds()`, which builds its own `/userfile/` URL — double-prefixing must be avoided). Relative paths resolve against the open file's directory via the route's `current_dir` (`Arc<Mutex<…>>`), identical to the video mechanism. **The Rust-side base64 embedding has been removed entirely** — `embed_images_as_base64` and its `IMG_RE` / `IMG_CACHE` statics are gone. They had become unreachable: the skip list (originally video-only) grew to cover every image extension, and every image MIME `get_mime_type` knows is in it, so the encode path could only ever fire for a non-renderable extension. **Raw vs. content channel** — `FileData` still carries both `content` and `raw`; they are now equal (both relative paths), but the distinction is kept so any host-bound save (the Marp theme picker's `savefile:` IPC) still serializes `currentMarkdownRaw`. **HTML export re-inlines images as base64** to stay self-contained: `buildExportArtifact()` in `assets/index.html` walks the cloned `<img>`s whose `src` is a `/userfile/` URL, `fetch()`es each unique one (the protocol route reads it off disk), converts the blob to a data URI via `FileReader`, and writes it back onto the clone (parallelized with `Promise.all`) — so single-file exports remain one self-contained `.html` exactly as before. Export is a one-shot user action, so the fetch latency is acceptable.
- **Image sizing** — Obsidian-style pipe syntax inside the alt text: `![alt|300](p)` (width px), `![alt|300x200](p)` (width × height), `![alt|x200](p)` (height-only), `![alt|@0.5](p)` (scale × intrinsic size). Implemented as a webview-side pass (`applyImageSizing()` in `assets/index.html`) that runs after both `marked.parse()` and `renderMarp()`. Pixel dimensions become `width`/`height` attributes; scale resolves to a concrete `width` once the image reports its `naturalWidth` (images now load asynchronously via the `/userfile/` route, so `applyImageSizing` reads `naturalWidth` on the `load` event when the image isn't yet `complete`). The sizing suffix is stripped from the displayed `alt`. Carries through to HTML export.
- **Relative image paths** are resolved against the directory of the open markdown file (current-directory tracked in `src/main.rs` via `Arc<Mutex<…>>`). **Parent-directory references (`../`, `../../`, …) that climb above the document directory are supported.** The Rust `/userfile/` resolver already handles `..` (`Component::ParentDir => resolved.pop()`, no boundary guard — escaping the doc dir is intentional). The catch is browser URL normalization: the page is served on the synthetic `https://app.localhost/` origin, so a relative `/userfile/../x` would be collapsed by the URL parser *past* the `/userfile/` prefix (→ `/x`, losing the route) before the request reaches Rust. So `toUserfileUrl()` in `assets/index.html` detects (via `relPathEscapesBase()`) when a relative path escapes the document directory and, when it does, resolves it to an **absolute** path (reusing `resolveRelativePath()` against `currentFilePath`'s dir, stripping the `file:///` prefix) — an absolute `/userfile/C:/…` path has no `..` to collapse and hits Rust's `file_path.is_absolute()` branch directly. Non-escaping paths (`img/foo.png`, `sub/../foo.png`) keep the original relative `/userfile/…` form. This covers images, `applyVideoEmbeds()` videos, and the `plotly` block's `file:` CSV (which now routes through `toUserfileUrl()` too) — all share the one helper. Sample: `samples/parent-paths/demo.md`.
  - **Non-ASCII (e.g. Japanese) paths** — `marked` percent-encodes non-ASCII characters in `<img>` / `<a>` URLs (`画像.png` → `%E7%94%BB%E5%83%8F.png`), while raw paths (file drops, `plotly` `file:`) arrive unencoded. `toUserfileUrl()` must not `encodeURI()` these — `encodeURI()` is **not idempotent** and re-encodes an existing `%E6` into `%25E6`, producing a double-encoded URL that Rust's single `urlencoding::decode()` can't recover (→ 404). Instead a shared **`encodePathForUserfile()`** helper in `assets/index.html` normalizes each `/`-split segment by decoding then re-encoding once (`encodeURIComponent(decodeURIComponent(seg))`), skipping empty / `.` / `..` / Windows drive-letter (`C:`) segments — idempotent for both raw and pre-encoded input. Used by all three `toUserfileUrl()` return paths and the workspace-export fetch. (Cross-file `.md` link nav via `openmd:` needs no such fix — the click handler's `decodeURIComponent` already normalizes `marked`'s encoding before the raw path reaches Rust.) Sample: `samples/japanese-path/文書.md`.
- **Video & YouTube embedding** — the image syntax `![alt](target)` is reused for video. `applyVideoEmbeds()` in `assets/index.html` runs a webview-side `<img>` scan (immediately *before* `applyImageSizing()`, in both the normal pipeline and `renderMarp()`) and converts: (a) a `src` whose extension is a video file (`.mov` / `.mp4` / `.m4v` / `.webm` / `.ogv` / `.ogg`) into `<video class="video-embed" controls preload="metadata">` with a `<source>` routed through the `/userfile/` protocol route; (b) a YouTube URL (`youtu.be/ID`, `youtube.com/watch?v=ID`, `…/embed/ID`, `…/shorts/ID`) into a responsive `<iframe class="video-embed youtube-embed">` (start offset parsed from `?t=` / `?start=`, accepting `90`, `1m30s`, or `90s`). The Obsidian `|W` / `|WxH` pixel sizing suffix (in the **alt text**, e.g. `![alt|480](clip.mp4)` — *not* inside the URL, where `marked`/marp-core percent-encode the `|` to `%7C` and it fails to match) is consumed here for videos (`@scale` is image-only). The alt is parsed by a shared **`parseVideoAlt(alt)`** helper (returns `{text, widthCss, heightCss, frameTime}`) that splits the alt on `|` and picks out, order-independently, a size token (`W` / `WxH` / `xH`) and a **PDF frame-time token `t=<time>`** (`parseTimeSpec()` accepts `3` / `2.5` / `90s` / `1m30s` / `0:03` / `1:02:03`); the frame time is stored on `video.dataset.pdfFrameTime` and used at PDF-export time to rasterize a still frame (see *Export → PDF export → video frames*), and the video is also seeked to it on `loadedmetadata` so the preview shows that frame. **Marp-native image sizing directives are honored for video/YouTube too**: marp-core translates `![w:400 h:225](…)` / `![width:400px](…)` into an inline `style="width:…;height:…"` on the `<img>`, and `applyVideoEmbeds()` carries that inline width/height (px **or** %) onto the generated `<video>` / `<iframe>` when no alt suffix is present — this is what fixes "Marp スライドで動画サイズ調整が効かない" (the swapped-in element previously discarded the `<img>`'s marp style). All sizes are applied via **inline `style` on the embed** (not `width`/`height` attributes), so they beat the `#preview video.video-embed { height:auto }` stylesheet rule and an explicitly-requested height actually takes effect; when only a width is given, height is left unset so `height:auto` (video) / `aspect-ratio:16/9` (the `iframe.youtube-embed:not([width])` rule) preserves the ratio. **Local videos are deliberately *not* base64-embedded** — `embed_images_as_base64` in `src/main.rs` skips video extensions (and now image extensions too — see *Image serving via the `/userfile/` protocol*) so the path passes through to JS and is served lazily via the `/userfile/` route, which now honors HTTP `Range` requests (`parse_byte_range` + a `206 Partial Content` branch) so seeking/scrubbing works. `.mov` plays only when its codec is Chromium-supported (H.264 ok; ProRes/HEVC not). YouTube `<iframe>`s survive HTML export unchanged; local videos are copied (see *Export*). The Marp figure-centering pass treats `<video>` / `iframe.video-embed` (and a paragraph whose sole child is one) as a figure.
- **Cross-file `.md` link navigation** — clicking a link to another `.md` / `.markdown` file re-opens it in the current viewer (WebView2 blocks `file://` navigation, so the click is routed back to the Rust host via `openmd:` IPC). **Relative links resolve against the document directory in the click handler** — Rust's `to_abs()` resolves a relative path against the *process CWD* (the wrong directory), so a bare `openmd:./foo.md` would fail. The normal pipeline sidesteps this by rewriting every `<a href>` to an absolute `file:///` path at render time (`resolveRelativePath()` in `renderMarkdown()`), but **the Marp pipeline leaves hrefs relative** (marp-core renders them as-is). So the delegated `#preview` click handler in `assets/index.html` resolves any still-relative `.md`/`.markdown` href against `currentFilePath`'s directory (via `resolveRelativePath()`) before posting `openmd:<abs>` — this is what makes **links inside Marp slides** work (they otherwise silently no-op'd because the relative path never resolved). Absolute (`C:\…`) and `file://` hrefs are passed through unchanged, so the normal pipeline is unaffected.
  - **`Ctrl`/`Cmd` + click opens the link in a NEW previewer window** — the same click handler branches on the modifier after the path is resolved (so both branches share the `file:///`-stripping / Marp relative-resolution / backslash-normalization logic, and `Shift`/`Alt` are excluded to keep the combo unambiguous), posting **`openmdnew:<abs>`** instead of `openmd:`. The Rust branch sits immediately *before* the `openmd:` one in the IPC chain (so the two prefixes can never be confused), gates on `path.is_file() && is_previewable_ext(&path)` — markdown or `.mdx`, extension-only so the predicate stays a pure unit test — and then, off-thread like `openinstalldir:`, calls `spawn_new_previewer()`: `Command::new(<this exe>).arg(target).spawn()`. **No `CustomEvent`, no shared state** — this window's watcher, `current_file`, `current_dir` and `history` are untouched; the new window is an *ordinarily launched* previewer, exactly as if Explorer had double-clicked the file, so it builds its own watcher / history / editor pairing (and inherits theme + dark mode through `localStorage`, which is per-user-data-folder). Nothing needs coordinating: there is no single-instance guard and the WebView2 user-data folder is left unpinned, so concurrent instances were already the norm. The IPC closure holds its own un-gated `ipc_self_exe` clone of `exe_path` (the existing `ipc_exe_path` is `#[cfg(windows)]`-gated for the updater). **The new window is cascaded, not centred.** Every window otherwise goes through `clamped_window_geometry()` (`src/editor_registry.rs`), which *centres* it on the primary monitor — so a spawned child landed exactly on top of its parent and the feature looked like it had done nothing. `next_cascade_origin(parent)` therefore reads the parent's `outer_position()` and `outer_size()` (in the IPC handler, the only place holding the `&Window` — the worker thread must not touch it), works out the target with `cascade_origin()`, and passes it as a new **`--window-pos <x>,<y>`** CLI flag (logical px, so the offset looks the same at any DPI). The decision is made in the *parent* because that is the only place that knows both where the window sits and which monitor (`current_monitor()`) it sits on. `cascade_origin()` steps `CASCADE_STEP` (36) × a `CASCADE_SEQ.fetch_add(…) % CASCADE_CYCLE + 1` counter down-right — so repeated Ctrl+clicks from one window walk a 6-step cascade instead of stacking — **but wraps to the monitor's top-left corner (+ the same step) when the stepped position would not fit**, which is what Windows' own "cascade windows" does. **The wrap, rather than a clamp, is load-bearing and was found by measuring.** This app's window is 1200×800 logical, which on a 1536×960 logical display (a 1920×1200 panel at 125% — an ordinary laptop) leaves *under one step* of slack on either axis; the first implementation clamped, the clamp saturated, and the child opened at its parent's exact position again. Measured before/after on that display: parent content origin `(175,70)`, children at `(43,66)` then `(79,102)`. In the child, `main()` parses the flag with `parse_window_pos()` and, **after `build()`, applies it with `window.set_outer_position()` — deliberately NOT `WindowBuilder::with_position()`**: measured on Windows, `with_position` lands roughly the *client* origin while `outer_position()` (what the parent read) returns the window rect ~20 logical px higher, so mixing the two ate that much of the vertical step on every hop (the first child came out 36px right but only 16px down). `cascaded_window_pos()` resolves the request against whichever monitor *contains* it (so a cascade off a secondary display stays there; falls back to primary) and `clamp_window_origin()`s it in as a defensive backstop, using `(mon - size).max(0.0)` so a window larger than the monitor pins to the origin rather than handing `f64::clamp` an inverted range (which panics). All three pure helpers are unit-tested. The `#fragment` is dropped — but the same-window path drops it too, so the two agree; likewise **`.mdx` links never reach either branch** (the handler's regex is `.md`/`.markdown`), a pre-existing gap deliberately left alone so both branches keep matching the same set of links. Verification: `tools/preview-harness` for the JS branch (the IPC shim shows `openmd:` vs `openmdnew:`), and for the Rust half launch the exe with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` and drive a real Ctrl+click over CDP — `/json` then lists one page target per window. Note a spawned child **inherits that env var**, so all instances share the one debugging port; also each launch **truncates `md-previewer.log`**, so read the log before spawning.
- **Back / Forward history** — each cross-file navigation pushes a `history.pushState` entry, so WebView2's native context-menu「戻る」/「進む」, `Alt+←` / `Alt+→`, and mouse side buttons traverse previously opened files. `popstate` routes the stored filepath back to Rust via the same `openmd:` IPC. **View position is preserved across Back/Forward** — the current view position is persisted per history entry as a source line in `history.state.line` and restored on return, so navigating back to a Marp deck lands on the **slide you were viewing** (not slide 1) and a plain doc restores its **scroll position**. The line is written by `__syncHistoryLine()` in `assets/index.html`, which reuses `currentPreviewLine()` (resolves the right line for deck active-slide / list / scroll / plain-doc modes) to `history.replaceState({...state, line})` the *current* entry — a continuous-sync design (updated whenever the view changes, not snapshotted on leave), since the History API can only edit the current entry, which keeps multi-hop Back/Forward correct. Two triggers feed it: **deck slide changes** via a call at the end of `__marpUpdateDeck()` (the single funnel for every deck move; deck navigation doesn't scroll the container), and **scrolling** via a debounced `previewContainer` `scroll` listener (plain docs + Marp scroll mode). A `__loadingFile` guard suppresses sync while a load is in flight (`history.state` is transient during render, so an unguarded sync would write the new doc's line onto the *outgoing* entry). On `popstate` the handler stashes `e.state.line` in `pendingHistLine`; after the file re-renders, `loadFileFromRust()` calls `applyEditorScroll(pendingHistLine)` (the same editor→preview bridge — deck branch advances the deck to the matching slide, scroll branch scrolls with the shared 25% top margin so the round-trip is stable) and re-stores the line on the (popstate-)replaced entry. No Rust change. `list` mode has no scroll target so restore is a no-op there. Sample: the リンク検証 slide in `samples/marp.md` (a cross-file link to click, then `Alt+←` back to confirm the slide is restored).
- **Drag & drop opening** — handled by a **wry file-drop handler** registered on the WebView via `WebViewBuilder::with_file_drop_handler` (`src/main.rs`). This is required because on Windows WebView2's own HTML5 drag-drop consumes file drops over the webview, so a JS `drop` event never carries a usable file path (`File.path` doesn't exist), and only folders — which HTML5 can't accept — used to bubble up to tao's `WindowEvent::DroppedFile`. wry's handler **revokes WebView2's drop target** (so the JS `handleDrop()` in `assets/index.html` no longer fires — it's now a no-op fallback) and hands the Rust host the dropped items' **real absolute paths**. On `FileDropEvent::Dropped`, paths are routed by preference **directory > markdown > image**: a folder dispatches `CustomEvent::OpenDirectory` (workspace mode); a `.md` / `.markdown` file dispatches `CustomEvent::OpenFile` — the *same* pipeline as double-click / CLI-arg / cross-file links — so the watcher, `current_dir` / `current_file` state, on-disk relative-image resolution (via `/userfile/`), and editor pairing are all set up identically (pressing `E` opens the companion editor); a single image dispatches `CustomEvent::OpenImage`, which points `current_dir` at the image's folder, clears `current_file`, and calls `window.loadImageFromRust(name)` to show it via the `/userfile/` route. The tao-level `WindowEvent::DroppedFile` arm is kept folder-only as a fallback for any drop that bypasses the webview handler. (Earlier, markdown drops were loaded entirely in JS via `FileReader`, which base64-inlined loose images dropped alongside the `.md` but couldn't learn the file's path — so `current_file` stayed unset and `E` failed with "no file is currently loaded".)
- **New file creation** (`Ctrl+N`) — a dedicated `Ctrl+N` keydown listener in `assets/index.html` (sibling to the `E`-key handler; `preventDefault()`s to suppress any WebView2 "new window" default) posts a payload-less `newfile:` IPC. The Rust handler (in the IPC chain next to `exporthtml:` in `src/main.rs`) runs an `rfd::FileDialog` Save dialog on a worker thread (same off-thread pattern as the export handlers), seeded with `untitled.md` and the current file's directory; on confirm it forces a `.md` extension if the chosen name lacks `md`/`markdown`, writes an **empty** file **only when the path doesn't already exist** (an existing target is opened *as-is* — never truncated, to avoid clobbering content via the dialog's overwrite prompt), then dispatches `CustomEvent::OpenFile(path)`. From there the standard `OpenFile` handler does everything else (watcher swap, `current_file`/`current_dir`, render, and — in workspace mode — the recursive watcher refreshes the tree + `__setActiveFile` highlight), so no new state model is introduced. The editor is *not* auto-spawned; press `E` to start writing.
- **Open install directory** (`Ctrl+D`) — a dedicated `Ctrl+D` keydown listener in `assets/index.html` (sibling to the `Ctrl+N` handler; requires ctrl/meta and not alt/shift, `preventDefault()`s to suppress the browser bookmark default) posts a payload-less `openinstalldir:` IPC. The Rust handler (in the IPC chain next to `fullscreen:toggle` in `src/main.rs`) spawns `explorer` on a worker thread pointed at an owned clone of `exe_dir` (`ipc_install_dir`, cloned before the `with_ipc_handler` move closure) — i.e. the folder holding the exe + `assets/`. No new state model.

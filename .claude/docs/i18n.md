## UI Language (日本語 / English)

Every user-visible string in **both** windows is localized. Default is **OS locale auto-detect**; an explicit choice overrides it and persists. Scope is app chrome only — the reader's document, `samples/`, filenames and Marp theme names are untouched. **No Rust change was needed.**

- **One shared key: `uiLang`, unprefixed.** The preview (`app://localhost/index.html`) and the editor (`app://localhost/editor.html`, `src/editor_registry.rs:256`) are the **same origin** in the same WebView2 user-data folder (no `WebContext` / `user_data_folder` is set anywhere in `src/`), so they **share localStorage**. One key is all the two windows need to agree — no IPC, no `push_ui_lang`. It deliberately breaks the editor's own `editor:*` convention because it is a *shared* pref, not an editor-scoped one.
- **The ABSENCE of the key is "auto".** There is no `'auto'` sentinel; "back to automatic" is `removeItem`, mirroring how `styleName` is cleared. The UI still shows three states, and `auto` is visually distinct from an explicit `ja` that happens to match the OS.
- **`__detectUiLang()` walks `navigator.languages`, not `navigator.language`** — someone whose Windows *display* language is English but whose preferred-language list leads with Japanese must get Japanese. `startsWith('ja-')`, never `startsWith('ja')`, so `jam` (Jamaican Creole) cannot match.
- **⚠️ Existing installs are pinned to Japanese.** Everyone predating this feature has been looking at a Japanese UI, so letting auto-detect apply to them would silently flip an existing install to English — exactly the wrong surprise for someone on English Windows who chose this app *because* it is Japanese-first. `__resolveInitialState()` therefore seeds `uiLang='ja'` when the key is absent **but any older pref key** (`darkMode` / `styleName` / `marpView` / …) is present. Auto-detect applies to genuinely new installs only. Structurally identical to the `styleName` migration already living beside it.

### The two tables

`assets/index.html` is an 11k-line monolith with one inline `<script>` and cannot `import`, so it carries its own table; the editor is an esbuild bundle and gets `tools/build-editor/i18n.js`. They are **mirror implementations** in the sense the repo already uses for `isParagraphLine` / `__isMdParagraphLine`, but the coupling is deliberately tiny:

- **Key spaces are disjoint by construction** — `i18n.js` owns `ed.*`, `index.html` owns everything else — so the *only* keys that must stay byte-identical are `common.*` (six of them).
- **Key-major, not language-major** (`{'help.title': {ja, en}}`, not `{ja: {...}, en: {...}}`). A 250-string change is reviewed for its **copy**, and this shape puts each pair on adjacent lines, so an `en` cannot be added without seeing the `ja` beside it.
- `t(key, params)` falls back `uiLang → ja → the key itself`, so a missing translation renders as `toast.marpView` on screen — loud in dev, never blank. The **`if (params)` guard is load-bearing**: `t()` is called per node while rendering the table / copy buttons, so the no-params path must stay a bare object lookup with no regex.
- Named `{placeholder}` substitution only, never positional — ja and en reorder constituents. The rule is **translate the fragment, then interpolate the translated fragment**; never concatenate a raw internal key. `bindBodyClassToggle`'s 4th argument became a *message key* rather than a string, which fixed its three call sites without changing the helper's shape.
- Both tables are exposed as `window.__I18N` / `window.__editorI18n` for the harness.

### `data-i18n`, and the ordering trap

Static markup carries `data-i18n` (textContent), `data-i18n-html` (innerHTML — fed **only** from the constant table; never a filename or a `@user-vars` label) and `data-i18n-attr="title:k;aria-label:k"`. A single `applyI18n(root)` pass rewrites them and sets `document.documentElement.lang` (which drives CJK line breaking and font fallback — not cosmetic in an app shipping vertical-writing themes).

The help table's 21 rows stay **static HTML** rather than becoming JS-generated: it is the app's primary documentation surface and is readable as a table in the source, the key cells are `<kbd>` markup, and rows 11101/11106 mix Japanese *inside* the key cell — which needs the HTML-valued path anyway.

**The key column is a fixed 200px, and a multi-key row must wrap each combination in `<span class="kc">`.** Before this the column was `white-space: nowrap; width: 1%`, so the single widest row (`←` / `→` / `PgUp` / `PgDn` / `Home` / `End`, ~300px) set the width for all 21 rows and left the description column about 150px inside the 520px panel — every long description wrapped to four or five lines, and English runs 2–3× the Japanese character count. Now the panel is 680px (`#help-modal .panel` overrides the width it otherwise shares with `#style-modal`), the key column is a fixed 200px so every row's descriptions start at the same x, and the cell wraps at the separators. Three details are load-bearing: `#help-modal table { table-layout: fixed }` is what makes the 200px authoritative (under auto layout a declared width is only a suggestion and the key column's max-content wins) and must **not** be added to the rule shared with `#style-modal`, whose columns are content-sized on purpose; `.kc` carries the `nowrap` so a combination like `Ctrl`+`N` is never split across lines; and the ` /` separator lives **inside** the preceding `.kc`, so a wrap puts the slash at the end of a line rather than orphaning it at the start of the next. The two `data-i18n-html` key cells carry the same `.kc` markup in both languages. Measured after the change: every description is ≤ 2 lines in ja and en, and only the zoom and slide-navigation rows wrap, to exactly 2 lines. A narrower window (the panel clamps at `100vw - 40px`) degrades to 3 lines for the longest English rows, which is accepted. Regression net: no harness asserts the geometry — re-measure with the snippet in *Browser preview harness* if you add a row.

**⚠️ `applyI18n` must be called on `DOMContentLoaded`, not only from the inline script.** That script sits at the top of `<body>`; `#help-modal` / `#style-modal` / `#update-banner` are parsed **after** it and do not exist yet (this is why `__helpModal()` resolves lazily). Calling it once early *looks* like it works — the splash and drop zone do translate — while silently no-opping on every modal. It is idempotent, so the three call sites (early, DOMContentLoaded, `setUiLang`) are free.

### Live switching

`setUiLang(pref, persist)` mirrors `applyDarkMode()`. Beyond `applyI18n` it must do three things, each of which is a silent bug if skipped:

1. **`MARP_VIEW_LABELS` became `__marpViewLabel(v)`.** A `const` map captured at boot freezes the language. Same reason the two `__TIKZ_*_HTML` constants became `__tikzErrorHtml(key)`.
2. **`__styleVarSpecCache.clear()`** — it memoizes *normalized* `@user-vars` specs, which carry localized labels. Symptom of forgetting: "style settings labels don't change until restart".
3. **An anchored `#preview` re-render.** `#preview` carries localized output — the markwhen calendar, the renderer error blocks, the table hover/copy buttons — so the chrome pass alone is not enough. Re-render + `restorePreviewAnchor()`, mirroring `__schedulePaginateRefresh()`.

**Diagram caches**: markwhen bakes localized month / weekday text into its SVG string, so **both** `__markwhenCache` and `__markwhenCalCache` keys carry `uiLang`. mermaid / abc / tikz need no such salt — none of them bake UI text.

**Cross-window sync is zero-Rust**: a `storage` listener (fires only in *other* documents, so no loop; still passes `persist=false` so a future broadcast cannot ping-pong) plus a `focus` re-read as belt-and-braces — the same shape `clipboardSync.js:162` already uses for the OS clipboard.

### The editor, and why no mount refactor was needed

**Every editor modal and the status bar assign `innerHTML` exactly once at boot** (`entry.js` ~236 / ~280 / ~321 / ~374 / ~414, status bar 162-216); only the char-count `tbody` is rebuilt per open. So "apply on next open" would not work either — the DOM already exists with stale text — and the obvious alternative was a mount refactor, made expensive by `settingsCtl` caching element references and binding listeners in a separate block.

Using the **same `data-i18n` + `applyI18n` pass** avoids both: it rewrites only text and attributes, **never structure**, so every cached reference and every `<select>` value survives. `relabelChrome()` (applyI18n + `updateMarpButtons` + `updateStatus`) is called at boot and from the language setter, and switching is genuinely live.

The language row is the first row of the settings modal's `表示` section and follows `setKeyLayout`'s shape exactly (validate → persist → apply → `updateSettingsUI()` → hint suppressed while the modal is up → `refocusEditor()`).

`CELL_HELP` (`cells.js`) became `[keys, i18nKey]`. It is **display-only** — it feeds the help modal and nothing else; the keymap is separate switch logic in `cellGate()` — so localizing a description can never affect a binding. `FONT_FAMILIES` / `KEY_LAYOUTS` gained `labelKey` in place of `label`.

### Theme `@user-vars` labels

A declaration MAY carry optional **`labelEn` / `labelJa`** beside `label` (and on each `options[]` entry), plus **`unitEn` / `unitJa`** beside `unit`; absent ones fall back to the base key, so no existing or third-party style is affected (unknown keys were always ignored). `__styleVarLabel(obj, base)` picks at **render time** in `__buildStyleVarRow` — never in `__normalizeStyleVarSpec`, because `__styleVarSpecCache` memoizes the normalized spec and baking the language in at parse time serves stale labels after a switch.

- **⚠️ `unitEn` / `unitJa` are honoured for `type: "number"` ONLY.** A `number` unit is a display-only suffix (字 / 行 / 倍), but a `length` unit is interpolated into the emitted CSS value and validated against `/^(%|[a-z]{1,4})$/` — a translated one there would write `39chars` into the stylesheet.
- **⚠️ The `/* @user-vars … */` comment body is `JSON.parse`d whole.** Prose inside the same comment breaks the entire declaration (the style then silently shows no ⚙). Notes go in a separate comment above it — both bundled themes now carry one.
- `tategaki.css`'s `--confidential-label: "社外秘"` is **out of scope**: it is a watermark stamped on the *reader's document* and flows into exports, not UI chrome.

### Export

The artifact inherits the **exporting** UI's language, deliberately — the same choice already made for the user stylesheet and the `wide` / `confidential` body classes. `buildExportArtifact()` clones the live `#toc-sidebar`, so `Files` / `Contents` / the toggle `title` come out already translated with no special handling. Two riders: the artifact's `<html lang>` now follows `uiLang` (it was a fixed `en`, wrong for every Japanese export to date), and `'Plotly init failed: '` lives **inside** the `tocScript` template literal that is shipped into the artifact — it cannot call `t()` at view time, so it is baked in with `${JSON.stringify(t('err.plotlyInit'))}`. The artifact is a frozen snapshot and carries no `uiLang` reader.

### ⚠️ DO NOT TRANSLATE

Pinned at the top of both tables, because the next person auditing will re-derive it wrongly:

- `RUBY_KANJI_SRC` (`assets/index.html`) and `allow_re` (`src/main.rs:752`) — regex character classes.
- `stack` in `tools/build-editor/editorPrefs.js` — real font names (`BIZ UDゴシック`); translating one makes font selection fail silently.
- `--confidential-label` in `assets/tategaki.css` — document content.
- `SLIDE_CLASSES` (`marpSlides.js`) / `TABLE_ALIGNS` (`mdTable.js`) — identifiers used as data.
- Internal keys generally: localStorage values (`marpView` = `scroll|deck|list`), CSS class names, `dataset.style`, and the editor's `data-el` / `data-val` / `data-seg` values. `t('marp.view.' + v)` is the safe pattern; never build a reverse lookup keyed by a *label*.
- Vim's own errors (`E492: Not an editor command`) come from `@replit/codemirror-vim` and are out of reach without patching the dependency; only the app's own ex-command errors are localized.

### Tests

`tools/preview-harness/i18ncheck.py` (new) reads both tables out of the **live** pages and asserts: every message has a non-empty `ja` and `en`; placeholders agree across variants (a message whose languages legitimately reorder — the calendar month title — declares `params` and is checked as a subset instead); `common.*` is byte-identical across the two; and the namespaces do not otherwise collide.

Harnesses that assert on UI text now pin the language, because auto-detect would otherwise make them pass in Japan and fail on an en-US machine — `shoot.ui_lang_init_script(lang)` sits beside `style_init_script`, and contexts set `locale=` so `navigator.languages` is deterministic too. `keycheck.py` reads its expected copy out of `window.__I18N`, so it asserts the *wiring* rather than the *wording*; `tablecheck.py` pins `en` (its context-menu assertions were authored against the English labels); `domdump.py` gained `--lang` (default `ja`) because the table Copy/Edit buttons are now language-dependent.

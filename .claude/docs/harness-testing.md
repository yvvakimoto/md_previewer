## Browser preview harness for AI iteration (`tools/preview-harness/`)

A **fast, build-free feedback loop** so an AI agent (or a human) can open the *whole* previewer UI in a browser and inspect what it renders — **without any `cargo build`**. This is the complement to `--export-png`: the harness is for quick iteration on rendering/styling/layout; `--export-png` remains the highest-fidelity, actual-WebView2-binary path (use it — especially for final Marp deck layout — when byte-exact rendering matters).

- **`tools/preview-harness/serve.py`** — a single-file **stdlib-only** Python `ThreadingHTTPServer` (no pip deps) run from the repo root. It serves the **real** `assets/index.html` and reproduces, at serve time, the three things the Rust+WebView2 host normally does so the page boots unchanged:
  1. **Injects a bootstrap `<script>` right after `<head>`** (the on-disk `index.html` is never modified) that sets the host globals — `window.__appVersion` (read from `Cargo.toml`), `window.__userStyles` (scan `assets/*.css` minus `editor.css`), `window.__marpThemes` (scan `assets/marp/*.css`), `window.__styleExporters = {}` — matching Rust's init-script (the `window.__appVersion = …` block in `src/main.rs`), and installs a **logging IPC shim** (`window.ipc.postMessage = m => console.debug('[ipc]', m)`) so the guarded IPC flows become visible no-ops instead of throwing. `window.__captureConfig` is deliberately **not** set, so the `--export-png` capture path never triggers.
  2. **Auto-loads a document from a `?file=<ABS>` query param**: the bootstrap polls for `window.loadFileFromRust` (mirroring Rust's 100 ms retry), `fetch`es the raw markdown from **`/__doc?path=<ABS>`**, and calls `loadFileFromRust({ filename, filepath, content, raw })` — the same entry point Rust uses (`window.loadFileFromRust` in `assets/index.html`; `struct FileData` in `src/main.rs`, where `content === raw === source text`). With no `?file=` the app just shows its normal drop zone.
  3. **Serves local images / CSV / video through `/userfile/<path>`** exactly like Rust's route (the `/userfile/` branch of the `with_custom_protocol("app")` handler in `src/main.rs`): resolves relative paths against the current document's directory (component-walking `..`/`.`), passes absolute `/userfile/C:/…` paths through, sets the right MIME (incl. `csv`/`tsv`/`md`/`mov`/`m4v`/`webm`/`ogv`), and honors HTTP **`Range` → 206** so video scrubbing works. The doc's directory (the `/userfile/` base) is set from the `?file=`/`/__doc` path — **one document at a time**; to view another, navigate a new `?file=` URL. `/__log/…` returns 200 to swallow the preview's forensic logging fetches.
- **Launch config** — `.claude/launch.json` has a `preview-harness` entry (`python tools/preview-harness/serve.py --port 8770`). Start it (in the Browser pane: `preview_start {name:"preview-harness"}`), then open `http://localhost:8770/index.html?file=<ABSOLUTE .md path>`. See `tools/preview-harness/README.md`.
- **Intentional no-ops under the harness** (each just logs an `[ipc]` line; there is no Rust host): the companion editor (`E`) — *from the preview*; `cellcheck.py` drives `editor.html` directly instead, see below — save, HTML/PDF export (`X`), headless PNG capture, and cross-file `openmd:` navigation — to open another file use a new `?file=` URL. Everything *rendering-related* is fully live: Marp, themes/dark mode, mermaid, KaTeX, csv/tsv, plotly, abc, markwhen, footnotes, alignment/columns, inline styled spans, image sizing, video/YouTube embeds.
- **How the agent "sees" it** — `read_page` (rendered text/structure/attributes), `javascript_tool` (computed CSS, element geometry, and app state such as `window.__marpFitReport` = per-slide overflow/scale metrics, the same numbers `--export-png` writes to `layout.json`), `read_console_messages`, and `read_network_requests` (confirm `/userfile/` 200s). **Note:** in some environments the Browser pane's `computer {action:"screenshot"}` times out; the readers above are the reliable inspection surface, and `tools/preview-harness/shoot.py` (below) or `--export-png` is the fallback when actual pixels are required.
- **`tools/preview-harness/shoot.py`** — **actual-pixel capture** driven by Playwright + a system Chromium (Edge/Chrome, launched via `--channel` so no `playwright install` is needed). It starts the harness server in-process, loads the doc in a **real headless browser** (so fonts / `/userfile/` images / KaTeX / mermaid / Marp autofit all paint correctly — unlike a hidden WebView2 window or a `<img>`-rendered SVG), waits for async figures to settle, and writes PNG file(s) an agent can `Read`: `slide-NN.png` per (selected) slide **+ `layout.json`** for Marp, or `page.png` for a normal doc. For normal docs it first neutralizes the `#preview` overflow clip so nothing is cut off (the same clip that caused the old `--export-png` blank tail). Usage: `python tools/preview-harness/shoot.py <file.md> [--out DIR] [--slides 1,3,5-7] [--scale 2] [--channel msedge|chrome] [--full]`. This is the reliable pixel path when `computer {action:"screenshot"}` is unavailable; `--export-png` remains the byte-exact actual-WebView2-binary path.
- **`tools/preview-harness/cellcheck.py`** — the same harness pointed at the **editor** window (`assets/editor.html` + the `editor.iife.js` bundle) instead of the preview, standing in for the Rust host with an injected `window.__initialFile` and a recording `ipc` shim. It exists because the cell-mode facts that matter most are invisible to a unit test: whether the `Prec.highest` DOM keydown gate still precedes `@replit/codemirror-vim` (a dependency bump can invert that with no compile error), whether each cell op is exactly one undo step, whether the decorations / cell gutter / Command-mode caret-hiding actually compute, and whether each cell's "run" line equals the `data-line` the preview stamped on the matching slide (it opens `index.html` in a second page to compare). Note `add_init_script` takes a *script body*, so the injected globals must be an IIFE — a bare `() => {…}` is evaluated and discarded, which silently boots the editor with an empty document. Usage: `python tools/preview-harness/cellcheck.py [--channel msedge|chrome]`.
- **`tools/preview-harness/prefscheck.py`** — the same shape, for the editor's font zoom and settings modal. Beyond the assertions listed under *Tools* above, two harness mechanics are worth knowing before extending it: `add_init_script` calls **accumulate** and all of them re-run on every navigation in the order added, so the reset of a pref in an earlier script would wipe the value a later `page.reload()` is meant to read back — the persistence case therefore boots a **second page in the same context** (same origin, so it shares `localStorage`, but it carries only its own init script). And a focus assertion must use a real `page.click()`, since Chromium does not move focus on a programmatic `element.click()`. Usage: `python tools/preview-harness/prefscheck.py [--channel msedge|chrome]`.
- An earlier narrow markwhen unit harness (`assets/__cal_*`, loaded via the separate `assets-static` launch config) has been **deleted** — this full-UI harness replaces it. The `assets-static` launch config remains but now only serves `assets/` statically.

- `tools/preview-harness/serve.py` — stdlib-only static server that serves the real `assets/index.html` for build-free browser-pane inspection of the rendered UI. `tools/preview-harness/shoot.py` (Playwright + system Chromium) renders a doc in that harness and writes PNG file(s) an agent can `Read`; both it and `domdump.py` take **`--style NAME`** (an `add_init_script` setting `localStorage.styleName`), which is the only way to reach `bunko.css` / `tategaki.css` from a harness run — before that flag the two themes this project's vertical-writing work targets had no pixel or structural regression coverage at all. Both also share `shoot.wait_for_render()`, whose `_FIGURES_READY_JS` predicate is what stops a capture from snapshotting a half-rendered page — so a new async figure kind must be added there or its output is silently missing from every shot and digest. The **tikz** arm mirrors `__tikzAwait`'s `done()` rather than testing for a bare `<svg>`: while compiling, tikzjax parks an `<svg class="tikzjax-loader">` spinner inside a `.tikzjax-wrapper.tikzjax-loading`, so the obvious predicate is satisfied by the *unfinished* state (this is exactly how a baseline full of `tikzjax-loading` markers got recorded). Keying off the wrapper losing `tikzjax-loading` also resolves a **failed** compile immediately (broken-image placeholder, no svg). Because tikz is deliberately fire-and-forget and index.html waits 30s before swapping in a `.tikz-error`, a page carrying tikz blocks gets its own `_TIKZ_WAIT_MS` budget instead of the 20s page default. The **kataskeve** arms are the straightforward form — no loading placeholder exists to be mistaken for a finished render, and both engines are synchronous and awaited, so neither needs its own budget — but note the 3D arm tests for a **`canvas`**, not an `svg`, since kataskeve3d never emits one. **`domdump.py`** writes a normalized, diffable digest of the `#preview` tree — the regression net for render-pipeline refactors (`gate.sh <label> <files…>` re-dumps a subset and diffs it against `_dom/base`). `keycheck.py` also covers the Marp colour themes' ⚙ (gear on every family row, the one-control pane, a picked colour re-deriving `--accent` / `--rule` / the `::: message` border at the designed lightness with no re-render, persistence under `styleVars:marp/<file>`, the export carrying the override, reset). Note the digest records the text of `#preview > style#marp-style` (hashed), so **any** edit to a Marp theme CSS produces exactly one DIFF line per `samples/marp.md` digest even when nothing visible changed — confirm that is the only differing line, then re-baseline. **`keycheck.py`** drives real keydown / right-click events and asserts each shortcut's and context menu's observable effect, plus the autofit invariant that no shrunk-to-fit `.marp-fit-body` keeps a scrollbar (while a slide floored at the 0.5 minimum, and an overflowing body with autofit off, both still scroll) — the DOM digest records the wrapper's inline px but cannot see whether they actually hold the content — the diagram cache's dark↔light round trip, and the `@user-vars` settings pane (that a ⚙ appears on exactly the styles declaring one, that a slider retunes the live 版面 with no re-render, and that 既定に戻す restores the CSS default) — behavior the DOM digest cannot see. **`tablecheck.py`** does the same for the preview's table edit mode and asserts the exact `savefile:` payload (the harness's IPC shim makes the source round trip verifiable with no Rust host), and **`table-model.test.cjs`** tests that table model layer under plain `node` (idempotency of `tblEmit(tblParse(x))`); **`ruby-model.test.cjs`** does the same for the ruby grammar, pinning the three views built from the single `RUBY_ALT_SRC` alternation — above all that `start()` reports the offset of the **base**, since an offset pointing at `《` makes marked emit the base twice. **`i18ncheck.py`** checks the two UI-language string tables (see *UI Language → Tests* (`i18n.md`)) — it reads both out of the live pages, so it also proves the shipped editor bundle matches its source. **`pastecheck.py`** covers the editor's Office-table paste conversion — the DOM half that `tablePaste.test.mjs` cannot reach (real Excel/Word clipboard-HTML fixtures, `Prec` ordering vs. `pasteURLAsLink`, Vim INSERT/NORMAL, single-step undo, and a real-clipboard + real-`Ctrl+V` case confirming the `text/html` flavour actually arrives). **`exportcheck.py`** is the same idea for the `X` → **HTML** path: it builds the artifact in the live page, serves it back through Playwright request interception (nothing touches disk) and asserts that the reloaded artifact *renders* the same as the preview — writing mode, font, 行送り, 版面 height, page count, ノンブル, and the ruby annotation's size / position / line-box offset — under `bunko.css` / `tategaki.css` / `parchment.css` / no style. Its vertical fixture deliberately carries ruby: `<ruby>` is the one inline element whose annotation reserves space outside the line box, so it is the likeliest thing to make an exported bunko artifact paginate differently from the preview it was built from. Loading it back is the whole point: everything it catches produces valid HTML that merely renders differently, which is how the unresolved `@import` above shipped a horizontal bunko export for as long as it did. **`pdfcheck.py`** covers the `X` → PDF path without the native Save dialog (including the vertical-writing A4-landscape cases, whose text-completeness assertion is what catches a regression back to the silently-truncating orthogonal-flow behaviour): it drives the real `__beforePdfPrint()` handshake, reads the `pdfprintready:` ack out of the harness's IPC shim, feeds it through a **mirror of `src/pdf_win.rs`'s `print_params()`** into CDP `Page.printToPDF`, and asserts the resulting file with pymupdf — one page per slide **from all three view modes**, the page equal to the slide box (16:9 → 960×540pt, 4:3 → 720×540pt), a full-bleed background reaching all four corners (i.e. zero margins), an unchanged A4 + bookmarks for a non-Marp document, and that `__afterPdfPrint()` restores the view. **`cellcheck.py`** is the same idea for the *editor* window — it serves `assets/editor.html` and stands in for the Rust host with an injected `__initialFile` + `ipc` shim, then asserts the cell-mode behaviour a unit test cannot see: that the `Prec.highest` key gate really precedes `@replit/codemirror-vim` (with Vim ON, `Esc` then `j` must move by CELL), that every op is one undo step, that the decorations/gutter/caret-hiding actually compute, and that each cell's run line equals its slide's `data-line`. **`synccheck.py`** covers editor↔preview position sync on **both scroll axes** — that `applyEditorScroll()` actually moves the preview under `bunko.css` / `tategaki.css` (where it was a silent no-op), that it lands the target block ~25% in from the reading-start edge, that `currentPreviewLine()` round-trips it, and that stepping the cursor line by line moves the preview **monotonically** (the net for the interpolation-sign bug above); the DOM digest cannot see any of this, since the markup is identical either way and only the scroll offsets differ. **`prefscheck.py`** covers the editor's font zoom and settings modal: that `Ctrl+=` survives `@replit/codemirror-vim`'s non-insert key swallowing, that `Ctrl+Shift+-` still splits a cell (the one-modifier-away collision), that the gutter scales while the status bar does not, that a size round-trips through `localStorage` on a fresh boot and a corrupt stored value falls back, and that the modal's setters do not yank focus back into the editor. **`dvorakcheck.py`** covers the Vim Dvorak→QWERTY layout translation: that a real `page.keyboard.press('h')` (which is exactly what a Dvorak emulator emits, since `langmap` reads only `e.key`) drives `j`, and — the cases that separate `langmap` from a `Vim.map`-per-letter implementation, which passes every unit test and fails these — that multi-key sequences (`gg`, `[[`), operator-pending motions (`dd`, `dw`) and counts (`3j`) still work, that `f`'s argument stays literal, and that insert mode / the ex line / the default `qwerty` layout are untouched. See *Browser preview harness for AI iteration*.

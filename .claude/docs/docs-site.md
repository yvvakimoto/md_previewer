### GitHub Pages landing page (`docs/`)

The public introduction page, served by GitHub Pages from **`main` + `/docs`** (Settings → Pages → Deploy from a branch). Plain HTML + CSS + one small script — no framework and no build step, because the product's own pitch is "no CDN, everything bundled" and a landing page that needs a toolchain to rebuild contradicts it.

- `docs/index.html` / `docs/assets/style.css` / `docs/assets/site.js` / `docs/.nojekyll` / `docs/assets/favicon.ico` (a copy of `assets/icon.ico`) / `docs/assets/img/**` (generated — see `shoot-docs.py` above).
- **Structure** — hero, three steps, **five personas** (read / Marp / math / 縦書き文庫 / Vim+Dvorak), a feature grid, a **gallery**, a **keyboard-shortcut reference** (`#keys`), and download. The shortcut section sits *after* the gallery because it is neither argument nor proof but the control surface: the page runs why → what → proof → **how you drive it** → act, and reference material lands best between the proof and the CTA. It is also the one section a returning reader comes back *for*. The personas are the page's spine: the product's differentiator is the *combination* nobody else carries, not the feature count.
- **The gallery pairs each notation's source with a picture of it rendered**, and `GALLERY` in `shoot-docs.py` is the **single source of truth for both**: the script renders each snippet through the real pipeline, screenshots the one figure, and `check_gallery_sources()` then warns if `docs/index.html` no longer carries that exact snippet (HTML-escaped) in its `<pre>`. So the code shown and the picture beside it cannot drift apart silently — it already caught a bare `&` in the tikz-cd block that should have been `&amp;`. Three things this depends on:
  - **The fixture is written into `samples/`**, not a temp dir, because a snippet may reference a sibling resource the way a real document would (the plotly block reads `data/sales.csv`). It is removed in a `finally`.
  - **`trim_to_ink()` crops each shot to its drawn content.** The captured element is a block, so it spans the whole text column however small the figure is — display math and a commutative square both came out as 1360px-wide strips of empty paper, and the delivered aspect ratio is what the gallery grid places cards by.
  - **⚠ `model3d` is the one gallery card whose picture MOVES, and `shoot_gallery()` skips it.** It ships as a looping animated WebP (`model3d-spin.webp`) with the ordinary still (`model3d.webp`) behind `<picture><source media="(prefers-reduced-motion: reduce)">`, and **`shoot_spin_model3d()` emits BOTH files from one capture** — cropped to the **union ink box across every frame**, not to each frame's own `trim_to_ink()` (a per-frame crop makes the figure jitter inside the loop). Letting `--only gallery` re-shoot it would hand the still a tighter crop than the animation: the `<picture>` swap would then jump and `--g-cap` / `width` / `height` would go stale. `--only gallery:model3d` overrides the skip if you ever want the plain still back. `GALLERY` still owns the snippet, and the spin pass reads it from there rather than keeping a second copy, so `check_gallery_sources()` is unaffected.
  - **Card order is load-bearing.** Two constraints at once. Editorially the run goes general-purpose and humanities first (ruby, tables, columns, staff notation, timelines) and the sciences in the back half (math, tikz-cd, kataskeve 2D/3D, Feynman), so a reader who does not write formulas is not met with them. Mechanically a `span 12` card between two `span 6` cards leaves the first of them alone on its row, so the half-width cards are ordered to pair up (ruby+csv, mermaid+plotly, math+tikzcd, kataskeve+kataskeve3d) with the full-width ones (columns, abc, markwhen timeline, markwhen calendar, feynman) between them.
  - **A figure's DISPLAY width is `--g-cap`, not its `width` attribute.** The shots are `device_scale_factor=2`, so the intrinsic size is twice what the app drew — and `.g-card:not(.g-12) .g-out img { width: auto }` hands that intrinsic size straight back, overriding the attribute, which is why every small figure in a half-width card silently rendered at exactly 2× and its text came out roughly twice the page's 16px body copy. The attributes stay at the file's pixel size (intrinsic size / aspect-ratio / no layout shift); the cap is a CSS custom property consumed by `.g-out img { max-width: min(100%, var(--g-cap, 100%)) }`, set per `<img>` to `(file px / 2) * min(1, 16 / <the figure's own text size in the app>)` — 1:1 with the app, shrunk further only where the figure sets its own type larger than body copy (display math 17.6px, tikz-cd 21.3px = TeX 10pt × the previewer's 1.6 default, feynmark's KaTeX labels 16.5px). A heading *inside* a figure (abc's tune title, markwhen's title) is meant to be larger and forces no reduction; a cap wider than its panel is clamped by `max-width: 100%`, so only the small figures are affected. **Measure that text size, don't guess it**: an SVG `<text>` reports `font-size` in user units (tikz says `10`, kataskeve `0.34`), so it has to be multiplied by `getScreenCTM().a` to become CSS px.
  - **An animation's own pixel size does not have to match its still's** — the `width`/`height` attributes give the layout box and `--g-cap` clamps the display width, so a lower-resolution source just renders at lower density. Both animations are emitted at **exactly half** the 2× capture (motion masks the softness; it is by far the biggest byte lever). *Exactly* half is the rule, not roughly: the two files must agree on aspect ratio to the pixel or the `<picture>` swap shifts the layout, which is why `union_ink_box()` and `_to_even()` force both extents even. `model3d` came out 1008×510 still / 504×255 animation, so its `--g-cap: 504px` was unchanged by the move.
  - **The columns card shoots `#preview`, not `.inline-cols`.** The point of the fenced div is that a document *drops into* columns and *comes back out*, which a shot of the region alone cannot show — so its snippet is a whole little document (a paragraph, a two-column region quoting the Aeneid in Latin beside its Japanese translation, another paragraph) and `trim_to_ink` crops the paper away. It is the one gallery entry whose selector is the whole preview column, and it is `g-12` for the room.
  - **The markwhen calendar card carries `country: JP`**, so its picture shows a public holiday — and those come from an **online** lookup (nager.at) that the app deliberately swallows on failure. Regenerating the gallery without a network therefore produces a valid but holiday-less calendar; the note under the grid says so in both languages, so don't "fix" the difference.
- **The shortcut section republishes the app's own list, and is machine-checked against it.** The `<table>` inside `#help-modal` in `assets/index.html` is the **single source of truth** for the first three groups; `tools/preview-harness/docskeycheck.py` pairs the two **by i18n-key suffix, not by position** (`keys.h` ↔ `help.key.h`), because the page regroups the modal's 21 rows into three editorial groups — the window / open+export / Marp — and so legitimately reorders them; a positional compare would fail on day one for a reason that is a feature. A **key-cap** mismatch, or a shortcut present on one side only, **fails**; a **description** mismatch only **warns**, since the app's wording can be edited by a commit that has no business touching `docs/`. `ADAPTED = {"h", "esc"}` names the only two descriptions the page rewords, because 「このヘルプ」/「このダイアログ」 name the modal they live in and mean nothing on a web page — and the checker also warns if the *app's* string for one of those moves on. The editor group has no counterpart in the modal and is excluded by `data-sc-scope="editor"`; **a `.sc-group` with no `data-sc-scope` is an error**, so the exclusion is fail-closed and a fifth group can neither drag editor rows into the comparison nor dodge it. ⚠️ **Do not re-space the reused app strings** — the app writes 「Marpモード」/「Marp表示」 with no space while this page's own copy writes 「Marp スライド」; the description compare is literal after collapsing whitespace, and a space between CJK and Latin does not collapse, so a cosmetic re-space is 19 permanent warnings. Section furniture uses the page's voice; the reused rows keep the app's.
- **Three surfaces carry the shortcut list, in this order of authority**: the app's help modal (source of truth — **edit it first**), `README.md` (exhaustive: cell mode, Vim, ex commands), and this landing page (a curated subset, checked against the modal). This is what stops the next editor from "fixing" the page and leaving the modal behind, and it is what made `Space` the right call — `Space` advances a Marp deck (`assets/index.html`'s `e.key === ' '` branch) and `README.md` already listed it, so the modal was the lone stale surface and was corrected rather than the page bent to match it. Publishing a knowingly incomplete list to keep a consistency checker quiet is the wrong direction for a checker to push a codebase. Adding it pushed the key cell to a **third** line with `End` orphaned alone on it (greedy wrapping fits ~3 caps per 200px line, so reordering cannot help), so the row was **split in two** — `←` / `→` / `PgUp` / `PgDn` / `Space` (`help.key.slideNav`, now reworded to 前 / 次のスライド) and `Home` / `End` (the new `help.key.slideEnds`) — which is the split `README.md`'s Marp table already used. The table is therefore **21 rows**, and measured after the change the documented geometry still holds exactly: only the zoom and slide-navigation cells wrap, to two lines each, and every description is ≤ 2 lines.
- **`.sec-head` has no width cap, deliberately.** It used to be `max-width: 720px` inside a ~1050px column, which wrapped each one-sentence section lead about a third of the way from the right edge — with obvious empty space beside it, that reads as an intentional line break rather than a wrap. The leads are now sized to fit the column on one line in **both** languages (the Japanese feature lead had to be shortened by a few characters to make that true); re-measure with the snippet below if you edit one. `.sec-title` keeps a `22em` cap so a future long title still breaks sensibly.
- **The shortcut list is a CSS-grid `<dl>`, deliberately NOT a `<table>`.** The page has no table styles and no `<table>` at all, so one would mean introducing `table` / `th` / `td` / `table-layout` rules that apply to a single element and then sit there as a trap. More decisively it could not survive 390px: a table's columns are content-driven, `table-layout: fixed` is then required (the app's own CSS comment records the max-content fight that forces it), and a fixed key column leaves a 60-character Japanese description ~150px. `.sc-row` is instead a two-track grid that **collapses to one track below 700px** (caps above their description), so the section contains no scrollable box at all. The key track is `minmax(0, 200px)` — 200px to match the modal's own column width, `minmax(0, …)` for the same `min-width: auto` reason as `.g-src`; it deliberately does **not** fit the widest cap run (the 5-cap slide-nav row wants ~275px), which wraps at the separators exactly as it does in the modal. At ≥700px the caps are **right-aligned**, again matching the modal: twenty of the 30 rows are a single cap, and left-aligning them opens a ~190px river between the key and the sentence explaining it.
- **Grid and flex tracks here need explicit `minmax(0, 1fr)` / `min-width: 0`.** A track's default `min-width: auto` is its *content* width, so a long line inside a `.g-src` widened the single-column gallery track past the viewport instead of scrolling inside its own `<pre>` — `body { overflow-x: hidden }` hid it on screen, and only a full-page capture coming out 457px wide at a 390px viewport surfaced it. Assert `document.body.scrollWidth <= clientWidth` **and** that every overflowing element sits inside a scrollable ancestor that itself fits.
- **The feature grid credits upstream.** Fifteen of its twenty-four tiles are the bundled OSS engines (`.feat-ext`): each is a **link to the upstream project** carrying its SPDX licence (`MIT` / `BSD-3-Clause` / `GPL-3.0`), and the note under the grid points at the app's own Third-party licenses panel. The other nine (`.feat-own`) are this project's own work and are labelled 本体実装 rather than linked. Keep the total a multiple of four — the grid lands on four columns at desktop width, so an off-count leaves an orphan row. When a bundled library is added, upgraded or dropped, this grid is a second place to update alongside `THIRD_PARTY_LICENSES.txt`. The tile is made clickable by a **stretched link** (`.feat-ext > a::after { inset: 0 }`) so the anchor text stays one word for a screen reader while the whole card behaves as one target.
- **There is deliberately NO comparison-with-other-tools section.** One was written and then removed: a table of what VS Code / Obsidian / Typora do goes stale without anyone noticing (Typora, for instance, *does* associate `.md` at install time, which the first draft got wrong), and a landing page cannot be the place that tracks three other products' feature sets. The README keeps its comparison table — that one at least sits next to the code and is reviewed with it. If a section like this is ever reinstated here, the maintenance cost is the reason it was dropped.
- **Naming** — the page is the one surface carrying **"for Windows"**. `installer/md-previewer.iss`'s `AppName` stays `MD Previewer`: inside Windows itself — Start menu, uninstall list — "for Windows" is tautological. The suffix exists for discovery, where "MD Previewer" alone is a very crowded name (76 GitHub repos, plus MDViewer / MarkdownView / MDHero on the Store), so it also does real work as a search disambiguator. `md-previewer.exe`, the AppId, the ProgID and the registry keys are untouched, so existing installs upgrade in place.
- **i18n** — same convention as the app (`data-i18n` / `data-i18n-html` / `data-i18n-attr`, one `applyI18n()`, a **key-major** table so a message and its translation sit on adjacent lines), and it reads the **same `uiLang` localStorage key**. The `keys.*` namespace deliberately reuses the app's own `help.key.*` suffixes so the two tables can be paired mechanically rather than by text, and **19 of the 21 preview descriptions are byte-for-byte copies** of the app's ja *and* en — the translations were already written there. **Key caps are hand-written in the HTML**, not translated: a key name is what is printed on the key. Only the two cells that mix a key with a *word* (`Ctrl`+クリック/Click, ドラッグ/Drag) go through i18n, mirroring the app's own 18/2 split — and because both sides then carry the same literal markup shape (the ` /` separator inside the nowrap span), the drift checker compares them as plain strings instead of normalising each side separately. Two details are load-bearing: `promoteHtmlKeys()` moves any key whose text contains markup onto the innerHTML path at boot, so the markup does not have to be duplicated as a second attribute in the HTML; and `detectLang()` matches `ja-` with a hyphen, never a bare `ja` prefix (`jam` is Jamaican Creole) — the same rule as `__detectUiLang()`.
- **⚠ Avoid rare kanji in page copy.** Google Fonts serves Zen Kaku Gothic New as unicode-range subsets and **梱** is not in them, so 「同梱」 rendered two glyphs in a fallback face mid-sentence. Wording was changed to 「本体に入っています」/「付属テーマ」/「収録ライブラリ」. If a new string looks subtly off-weight, suspect this first.
- **⚠ `<kbd>`'s fill is `--paper-2`, which collides with any `--paper-2` card.** `.sc-keys kbd` therefore overrides it to `var(--paper)`. The shortcut cards are the first place on the page a `<kbd>` sits on a card rather than on the section paper (`.use-body`, `.feat-note` and `.foot-note` are all on `--paper`), which is why the collision never surfaced before. It stays token-only so it needs no dark-mode twin — but in dark mode `--paper` #14120f and `--paper-2` #1d1a16 are only nine levels apart, so a light-mode review cannot check it; the caps stay legible there mainly on their `--rule` border, which dark flips to near-white.
- **⚠ Screenshotting a section of this page needs `reduced_motion="reduce"`.** `.reveal` is `opacity: 0` until an IntersectionObserver adds `.in`, so a Playwright `element.screenshot()` of a section taller than the viewport captures it at ~zero opacity — a near-black image in dark mode that looks like a theming bug and is not. The page's own `@media (prefers-reduced-motion: reduce)` block makes `.reveal` unconditionally visible, so the context flag is the fix. `shoot-docs.py` is unaffected: it shoots the *app*, never this page. ⚠ **Second consequence, since the two animations landed:** `reduced_motion="reduce"` also flips both `<picture>` elements to their stills, so a capture taken that way can never show the motion. **Verify an animation by decoding the WebP with Pillow** (`n_frames`, `info['loop']`, frame 0 ≠ frame 1), never by screenshotting this page.
- **The version badge is fetched, not written.** `fillVersion()` reads `releases/latest` from the GitHub API and fills `.ver`; a hard-coded version would go stale on the next release-hook bump. Failure (offline, rate-limited) is silent and the button reads fine without it.
- **Deck fan** — the Marp figure stacks three slides with absolutely positioned cards. They must be `scale()`d down as they go back, not merely translated: a pure translate escapes the grid track and paints over the copy column. **`deck-a` is the only card shown in full** (and the only one at all below the mobile breakpoint), so it carries the slide that has to sell the deck pipeline — currently `samples/marp.md`'s two-column *Plotly: 3D サーフェス* slide, which puts KaTeX, bullets and an interactive 3D surface on one 16:9 frame. The section divider that used to hold the front is decorative and now sits at the back, where only its gradient edge shows. **`deck-a` is a `<picture>`, not a bare `<img>`**: its Plotly surface is drag-rotatable in the app and a frozen still said otherwise, so the front card loops (`slide-12-spin.webp`) with the still behind a `prefers-reduced-motion` `<source>`. ⚠ **`shoot_spin_marp()` owns slide 12 and its still together, and slide 12 is therefore ABSENT from `PREVIEW_SHOTS`** — `element.screenshot()` of a slide `<svg>` rounds (slide 02 comes out 1600×**902**), so a still regenerated by a separate pass could differ in aspect by a pixel and re-introduce the layout shift the `<picture>` exists to avoid. Slide numbers live in `PREVIEW_SHOTS` (and `SPIN_SLIDE`) in `shoot-docs.py`; **inserting a slide into `samples/marp.md` renumbers them**, so re-check both after editing the sample.

- `tools/preview-harness/shoot-docs.py` — generates **every screenshot on the GitHub Pages landing page** (`docs/assets/img/`) in one command, so the page cannot drift from the product. It reuses `shoot.py`'s harness (`start_harness` / `style_init_script` / `ui_lang_init_script` / `wait_for_render`) but differs from it in three deliberate ways. (1) It captures the **1440x900 viewport**, not the full page: `shoot.py` neutralizes every overflow-clipping ancestor to get one tall PNG, which is right for a pixel baseline and wrong here twice over — the result stops looking like the app, and under a *vertical-writing* theme `height:auto` on `#preview` collapses the line length so the capture comes out **entirely blank** (measured on `bunko.css`: a 22378x1800 all-white PNG). Viewport capture also lands the first 文庫 pages in frame for free, because `resetPreviewScrollToStart()` has already parked a `vertical-rl` document at its reading start. (2) It also drives **`editor.html`**, which `shoot.py` never opens, using `cellcheck.py`'s `__initialFile` + `ipc` shim; those shots use a **smaller viewport (1040x660)** because they are displayed at roughly half the width of a preview shot, and putting the same content on fewer CSS px is the only way to keep the code legible — cropping afterwards cannot buy that back. (3) Output is **WebP** (`MAX_EDGE = 1600`, q88) via Pillow: these are screenshots of text, and the lossless PNG set came to 2.9 MB against ~0.65 MB for the same displayed pixels. `--only <names>` regenerates a subset. **`tools/preview-harness/docskeycheck.py`** guards the other half of the same drift problem — that the landing page's `#keys` shortcut list still agrees with the app's `#help-modal` table — and is **stdlib-only, the one `docs/`-facing check needing neither Playwright nor a browser** (both sides are literal HTML plus literal JS string tables on disk, so it runs in well under a second and is cheap enough for a pre-commit hook). `shoot-docs.py`'s `main()` also calls it warn-only beside `check_gallery_sources()`, so whoever regenerates the images hears about both; the hard gate is the standalone entry point, whose exit code means exactly "do the two lists agree".

- **`--only spin` — the two looping figures, and the one pass that is NOT in the default sweep.** `model3d` and the Plotly 3D surface on Marp slide 12 are both genuinely mouse-driven in the app and both read as dead stills on the page, so each ships as an animated WebP with a drawn cursor sweeping in step with the motion. It is opt-in (`spin` / `spin:model3d` / `spin:marp`) because an animated WebP re-encodes byte-differently every run: folding it into the default sweep would add its whole size to the repository each time anyone regenerated a screenshot, for no visible change. Its outputs also bypass `to_webp()`, being WebP already.
  - **model3d is dragged with the REAL mouse.** `interactive: !window.__captureConfig` is true outside `--export-png`, so OrbitControls is attached in the harness too; three's `rotateLeft` is `2π · dx / domElement.clientHeight` at `rotateSpeed` 1, so a horizontal drag of `clientHeight · deg/360` CSS px is exactly `deg` of yaw. `enableDamping` is false, so the pose is final one `scheduleRender()` beat later. The cursor drawn into the frame therefore sits at the coordinate the pointer really was at, not at a guess. The Plotly camera is driven by `Plotly.relayout` instead, because there the exact angle is what closes the loop — ⚠ call `fitMarpSlides()` ONCE before the orbit, never inside it: it ends in `Plotly.Plots.resize`.
  - **The sweep is an oscillation, θ = θ₀ + A·sin(2πk/N), not a revolution.** It loops seamlessly with no repeated closing frame (the k = N phase is deliberately not emitted); a full turn swings model3d's `GridHelper` far enough to grow the union box by about a third, which would cost `--g-cap` a re-measure and buy nothing; and a hand on a mouse moves back and forth, which is the entire message.
  - **Half the frames are byte-identical, and that is the oscillation, not a bug.** `sin(2πk/N)` retraces its outward poses on the way back, so frame k and frame (N/2 − k) mod N are the same phase; expect about N/2 + 1 distinct poses out of N. libwebp encodes the repeats as near-empty delta frames, so they are close to free — a check that asserts *all* frames differ is the one that is wrong.
  - **⚠ `kmin=0, kmax=0` is the encoder flag that matters.** libwebp already reduces each frame to the rectangle that changed, but by default it still inserts a full keyframe every `kmax` frames — measured on the 1600×900 slide that alone was 282 KB vs 182 KB. With keyframes off, animating the **whole slide** costs the changed rectangle plus about one keyframe (~50 KB), which is what let this skip a hand-positioned overlay over the still and its alignment invariant entirely. `encode_spin()` tries lossy and lossless and keeps the smaller (flat-shaded geometry on white is where lossless can win; a Plotly surface is not — measured 120 KB vs 613 KB, so both currently ship lossy). ⚠ Do **not** gate on `PIL.features.check('webp_anim')`: Pillow 12 returns `False` with "Unknown feature" because the flag went away when libwebpmux became mandatory.
  - **`encode_spin()` refuses a frame set with fewer than two distinct frames.** A browser without WebGL2 renders every model3d block as an error box (`shoot.py` warns about it), and 20 identical copies of that box is exactly what would otherwise ship. Budget: the two animations add ~210 KB to a `docs/assets/img` that was 1052 KB.

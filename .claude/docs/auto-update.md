## Auto-update over an internal file share (opt-in, OFF by default)

An **opt-in** startup update check + background install, for **internal (intranet) distribution** — packaged by a distributor's own overlay so the whole flow stays inside the organisation's network. **OFF by default: base md_previewer ships no config file, so nothing runs and the app stays fully offline** (this is the deliberate gate — the capability is compiled into the binary but dormant). Windows-only (`src/updater.rs`, gated behind `#[cfg(windows)]` where it spawns the installer). No new crate dependency — the transport is a plain filesystem path (UNC `\\server\share\...` or local), read via `std::fs`; version parsing/compare and JSON use the existing `serde`/`serde_json`.

- **Config gate** — `updater::load_config()` looks for `update.json` next to the exe first, then in `assets/`. Absent / `enabled:false` / empty `source` / malformed ⇒ returns `None` ⇒ **no thread, no network**. Schema: `{ "enabled": bool, "source": "<UNC or local dir>", "manifest": "latest.json", "timeoutMs": 4000 }`. `assets/update.example.json` is a **non-functional example** (wrong filename on purpose); a distributor supplies the live `assets/update.json` via the existing `assets\*` overlay (no `.iss` change). The whole `assets/` tree is copied into installs, so the example file ships harmlessly but is never read.
- **Trigger — content first, and nothing runs at startup.** The check used to be kicked off from `main()` before `WebViewBuilder::build()`, which was wrong in three compounding ways: `updater::load_config()` ran **on the main thread** (two untimed `fs::read`) ahead of first paint; the worker started **before the webview existed**, so its SMB I/O competed with WebView2 creation and with the `app://` protocol reads for the very document the user was waiting on; and the notification was gated behind the installer download (below). Measured against an unreachable share, that stall is ~2.3 s of SMB failure landing squarely on startup. Now `main()` only records `is_capture` plus owned `upd_exe_dir` / `upd_assets_dir`, and the worker is spawned from the **`CustomEvent::StartUpdateCheck`** arm, fed by whichever of two triggers arrives first:
  - the preview's **`renderdone:` IPC** — the normal path. `__emitRenderDone` is no longer capture-gated, and because it posts on an 80 ms `setTimeout` (a macrotask) while `loadFileFromRust`'s `await renderMarkdown(...)` resumes on a microtask, the `#app-container` reveal + `hideSplash()` are guaranteed to have already run. The signal therefore means *the document is on screen*. It also fires from the render-failure `catch`, so a broken document does not have to wait the watchdog out.
  - a **watchdog** (`UPDATE_WATCHDOG_MS`, 5 s), spawned right after `webview_builder.build()`, for a page that never reports render-done — a JS error before the signal, a hung render, or a launch with no file at all (the drop zone renders nothing). Timed from the webview's creation, so it measures “time since the UI existed”. Skipped entirely in capture mode.

  Idempotency is a plain `let mut update_check_started: bool` owned by the event loop — both triggers funnel through that one single-threaded arm, so no `AtomicBool` / `Once` is needed. The arm itself does no I/O and takes no `webview` lock.
- **The check is two-phase, so the banner is never gated behind the download.** `check_and_prepare` was split, because it used to finish an **untimed multi-MB `fs::copy`** before returning — meaning `UpdateAvailable` could not be dispatched until the whole installer had come over SMB. The worker now runs: (1) `updater::load_config()` (the reads that used to be on the main thread; absent `update.json` ⇒ it stops here having touched no share at all); (2) **`check_manifest()`** — reads `<source>/<manifest>` via `read_with_timeout()` (the blocking read runs on a helper thread with `recv_timeout(timeoutMs)` so an unreachable UNC share gives up promptly instead of hanging for the SMB timeout), parses `{version, setup, notes}`, semver-compares (`parse_semver`/`is_newer`, tolerant tuple compare; parse failure ⇒ "not newer") and returns an `UpdateFound`; (3) publishes `found.as_ready()` into the shared `Arc<Mutex<Option<updater::UpdateReady>>>` (`update_ready`) and posts `CustomEvent::UpdateAvailable { version, notes }` **immediately**; (4) **`prefetch_installer()`** copies `<source>/<setup>` into `%TEMP%\mdp-update\` and, on success, upgrades the stored `setup_temp` to that local path. **`UpdateReady` is deliberately just the path** — the version/notes the banner shows live on `UpdateFound`, and its two consumers (`update:install`, `run_deferred_update`) only launch the file. A click landing mid-download is therefore merely slower, never broken: `as_ready()` points at the share, which both consumers already accepted (it has always been the prefetch-failure fallback). The copy goes to a `.part` file and is `rename`d into place — publishing an installable handle *before* the copy widens the window in which a second instance could observe a half-written `%TEMP%` file, and `fs::rename` replaces atomically on Windows.
- **The log is timestamped** (`[+   707ms] …`), because a 「起動が止まる」 report is about *gaps*, not ordering, and the bare lines made it unmeasurable. Nothing parses `md-previewer.log`, so the format is ours. A healthy enabled run reads: `check triggered by renderdone` → `enabled via …` → `update available … -> …` → `banner dispatched` → `[js] update banner shown` → (seconds later) `prefetched N bytes`. **`banner dispatched` preceding `prefetched` is the invariant this split exists for.**
- **UX = notify then update** — the event loop handles `UpdateAvailable` by calling `window.__updateAvailable({version, notes})` in the webview, which shows **`#update-banner`** (theme-aware, distinct from the transient `#toast`): a small **bottom-right card**, not a full-width top bar — an update is 「気づけばよい」 information, so it must not cover the first lines of the document nor carry modal-like weight. It reuses the help/style modal's `.panel` palette so it reads as native chrome, and carries two update buttons — a filled primary **「今すぐ更新」** (`update-install-btn`) and an outline secondary **「終了後に更新」** (`update-onexit-btn`), which differ only in *when* the install runs — plus an absolutely-positioned **「×」** close in its top-right corner (that button keeps the id `update-later-btn`) and a small underlined **「今後表示しない」** text link. The action row is `flex-wrap: wrap; row-gap: 6px` because the four controls only just fit the fixed `min(320px, …)` card; `#update-optout-btn`'s `margin-left: auto` keeps the opt-out at the right edge whether or not it wraps, which is why a new button belongs *before* it. Its `z-index` (9600) sits *below* `#toast` (10000) and the modals (10001) so a notification arriving while the help modal is open never lands on top of it, and `body.marp.deck-mode` nudges it above `#slide-counter`. Appearance is a `@keyframes` animation rather than a transition, because the `.visible` class is added in the same frame as `display: none` → `flex`. 「今後表示しない」persists `localStorage['autoUpdate:optout']='true'` so a user can permanently suppress it on their machine even under a managed build; the banner JS gates on that flag. `body.capturing` hides the banner so `--export-png` shots are unaffected.
- **The notification must survive arriving mid-page-load** — this used to be the common case (the check thread was spawned *before* the webview was created and finished in well under a second, so `evaluate_script` routinely landed while `index.html` was still parsing). Now that the check is released by `renderdone:`, `__updateAvailable` is normally long since defined — but the **watchdog path can still fire while a slow document is parsing**, so the stash is still load-bearing and must not be removed. Both halves therefore stash instead of dropping, mirroring `loadFileFromRust`'s `DOMContentLoaded`+retry and the `__pendingWorkspace` stash: (1) **Rust** emits `if (typeof window.__updateAvailable === 'function') { … } else { window.__pendingUpdate = … }` — the previous bare `window.__updateAvailable && …` short-circuited to nothing when the function (defined ~line 2380) wasn't reached yet; (2) **JS** — `__updateAvailable` defers into an IIFE-scoped `pending` when `document.readyState === 'loading'` or `#update-banner` (~line 8420, ~6000 lines *after* the function) isn't parsed yet, and the existing `DOMContentLoaded` handler drains both `pending` and `window.__pendingUpdate`. Without both, the banner was silently lost until the next launch — the actual cause of the 「自動更新が働かない」 report, confirmed by CDP-inspecting a live 0.17.0 install (banner element present, `__updateAvailable` a function, opt-out unset, yet `className` empty).
- **Delivery is traceable in `md-previewer.log`** — the Rust handler logs `updater: banner dispatched (version=…)`, and the banner JS reports back over the existing `__dbgLog` (`/__log/`) bridge with `update banner shown v<ver>` / `update banner deferred (dom not ready)` / `update banner suppressed by optout` / `update deferred to exit` (the last one distinguishing which of the two update buttons was pressed). Before these, the log stopped at `prefetched` and could not distinguish "shown", "user opted out" and "silently dropped" — which is why the race went unnoticed. A healthy run shows `banner dispatched` followed by `banner shown`.
- **Install + relaunch (「今すぐ更新」)** — posts `update:install`; the IPC handler (next to `openinstalldir:`) reads `update_ready`, then on a worker thread calls `updater::launch_installer_and_relaunch(setup_temp, exe_path, current_file)`. That spawns a detached `cmd /S /C "…"` (CREATE_NO_WINDOW) that: waits ~1s (`ping -n 2 127.0.0.1 >nul` — console-independent, unlike `timeout`) so this app fully exits and releases its exe lock, runs the Inno installer `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART` (per-user, no UAC; stable AppId ⇒ in-place upgrade), then `start`s the (new) exe — reopening the current file if one was open. It then posts `CustomEvent::QuitForUpdate` ⇒ `ControlFlow::Exit`. (`skipifsilent` in the installer's `[Run]` means the installer won't relaunch the app itself, so the wrapper's `start` does it.) The command string is built by the pure, unit-tested **`installer_cmd_line(setup, relaunch)`** in `src/updater.rs`; `launch_installer_and_relaunch` is now a thin wrapper over **`launch_installer(setup, relaunch)`**, which the two paths share.
- **Install on exit (「終了後に更新」)** — posts `update:onexit`, whose IPC arm does nothing but set the shared `install_on_exit: Arc<Mutex<bool>>` (declared next to `update_ready`) and log — **no thread, no `update_ready` read**. The banner then closes and a toast confirms the reservation, so the reader keeps working. The install itself happens in `run_deferred_update()`, called from the **`WindowEvent::CloseRequested` else-branch** — the app's only user-initiated quit — just before `ControlFlow::Exit`; it passes `relaunch: None`, so the chain stops after the installer and the new version simply appears at the next launch. **The call is synchronous, not on a worker thread**: the process is exiting, and a detached thread can be killed before its `spawn()` completes (`Command::spawn` returns immediately, so the quit isn't held up). The reservation is in-memory and per-session — closing the banner with 「×」 and relaunching gets the notification back. `update_ready` / `install_on_exit` are captured directly by the event-loop closure (only clones were handed to the IPC handler), so no alias in the `src/main.rs` block above `event_loop.run` is needed.
- **Failure = silent no-op** — unreachable share, timeout, missing/invalid manifest all log to `md-previewer.log` (`updater: …` lines) and return `None`; the UI is never disturbed. Unit tests live in `src/updater.rs` (`#[cfg(test)]`): `parse_semver`/`is_newer`, `installer_cmd_line` (both the relaunching and the exit-path command strings), `load_config`'s gate, and the two phases — `phase1_detects_without_downloading` (the split's whole point: phase 1 returns a share-side path and has copied **nothing**, and `as_ready()` is already installable), `phase2_prefetch_upgrades_to_temp` (incl. no surviving `.part`), `phase2_failure_is_soft` (a missing installer still yields a banner) and `installer_temp_path_uses_file_name_only`.
- **Distributor setup** (preparing the share, publishing a new version, editing `update.json`/`latest.json`) is documented by the distributor's own package.

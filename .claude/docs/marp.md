## Marp Mode

When a markdown document begins with a YAML front-matter block containing `marp: true`, the previewer switches to a slide-rendering pipeline backed by `@marp-team/marp-core` (bundled as a single IIFE at `assets/libs/marp/marp.iife.js`).

- **Themes** — slides render as 16:9 sections using Marp's built-in themes (`default` / `gaia` / `uncover`, selected via the `theme:` directive). Additional user-defined themes can be dropped into `assets/marp/*.css` (each file must begin with a `/* @theme <name> */` header) and selected by name via the same `theme:` directive — the Rust host scans `assets/marp/` at startup and exposes the file list as `window.__marpThemes`, which `renderMarp()` fetches once and registers via `marp.themeSet.add()` before rendering. **Eight colour themes are bundled as one family**: `magenta.css` is the base (`@import "default"`) and `indigo` / `purple` / `green` / `gold` / `silver` / `black` / `dark` are each `@import "magenta"` plus a token block — Marpit resolves `@import "<theme name>"` against the whole `themeSet`, user themes included, inlining the import in place (so the packed order is default → magenta → variant and the variant's `section` tokens win by source order), but **only when the `@import` precedes the first rule** (a later one is silently ignored), and it rewrites `:root` to `section`. Sample: `samples/marp-themes.md` (`theme: gold`).
  - **Colour model — one input, everything derived.** Each theme's `:root` declares a single `--theme-color` (its designed accent) and writes every chromatic token as a relative colour of it, `oklch(from var(--theme-color) L calc(c * K) calc(h + ΔH))`: **hue and chroma follow the picked colour, lightness is fixed by the design**, so whatever the reader picks in the ⚙ pane h1 / h2 / links / inline code keep their contrast, a pastel pick gives a pastel deck and a grey pick a silver one. L / K / ΔH were solved from the designed hex values by **`tools/marp-theme-gen/gen_themes.py`**, which also *emits* the seven variant files from its hex table (`magenta.css` is hand-written and is the template; re-run the script after editing a colour there, and keep `magenta.css`'s `section.invert` equal to the magenta dark block it prints). With `--theme-color` at its default the derivations reproduce those hexes **byte for byte** — verified through the harness with a 1×1 canvas readback, since `getComputedStyle` returns relative colours in `oklch()` form. **Gradients need `in srgb`**: once a stop is a non-legacy colour (`oklch()`), CSS Color 4 switches the gradient's default interpolation space from sRGB to oklab, and the section-divider gradient came out visibly different from the old hex-stop version (1.9 M differing pixels on `samples/marp.md` slide 2) although every stop was identical. `linear-gradient(135deg in srgb, …)` / `radial-gradient(… in srgb, …)` restore the original ramps; the residual difference is ≤ 1/255 per channel (float stops vs 8-bit hex). Neutrals (`--bg` / `--ink*` / `--surface` / `--surface-alt` / `--code-bg` / `--code-ink`) are fixed. **`--code-bg` / `--code-ink` are the app's own normal-pipeline code colours** — `#f6f8fa` / `#24292e` in a light token set, `#161b22` / `#c9d1d9` in a dark one, i.e. byte-identical to `body:not(.marp) #preview pre` and its `body.dark-mode` twin — so a slide's code block looks like the same app, and Marp only switches light↔dark (see *index.html's element chrome…* below for why the theme must also restate the highlight.js palette). `--surface` / `--surface-alt` paint the table rows the default theme used to paint from its `light-dark()` variables (`#fff` / `#f6f8fa`, so the light look is unchanged) — which is what lets a dark set recolour them. `--divider-a/-b/-c` **duplicate** the accent-deep / accent / rule formulas on purpose: `section.invert` re-derives the accent tokens for a dark slide but must not lighten the section-divider gradient, and a `var(--accent-deep)` reference would follow the override. `--confidential-color` is `color-mix(in srgb, var(--accent) 13%, transparent)` (= the old `rgba(194,24,91,.13)`), and the theme also feeds `--md-message-*`, `--laser-color` (absolute chroma, so it stays visible under a muted pick) and `--marker-color`. **`black` / `silver` are the exceptions**: their accent is (near-)achromatic so `c * K` is meaningless — black writes the accent family as absolute greys and lets only the rule family / laser / marker take the picked hue (`min(c, 0.08)`), silver caps chroma at its designed value (`min(c, 0.0324) * K`) so the picker tints without saturating.
  - **`section.invert` = a dark token set from the same `--theme-color`** (`<!-- _class: invert -->`, which the editor's slide-class picker already offered). marp-core's `default` implements `.invert` as nothing but `section:where(.invert){color-scheme:dark}` — zero specificity, so none of our rules lose to it — and the table-row backgrounds / highlight.js colours it leaks into this family are `light-dark()` values, so **every token set must also declare `color-scheme`** (light in `:root`, dark in `section.invert`; `dark.css` reverses both) or a dark slide keeps white rows. `dark.css`'s `:root` is byte-identical to `magenta.css`'s `section.invert` — a documented duplication, marked "keep in sync" in both files; its `section.invert` swaps back to the light set. The seven variants are generated from a hex table (light + dark per hue) by `tools/marp-theme-gen/gen_themes.py`; each derived line carries the hex it reproduces in a trailing comment so a file reads as a palette.
  - **index.html's element chrome no longer leaks into slides.** The normal pipeline's `#preview pre` / `code` / `pre code` / `a` / `th` / `td` / `blockquote` / `hr` rules (and their `body.dark-mode` and `@media print` twins) are now `body:not(.marp)`-scoped. At ID specificity they out-ranked every Marp theme's own `section pre` / `section a` (0,0,2): magenta's dark `pre` had **never** rendered — slides showed `#f6f8fa` behind the theme's near-white code text, braces invisible — and every theme's links were `#0366d6`, table headers `#f6f8fa`, quote rules `#dfe2e5`; the print `!important` rules forced a light `pre` into Marp PDFs. This is a visible (and intended) change for the built-in `default` / `gaia` / `uncover` too, which now render as Marp designed them. `#preview table { width: 100% }` is deliberately left alone — the `.marp-fig` `fit-content` centering depends on it (see *Figure horizontal centering*).
  - **The one piece of chrome that CANNOT be scoped is the highlight.js theme, so the Marp theme restates it instead.** `assets/index.html` `<link>`s `libs/highlight.js/github.min.css` — the GitHub *light* theme — unconditionally from `<head>`, and `renderMarp()` deliberately re-runs `hljs.highlightElement()` over marp-core's slide code blocks, which stamps `class="hljs"` on every slide `<code>`. Being an external file it cannot be given a `body:not(.marp)` prefix, and its `.hljs{color:#24292e;background:#fff}` (0,1,0) and `pre code.hljs{padding:1em}` (0,1,2) out-rank the theme's `section pre code` (0,0,3). So `--code-bg` / `--code-ink` never applied and the light token set painted a **white code box, dark-on-dark, inset 1em inside the theme's near-black `pre`** — the bug this family shipped with. marp-core's own `light-dark()` palette cannot save it either: it is written `pre :where(.hljs-keyword)` = **(0,0,1)**, so it loses to everything. `magenta.css` therefore carries the palette itself, at `section pre …` (which Marpit rewrites to `div.marpit > svg > foreignObject > section :is(pre, marp-pre) …`, comfortably above the link's class specificity), with values copied verbatim from the app's two existing palettes — `github.min.css` for light, index.html's `body.dark-mode .hljs-*` block for dark. **The switch must be `light-dark()`, not a `section.invert` branch**: `dark.css` reverses the two token sets (`:root` is its dark set), so an `.invert`-keyed rule is exactly backwards there, whereas `light-dark()` reads each set's own `color-scheme` — the declaration the family already requires — and is right in both. The two source palettes group tokens *differently* (`.hljs-template-variable` sits with the keywords in light and with the numbers in dark), so the block is their token-by-token union, and four tokens absent from the dark palette (`operator` / `selector-attr` / `selector-pseudo` / `bullet`) follow the dark value of a sibling sharing their light one. Correspondingly the `body.dark-mode .hljs*` overrides in `index.html` gained the `:not(.marp)` the rest of that chrome already had — at (0,2,x) they would out-rank the theme and paint GitHub Dark tokens onto a *light* slide whenever the app's `M`-key dark mode happened to be on (which is why, before this, slide code was only ever legible in dark mode). Normal-pipeline colours are untouched. Regression net: `samples/marp-themes.md` carries a code fence on both a light slide and the `_class: invert` one.
- **Extension inheritance inside slides**:
  - `[^id]` footnotes — extracted before passing markdown to marp-core and restored as `<sup>` tags afterward. Each footnote's body is rendered **at the bottom of the slide it is referenced on** (compact style: small font + top rule, no heading / back-links), via `renderMarpSlideFootnotes()` + a post-pass in `renderMarp()` that runs *after* the figure-centering / split passes so the block lands as the section's last child and (in the flex-column slide layout) is pushed to the bottom by `margin-top:auto`. Numbering is **global / continuous** across all slides (matches the in-text `<sup>`), so a footnote referenced on multiple slides repeats its body on each with the same number. Because that means N rendered copies, the canonical `id="fn-…"` anchor target is stamped only on the **first** copy (a caller-owned `emitted` Set threaded into `renderMarpSlideFootnotes(ids, emitted)`), while **every** copy carries `data-fn-id` — the attribute the hover tooltip resolves against, so it can prefer the copy on the reader's own slide. Sections carrying footnotes get a `marp-has-footnotes` class; split slides get `grid-column: 1 / -1` on the block. Carries into HTML export automatically (the per-slide blocks live in the serialized `#preview` DOM).
  - ` ```mermaid ` and ` ```csv ` / ` ```tsv ` code blocks — post-render DOM substitution, reusing the same renderers as the regular pipeline.
  - ` ```feynman ` code blocks — same `.feynman-block` placeholder + `renderFeynmarkCached()` as the regular pipeline (see *Preview Pipeline → Feynman diagrams* (`preview-blocks.md`)), plus KaTeX loaded the same way for math labels/equation embedding.
  - GitHub task lists (`- [ ]` / `- [x]`) — marp-core has no task-list plugin, so a `renderMarp()` DOM post-pass (`applyTaskLists`, shared with the normal pipeline) converts the literal `[ ]` text into disabled checkboxes — see *Preview Pipeline → GitHub task lists* (`preview-markdown-ext.md`).
  - Definition lists (`用語` / `: 説明`) — marp-core has no deflist plugin *and* runs `breaks: true`, so a `⦃DL⦄`/`⦃DT⦄`/`⦃DD⦄`/`⦃/DL⦄` sentinel pre-pass (sharing `scanDefList()` with the normal pipeline) plus a DOM post-pass builds the `<dl>`; it must run before the `.marp-fit-body` wrapper — see *Preview Pipeline → Definition lists* (`preview-markdown-ext.md`).
  - Video / YouTube image-syntax embeds — `applyVideoEmbeds()` runs inside `renderMarp()` (just before `applyImageSizing()`) so `![](clip.mp4)` / `![](youtube-url)` become `<video>` / `<iframe>` in slides too.
  - `highlight.js` for syntax-coloring.
  - KaTeX math and Marp directives like `paginate` work out of the box.
- **Figure horizontal centering** — when a non-split slide contains a `.mermaid` / `.csv-table` / native `<table>` / `.abc-notation` / `.plotly-block` / `.markwhen-timeline` / `.tikzcd-diagram` / `.tikz-diagram` / `.feynman-block` / `<video>` / `iframe.video-embed` / image-(or video-)only `<p>` (a paragraph whose sole meaningful child is `<img>` / `<video>` / `<iframe>`) as a **direct child** of `<section>`, a post-pass in `renderMarp()` tags each such element with the class `.marp-fig`, and CSS centers it **left-right** in normal document flow. Three centering mechanisms: (1) **inline-SVG containers** (`.mermaid` / `.markwhen-timeline` / `.abc-notation` / `.feynman-block`) and image-only `<p>` via `text-align: center`; (2) **tables** (native `<table>` + `.csv-table`) via `width: fit-content; max-width: 100%; margin-left/right: auto` — the `fit-content` is essential because the general `#preview table { width: 100% }` rule (ID specificity) would otherwise force a marp table to full slide width, making `margin: auto` a no-op (no free space) so the table hugs the left; reasserting content width gives `margin: auto` room to center, and `max-width: 100%` caps a table wider than the slide. A `<table>` deliberately gets no `text-align` so its cell text isn't centered; (3) **Plotly** (`.plotly-block`) via `align-items: center` on its `body.marp .plotly-block` flex column (not `margin: auto`, which is inert on a full-width flex block) — this centers a width-fixed chart (`layout.width` < slide) while an autosizing chart is NOT shrunk (Plotly measures the full-width container and writes an explicit width onto the rendered SVG, so the now-definite-size flex item still spans the slide). The same `width: fit-content` is applied to `.md-vcenter > table` / `.csv-table`, and vcenter Plotly is centered by the shared `align-items: center`. The figure stays in document order; there is **no vertical centering and no sweeping of following siblings**. Split slides (`split` / `split-2` / `split-3` / `split-4`) are excluded. **The automatic *vertical* centering was removed** — the old version wrapped the first figure and all following siblings into a `flex:1` `.marp-figure-stage` with `justify-content:center`, but when the figure was taller than the remaining space, flexbox center-overflow spilled the figure's top over the heading/text above it (the "大きな Mermaid 図が文中にあると上下の文章と重複する" bug). Now figures flow normally and the body autofit (`A` key, *Auto-shrink*) scales an overflowing body instead of overlapping it; **`::: vcenter`** is the explicit opt-in when vertical centering is wanted (see *Preview Pipeline → Text alignment* (`preview-markdown-ext.md`)).
- **Column layout** (`<!-- _class: split -->` / `split-2` / `split-3` / `split-4`) — break a slide into 2 / 2 / 3 / 4 equal-width columns. Authors separate columns with a `+++` line at the start of a line; a `renderMarp()` pre-pass replaces each `+++` with a `⦃COL⦄` sentinel paragraph (skipping fenced code blocks so e.g. ```diff stays intact), and a post-pass groups direct children of `section[class*="split"]` into `<div class="split-col">` buckets at every sentinel `<p>`. Leading `<h1>` / `<h2>` of the first bucket are pulled out as a full-width header row (`grid-column: 1 / -1`) so all columns start at the same y. CSS applies `display: grid` with `repeat(N, 1fr)` and per-class gap. Runs after footnote restoration (so `<sup>` refs stay in their column) and before mermaid / csv / plotly substitution (so those land inside the correct column). The figure horizontal-centering pass explicitly skips these sections.
- **Inline column region** (`::: columns` … `+++` … `:::`) — switch to multi-column **partway through** a slide and back to single-column, without making the whole slide a `split`. Uses the same Pandoc-style fenced-div family as text alignment (`::: center`): `::: columns` (or `::: columns-3` / `columns-4` to force a count) opens the region, a `+++` line divides columns inside it, and a bare `:::` closes it (returning to full-width single-column). Column count is the explicit `columns-N` if given, else the number of `+++`-delimited buckets (clamped 2..4). Because `:::` closes either an alignment or a columns block, the alignment pre-pass was generalized into a single **fenced-div pre-pass** that keeps a `fenceStack` of the open block kinds so each `:::` emits the correct close sentinel (`⦃/ALIGN⦄` vs `⦃/COLS⦄`) for the innermost block — this also lets `::: center` nest inside a column. Inside a `columns` region a lone `+++` is emitted as the same `⦃COL⦄` sentinel the split pre-pass uses (the split `+++` pre-pass stays untouched and is inert on a non-split slide, so it leaves the region's `+++` for the fenced-div pass). The post-pass (run right after the split post-pass, before the alignment post-pass) finds each `⦃COLS⦄` / `⦃COLS:N⦄` `<p>`, replaces it with a `<div class="inline-cols">` (`.inline-cols-3` / `-4` for ≥3 columns), and walks the following siblings into `<div class="split-col">` buckets (reusing the split column class + CSS) at every `⦃COL⦄`, stopping at `⦃/COLS⦄`. CSS gives `.inline-cols` a `display:grid` `repeat(N,1fr)` layout scoped under `#preview` (generalized from `body.marp #preview` so the same grid CSS serves the normal-pipeline `columnsDiv` extension below). Carries into HTML export automatically (serialized DOM + inline CSS). **Normal (non-Marp) documents now also render `::: columns`** — see *Text alignment → Inline columns in the normal pipeline* (`preview-markdown-ext.md`) below. Sample: the "スライド途中からのカラム" slide in `samples/marp.md`.
- **Theme picker via S key** — in Marp mode, pressing `S` opens the same modal as the regular style picker but lists Marp themes instead: marp-core built-ins (`default` / `gaia` / `uncover`) plus every user theme discovered under `assets/marp/*.css` (theme name extracted from each file's mandatory `/* @theme <name> */` header; user themes sorted by name). Rows whose CSS declares `@user-vars` carry the same **⚙** as user styles — see *Styles & Theming → Per-style settings → Marp themes get the same ⚙* (`styles-theming.md`). Selecting a row rewrites the front-matter `theme:` line of the *current file on disk*: `applyMarpTheme()` calls `setMarpTheme()` on **`currentMarkdownRaw`** (the canonical un-rewritten source; see *Preview Pipeline → Image serving via the `/userfile/` protocol → Raw vs. content channel* (`preview-files-media.md`) — kept as defensive practice so any future display-only source rewrite can never leak into the `.md`) to splice / replace the line (preserving LF vs CRLF), then posts `savefile:<json>` IPC to the Rust host. The new `savefile:` handler in `src/main.rs` does the same disk-write + 1.5s `suppressed_saves` dance as `editor:save:`, additionally pushing the new content to the paired editor (via `EditorRegistry::push_file_to_editor`) so its buffer doesn't drift from disk, and finally re-renders the preview via the existing `EditorSavedContent` event path.
- **Auto-shrink overflowing slides to fit — body-only scaling** (`A` key, default on, persisted in `localStorage.marpAutofit`) — marp-core renders each slide as a fixed `1280×720` logical box (`<svg viewBox><foreignObject width=1280 height=720><section>`); content taller than the slide is otherwise clipped by the `foreignObject`. The goal is to shrink an overflowing slide's **body only**, keeping the **title (H2) / header / footer at their natural size** so titles stay consistent across slides (the earlier version scaled the whole `<section>`, shrinking the title too). Two pieces:
  - **Body-wrapper post-pass** — a pass at the end of `renderMarp()` (after the figure / split / footnote passes) walks each non-`split` `<section>` and wraps its **body** content into `<div class="marp-fit-body">` (adding class `marp-has-fitbody`). Body = everything except the *fixed head* (leading `<header>`(s) + the leading heading run = the title) and the *fixed tail* (trailing `<footer>`). Any `<footer>` is first hoisted to be the section's last direct child via a `:scope footer` descendant scan (a footer left inside a scaled `.md-vcenter` wrapper would shrink — a transformed wrapper becomes the containing block for its absolute footer; footers are usually `position:absolute` so moving them in the DOM doesn't change where they paint). The `.md-vcenter` and `.marp-footnotes` blocks are swept **into** the wrapper (body content), so they scale with the body. `split` / `split-*` (grid) slides are skipped — they fall back to uniform section scaling.
  - **`fitMarpSlides()`** — for each `<section>` (all logical-coordinate measurements): resets prior inline styles on the wrapper and the section, then, **if a `.marp-fit-body` wrapper exists**, computes the height available to the body = `H − topUsed − bottomUsed`, where `topUsed` (space above the body: header + title) is `(bodyRect.top − sectionRect.top) / scale` with `scale = sectionRect.height / section.offsetHeight` (display/logical ratio, so it's correct under the svg display scaling) and `bottomUsed` = section `padding-bottom` + any in-flow (`static`/`relative`) footer height. The body's **natural** content height is measured by momentarily neutralizing the flex clamp (`flex:none; height:auto; overflow:hidden`) — the `flex:none` is required because on `::: vcenter` / footnote slides the wrapper is `flex:1 1 auto; min-height:0`, which would otherwise clamp `scrollHeight` and hide an overflowing figure inside the `flex:1` `.md-vcenter`; and the **`overflow:hidden` must not be `visible`** — it makes the wrapper a **block formatting context, exactly like the `overflow-y:auto` the fit then applies**. Under `visible` the leading child's `margin-block-start` and the trailing child's `margin-block-end` *collapse through* the wrapper's edges and are absent from `scrollHeight`, so the instant the fit is applied the BFC contains them and the content is taller than the box that measurement sized — leaving a scrollbar on a slide the fit report calls fitted. The trailing margin of a body ending in a `<p>` / `<ul>` / `<dl>` is 16px, which is exactly how much the `samples/marp.md` 定義リスト slide overshot by. **Measure in the box model you apply**: a future edit that changes the applied `overflow` must change this measurement with it. (Also note the measurement is taken at the *natural* width while the applied state widens the box to `(100/f)%`; a reflow there can only make ordinary text flow *shorter*, and anything that does grow falls back to the scroll region below.) When it overflows (`contentH > avail + 1`) only the **wrapper** is scaled + made a scroll region: `f = __marpAutofit ? max(0.5, avail / contentH) : 1` (autofit ON shrinks to the `__MARP_FIT_MIN = 0.5` floor; **autofit OFF uses `f = 1`, i.e. no shrink** — the reorder that dropped the old early `if (!__marpAutofit) return` so the wrapper path now runs regardless), `transformOrigin: top left`, `width: (100/f)%` (fills after the horizontal scale), `height: (avail/f)px` (renders at exactly `avail` after `scale(f)`; locks layout height so no extra space is reserved / an in-flow footer isn't pushed down), `overflow-y: auto` + `overflow-x: hidden`, `transform: scale(f)` (only when `f !== 1`). Because the box is `avail/f` and the content is `contentH`: autofit ON & unfloored → `avail/f === contentH` so the box holds the whole body and **no scrollbar appears** (unchanged look); autofit ON & floored at 0.5 → box `2×avail < contentH`; autofit OFF → box `avail < contentH` — the last two show a **scrollbar** so the reader reaches the rest, with the title/header/footer (outside the wrapper) staying fixed and full-size. Plain (non-Ctrl) wheel is not `preventDefault`ed outside vertical-writing mode, so the wrapper scrolls natively in deck / scroll / list modes. **Fallback** — a section with no wrapper (split / inline-cols grid slides) keeps the old uniform whole-section scaling (enlarge box to `1/f` then `scale(f)` so the rendered box snaps back to `1280×720` and the background still covers the slide; the title scales too there).
  - **CSS** — `.marp-fit-body` is `display:block` by default (so a non-overflowing normal slide preserves the theme's own vertical layout); `section.marp-has-vcenter > .marp-fit-body` and `section.marp-has-footnotes > .marp-fit-body` are `flex:1 1 auto; min-height:0; display:flex; flex-direction:column` so the nested `.md-vcenter`'s `flex:1` vertical centering still works and footnotes (`margin-top:auto`) stay pinned to the body's bottom.

  The pass is idempotent (reset → measure → re-apply). When `__marpAutofit` is off, body-wrapper slides still get the `f = 1` scroll treatment (bounded to `avail` with `overflow-y: auto`) so an overflowing body is scrollable rather than clipped; only the **fallback** whole-section (split / grid) path early-returns when off (those revert to being clipped by the `foreignObject`, since they have no fixed title/footer to scroll under). Called from `__marpUpdateDeck()` (so the slide just made `.active` in deck mode — the others are `display:none` and measure 0, so they get fitted when navigated to) and once more via `requestAnimationFrame` at the end of `renderMarp()` (after the async mermaid / abc / plotly renders so their final heights are accounted for). Orthogonal to the deck-mode `Ctrl+Wheel` zoom, which transforms the **svg** (this transforms the inner **`.marp-fit-body`** / section), so they compose; `__resetMarpZoom()` clears only the svg transform, leaving the fit intact. Carries into HTML export automatically — `buildExportArtifact()` serializes the post-pass `#preview` DOM, so the `.marp-fit-body` wrapper and its inline `transform/width/height` ride into the artifact. Sample: the 自動縮小 slide in `samples/marp.md`.
- **Three view modes** (cycled by `P`: scroll → deck → list → scroll):
  - **Scroll mode** (default) — stacks every slide vertically.
  - **Deck mode** (`body.deck-mode`) — one slide at a time, navigated by `←` / `→` / `PgUp` / `PgDn` / `Space` / `Home` / `End`, with a counter overlay in the bottom-right and `F` to toggle fullscreen. **Cursor-anchored zoom** — `Ctrl+Wheel` zooms the active slide centered on the mouse pointer (drag to pan once zoomed); implemented in `assets/index.html` as a CSS `transform: translate()+scale()` (origin `0 0`) on the active slide `<svg>`, with `__marpZoom`/`__applyMarpZoom`/`__clampMarpPan` state and a non-passive `wheel` listener that `preventDefault`s WebView2's built-in `Ctrl+Wheel` browser zoom *only* while in deck mode (so scroll/list keep the native zoom). Each wheel tick **animates** to the target scale via a `transform 0.16s ease-out` CSS transition (`__MARP_ZOOM_ANIM`, set inline on the active svg); the transition is set to `none` during drag-pan so dragging tracks the cursor with no easing lag. To keep the cursor-focal math accurate *during* an in-flight animation, the identity-state geometry (`{left,top,w,h}` at scale 1) is cached once in `__marpZoomBase` (measured via `getBoundingClientRect` on the first zoom, when the transform is still cleared) and the rendered box is then derived logically as `base + (tx,ty)` rather than re-measured — a live `getBoundingClientRect` would return the mid-transition box and corrupt the focal point / pan clamp. `tx/ty` are accumulated in screen px. Zoom auto-resets to 1:1/centered (and `__marpZoomBase` is dropped) on slide change, deck entry, re-render (all via `__marpUpdateDeck()`), on leaving deck mode (`setMarpView()`), and on window resize (cached base would otherwise go stale). **Laser pointer** — pressing `Z` in deck mode toggles a software laser pointer that follows the mouse with a glowing head dot + a short fading **comet trail** (and hides the OS cursor over the slide). Implemented in `assets/index.html` as a viewport-fixed `<canvas id="laser-canvas">` overlay (`pointer-events:none`, `z-index:9500`) driven by a `requestAnimationFrame` loop (`__laserLoop`): a `window` `mousemove` listener pushes timestamped `{x,y,t}` samples (screen `clientX/clientY`) into `__laserPoints`, the loop drops samples older than `__LASER_TRAIL_MS` (550ms) and strokes them as a width/alpha-tapering trail then a glow (`shadowBlur`) head dot with a white core. Because it tracks the physical cursor it is correct regardless of the zoom/pan transform on the active slide, and it never `preventDefault`s so `Ctrl+Wheel` zoom / drag-pan keep working underneath. The canvas backing store is sized to `devicePixelRatio` (`__resizeLaserCanvas`, also re-run on window resize). The color is **CSS-specified** via the `--laser-color` custom property: `__laserColor()` reads it from the **active slide's** `<foreignObject> section` first (so a Marp theme can brand it — every `assets/marp/*.css` colour theme derives it from its `--theme-color`), falling back to the `:root` default `#ff2d2d` in `assets/index.html`. State lives in `__laserOn` / `setLaser(on)` (toggles `body.laser-on`); the laser is **deck-mode only** and auto-disabled by `setMarpView()` when leaving deck mode and by the Marp-exit cleanup in the render path.
  - **List mode** (`body.list-mode`) — every slide as a clickable 16:9 thumbnail in a responsive CSS grid; clicking a thumbnail jumps into deck mode focused on that slide.
- **Persistence** — the active mode is persisted to `localStorage.marpView` (`'scroll' | 'deck' | 'list'`); the legacy `localStorage.deckMode` boolean is read once for back-compat.
- **Slide TOC sidebar** — in non-workspace Marp mode the TOC sidebar shows a **slide table of contents** in **scroll / list** modes (hidden in **deck** mode so the slide stays immersive, via `body.marp:not(.workspace).deck-mode #toc-sidebar { display:none }`). `generateMarpTOC()` in `assets/index.html` (called at the end of `renderMarp()`) mirrors `generateTOC()` but uses each slide `<svg data-marpit-svg>` as the scroll/highlight unit (slides live inside `foreignObject`, so this avoids relying on `scrollIntoView` of inner heading elements — the same model as `applyEditorScroll`'s Marp branch). It lists every `section h1`–`h6` (level-indented like the normal TOC); each item carries `data-target=<heading id>` (export / a11y) and `data-marp-slide=<index>` (live nav). Clicking scrolls the slide `<svg>` into view (scroll mode) or jumps into the deck focused on that slide (list mode, like a thumbnail click). A scroll-spy `IntersectionObserver` over the slide `<svg>`s highlights the active slide's headings. Carries into HTML export automatically (the populated `#toc-sidebar` is serialized; the export's inline scroll-spy keys off `data-target`). Workspace Marp keeps the file tree (no slide TOC), unchanged.
- **Constraints** — in Marp mode section numbering and the `M`-key dark toggle are no-ops (Marp themes win — a toast explains). The `S` key is repurposed to the Marp theme picker described above instead of being disabled. **Editor-sync** *does* work in deck / scroll modes: marp-core's SVGs carry no `data-line`, so `renderMarp()` stamps each slide `<svg>` with the source line of its starting `---`/`***`/`___` boundary, and `applyEditorScroll(line)` advances the deck (or scrolls) to the slide whose stamped line is the largest `<= line`. The `slideStartLines` scan that produces these line numbers must run on the **original** source markdown (not the footnote-extracted / `+++`-expanded copy, which shifts line numbers) and must skip fenced code blocks (so a `---` inside ``` isn't counted as a phantom boundary) — the separators' count/order are preserved by the pre-passes, so the i-th boundary still maps to the i-th slide. List mode has no scroll target and bails. The user-style `<link id="user-style">` is also stripped from `<head>` on entering Marp mode (so generic `body` / `#preview` / heading rules from `parchment.css` / `tategaki.css` etc. don't cascade into slide `<foreignObject>` text); `localStorage.styleName` is preserved, and the link is re-injected automatically when the next non-Marp document is rendered.

- **Selection marker (highlighter behind text, auto-fade) — Marp only** — in **Marp mode** (`body.marp`), selecting text in a slide paints a translucent **highlighter band behind the glyphs** (so the text stays crisp on top and the band reads on any background, incl. dark slides) instead of the browser's blue selection, and the band **auto-fades after ~2s**. In **normal (non-Marp) previews the feature is off** — the native blue selection is kept (both the suppression CSS, scoped to `body.marker-supported.marp`, and `drawMarker()` bail out when `body.marp` is absent). Implemented purely webview-side in `assets/index.html` (no Rust changes) on the **CSS Custom Highlight API**: a single module-level `Highlight` (`__markerHighlight`, registered once via `CSS.highlights.set('marker', …)`) holds a *clone* of the live selection range, and the browser paints `::highlight(marker)` as the text background — so the band tracks the selection **smoothly as you drag** and stays aligned under the Marp deck-mode zoom/pan **automatically** (range-based; no manual coordinates / no overlay / no per-rect math, unlike the earlier `getClientRects()` band approach). The selection **range is kept while the marker is visible** — so `Ctrl+C` copies during that ~2s window — and is **auto-cleared together with the marker** when it fades (the `clearMarker(dropSelection)` fade-completion path calls `removeAllRanges()`, guarded to a still-in-`#preview` selection so it never wipes a selection the user has since made elsewhere). The native selection color is suppressed only inside `#preview` **and only when the API is available** (`body.marker-supported #preview ::selection { background: transparent }`, the class added at init after feature-detecting `Highlight`/`CSS.highlights`), so unsupported engines keep their normal selection. **Color**: `::highlight()` pseudos don't inherit custom properties in Chromium, so `var()` won't resolve there — instead `__resolveMarkerRGB()` reads the `--marker-color` custom property (from the element containing the selection first, then `:root`; default highlighter yellow `#ffd60a`) via a throwaway probe to normalize any CSS color to `[r,g,b]`, and `__setMarkerFill(alpha)` writes the literal `::highlight(marker){background-color:rgba(r,g,b,alpha)}` rule into a dedicated `<style id="marker-style">`. A Marp theme or user style can rebrand it by setting `--marker-color` on `section` / `#preview`, exactly like `--laser-color` brands the laser pointer. `drawMarker()` (wired to `selectionchange`) re-adds the cloned range on every change (single range, no stacking) and clears on a collapsed / out-of-`#preview` selection. `armMarkerFade()` waits the ~2s visible period (`__MARKER_LIFE_MS`) then animates the fill alpha `0.55→0` over `__MARKER_FADE_MS` via `requestAnimationFrame`, with a **guaranteed-clear `setTimeout` safety** (`__markerFadeSafety`) so the marker still vanishes if rAF is throttled (window occluded mid-fade). The fade is armed based on mouse-button state (`__markerMouseDown`): the marker stays solid (and grows) during a drag-select and (re)arms on `mouseup`; keyboard / programmatic changes happen with the button up so they arm directly in `drawMarker()` (each change restarts the countdown). No `resize` handling is needed — the range-based highlight re-paints natively on layout changes.
